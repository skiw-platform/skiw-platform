## 2026-10-14 — M1d-2: bootstrap-secrets restore and the owner-only key-version override
- **Decision:** (1) **`bootstrap-secrets restore --env-file <env>`** (`infra/host/skiw_host/bootstrap_secrets.py`) reads the decrypted `skiw-escrow-1` bundle on stdin (the owner pipes `age --decrypt` over SSH; the private identity never reaches the host) and checks it all in memory before writing anything: the format, every inventory app key present and no other entry (a DB password is refused), each version a `v<n>:<base64>` line, not repeated, equal to its SHA-256 (constant-time compare) and at least 32 bytes (`app/config/env.py` `MIN_KEY_BYTES`). Any refusal, a non-empty store or an existing `.restored` exits 2 with nothing written and no directory created; messages name the key and the entry number, never a value (UNI-09). (2) **Order and commit point (same as `init`, M1d-1 / PR 38 R1):** a fresh escrow bundle of exactly what will be installed is written first (so a version minted by the override is escrowed before it exists on the host) and its directory entry made durable; then every version is installed verbatim, one file per key, oldest first; then `/etc/skiw/secrets/.restored` (root, 0400, content: the UTC time); then the store directory is synced. **The marker is the last file before the commit point**: a failure writing any key file or the marker removes everything the run wrote (exit 1, retryable). After the commit point the override lines and the summary line form the final log step; if any of them fails the keys, the bundle and the marker are kept and the run exits 3 with a value-free message that repeats the override names and versions so the owner can record them by hand. (3) **`init` and `restore` both refuse when `.restored` exists**, with a message naming it (checked before the generic non-empty-store check). (4) **`--allow-new-key-version NAME`** (repeatable; duplicates collapse; restore only; app-key names only, else exit 2 before anything is read or written): adds one new newest version from `os.urandom(32)`: `v1` when the bundle lacks the key (the only way a bundle missing a key is accepted), otherwise the newest version number plus one; older versions are kept so data under them stays readable. Each override is one line, `restore minted <name> v<n> (--allow-new-key-version)`, on stderr, in the journal and in the deploy log; restore mints nothing else. (5) `main()` takes an injectable `stdin: BinaryIO | None` again (test seam; default `sys.stdin.buffer`). (6) **Evidence (2026-10-14, macOS):** `make host-test` 63 passed, 9 deselected (49 before; 14 new in `test_bootstrap_secrets.py`: verbatim restore then `init` and `restore` refuse, seven bad-bundle cases each refused for its own reason with nothing written, non-empty store, override minting and recording, override refusals, value secrecy across init + restore + override, rollback when the marker write fails, exit 3 on a journal failure after restore, escrow-before-keys and marker-before-commit order for restore). Each check was shown to fail in a scratch copy: the SHA-256 check removed, a missing key accepted, a non-inventory entry accepted, the length check removed, the marker ignored, the marker not written, the override minting a second key, the override allowed for `init`, the override line skipped, the override line carrying the key value, the rollback removed. Not repeated in this PR: the real-age, root-container restore run (done on the unsplit build, recorded in M1d-1).
- **Deviations from plan §3 M1d:** none beyond the M1d-1 split. The plan says restore "checks the manifest" and "mints nothing unless" the override; this adds that restore also writes a fresh escrow bundle and that the override never replaces a version, only appends a newest one.
- **Still OPEN:** the narrow noninteractive elevation that the streamed restore needs (PR 39 review R1): the operator account has password-protected `sudo` (spec H2), but the restore pipeline has no terminal and its stdin is the plaintext bundle, so the runbook command is conditional (`ssh -T ... sudo -n ...`, with a `sudo -n -l bootstrap-secrets` preflight before decrypting) until M1f provisions a `sudoers` rule for that one command (not global passwordless `sudo`, not root login, no password in the stream) and M1k proves it, including that a missing rule refuses with no store change. An override makes data encrypted or signed under the lost version permanently unreadable (accepted by design; the owner decides each use and records it); on hosts (M1k): real `age` with the owner's recipients, the off-host copy of the bundle, and a restore on a fresh VPS; G5, G10, G11 as in M1d-1.
- **Why:** Plan `docs/plans/2026-10-12-m1-vps-infrastructure.md` §3 M1d; spec §8.4 H4, H6; UNI-03, UNI-09, UNI-16.
- **Alternatives rejected:** installing the bundle's versions without re-escrowing (an overridden key would exist on the host with no escrow); writing the marker after the commit point or as part of the log step (a marker failure would then leave a restored host with no record that it was restored, outside the rollback); writing the marker before the keys (a crash between the two would leave a marker on a partial store); an override that replaces the lost version in place (would silently change which key reads existing data); reading the bundle from a file on the host (the plaintext would touch the host's disk).
- **Scope / affects:** `infra/host/skiw_host/bootstrap_secrets.py`, `infra/host/tests/test_bootstrap_secrets.py`, `docs/runbooks/host-rebuild.md`.
- **Versions:** none new.
- **Exception to a rule?** no
