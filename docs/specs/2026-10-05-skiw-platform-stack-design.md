## 1. Goal

SK iWealth advisers (~5 staff accounts, ~146 clients today) use "SKIW Assistant" daily to prepare work against
three external systems that have no public API (TechVision CRM, Phillip FAME, Great Eastern ePartner), plus AI
chat, the Life Goal Planner, returns/IRR, reviews, the Case Guide and PDF form filling. The current build works
but cannot scale past one process, keeps reversible third-party passwords, bypasses database row security, ships
an unsigned extension, and stores Malaysian client personal data (IC numbers, financial holdings) on free-tier
infrastructure outside Malaysia with no audit trail. This spec replaces the stack with one coherent, managed,
in-country platform that: (a) keeps every current feature and the **"the app prepares, a person submits"**
invariant for every write to a third-party system of record (D11), enforced in code and in the database, with a
separate, audited policy for filing into the agency's own Google Shared Drive (D25); (b) scales from 5 to 50 to 500 advisers by changing named components, not
rewriting; (c) treats security and Malaysian PDPA (as amended 2024) as first-class; and (d) is migrated in by a
strangler plan with no big-bang cutover, because the live app is in daily use.

## 2. Non-goals

- No automated submission of anything to FAME, ePartner or a fund house. No FAME write adapter will exist (D11).
- No captcha solving, OCR of captchas, VPNs, rotating/residential IPs, or any technique that evades FAME's
  firewall or any portal's controls (D10, Flow 5.3).
- No building of the Doc2 Marketing suite (Campaigns, Funnels & sites, Automation builder, Media, Reviews
  widgets, WhatsApp inbox) in this spec; buy-vs-build decided in D21, delivery deferred.
- No Kubernetes, no microservices, no multi-region active-active.
- No new business rules: fees, targets (FYP, MDRT, SES, Supremacy), CPD rules and commission logic are read
  from configuration supplied by the owner, never invented here.
- No mobile app. Responsive web only (Doc2 mockup is desktop 1440x900; mobile layouts are a frontend task).
- Not a CRM replacement. TechVision CRM stays the system of record for clients/tasks/insurance until the owner
  decides otherwise (§10 Q4).

Dead-letter = `failed` status + admin retry UI (EVT-05). **Transaction handoff (EVT-01):** the app uses Procrastinate's Django integration (`procrastinate.contrib.django`, connector `DjangoConnector`; queue tables come from Django migrations, D16). `DjangoConnector` runs every query on `django.db.connections[alias]`, the calling thread's Django connection, so a **synchronous** `.defer()` called inside `transaction.atomic()` on the same alias inserts the job in that same transaction; its async path (`.defer_async()`) goes through `sync_to_async` on another thread and is therefore not same-transaction; and it does not support `task.configure(connection=…)` (its external-connection methods raise `ConnectorException`) [V: Procrastinate 3.10.0 source, checked 2026-10-05 / owner decision 2026-10-06]. So all enqueueing goes through one sync helper, `jobs.enqueue_in_tx(task, /, **ids: uuid.UUID)`, which (1) raises if called while an event loop is running in the calling thread, and raises unless `in_atomic_block` is true on the Django connection of the alias it defers on (both checked before any SQL; it is only callable inside `with_agency()`), (1a) **derives the agency itself and accepts none from the caller**: it takes the agency the enclosing `with_agency()` minted for (in-process context) and requires `SELECT guard.current_agency()` on the same connection to return that same non-null value; an `agency_id` keyword or any id argument not declared in the task's typed id schema raises before anything is signed; (1b) checks every referenced id under that tenant: each task declares its id arguments with their tables, and the helper requires each id to be visible by a `SELECT 1 … WHERE id = $1` under RLS in the current transaction (an id of another agency's row is invisible, so the enqueue raises), (2) converts every uuid it sends (the derived `agency_id` and each id) to its canonical string, because Procrastinate's JSON job arguments cannot serialise `uuid.UUID` [V: Procrastinate 3.10.0 source, checked 2026-10-05 / owner decision 2026-10-06], and (3) calls the task's synchronous `.defer(...)` through `DjangoConnector` on that same alias, so the job `INSERT` runs on the caller's connection inside the caller's transaction. Direct `.defer()` / `.defer_async()` / `.batch_defer()` / `.batch_defer_async()` / `.configure(...).defer*()` calls anywhere else are banned by a Semgrep rule in CI. Job args are the derived `agency_id` + ids only (never PII), as strings, plus an `args_mac` added by the helper (§4.1 global tables); the worker verifies it, parses the ids back to `uuid.UUID` (a malformed id fails the job without side effects), then re-enters `with_agency(agency_id)` and re-reads its rows, failing without side effects if any is missing. Async code (the bridge long-poll, D26) never enqueues Procrastinate jobs. The app and the worker connect as `skiw_app` from M0; an M0c migration run as `skiw_migrator` grants `skiw_app` the Procrastinate queue table and sequence permissions its defer and worker paths need (no exception to TEN-02; owner decision 2026-10-06). Verified at M0 by integration tests using the production connector configuration, run as `skiw_app` with migrations applied as `skiw_migrator` (§9 M0): rollback → neither data row nor job exists; commit → both exist; the job is invisible from a separate connection before commit; a real `uuid.UUID` id round-trips; and by the wrong-agency enqueue tests in M4. Still unproven: the same-transaction guarantee if Django's connection pooling (`OPTIONS["pool"]`) is enabled later [A — re-run the M0c transaction tests in the PR that enables it] (the async path is refused by the helper, not relied on), and that `skiw_app`'s grants still cover tables, sequences or functions added by future Procrastinate migrations [A — re-run the M0c tests as `skiw_app` in every Procrastinate upgrade PR]. Budget: append-only `ai_usage_ledger` events per Bedrock call (reserve a conservative upper bound, `dispatch` just before the call, then exactly one terminal settle / release / expire, keyed by `request_id`, §4.1) checked atomically against the per-user and agency monthly caps; refusal at 100 %, warning at 80 %. **What the cap guarantees.** (i) *Admission is hard:* no reservation is admitted that would take the ledger total for the period above either cap, under bugs, crashes and process suspension, because a reservation is reduced early only when no charge is possible: `expire` applies only to a reservation never dispatched (dispatch is refused once it has expired), `release` only to a definite pre-billing rejection, and a dispatched call with no recorded outcome stays counted at its full reservation (`unknown`) until its period ends — there is no provider-log reconciliation and no write-off (Bedrock model invocation logging is **disabled**: its text records carry prompt and response bodies, UNI-09, D17). The price of not knowing is unused budget, never overspend. (ii) *Each call's cost is bounded by its reservation:* the reservation is computed from the maximum billable usage of the exact request (every input-side token category priced at the highest input-side rate, `maxTokens` of output, which also bounds any reasoning output, plus a configured margin) at prices and FX frozen on the reservation (Flow 5.8), so actual ≤ reserved holds unless the bound's stated assumptions are broken (provider token count above the byte-based bound, or AWS prices above the configured ones). (iii) *If that ever fails* the excess is recorded and counted as a separate `overrun` event (never a positive `settle`), AI is paused for the agency until the owner re-prices, and an incident alert fires. The pause is **atomic with admission and dispatch**: the `overrun` transaction holds the agency's AI admission lock exclusively, which every `reserve` (exclusive) and every `dispatch` (shared) also takes, and both re-read the committed pause under it (Flow 5.8); so after the `overrun` commits no reservation is admitted and **no new `dispatch` marker commits** — reservations admitted earlier but not yet dispatched are refused at dispatch and expire unsent — for the paused price version or the current one. The guarantee stops at the `dispatch` commit: the shared lock is released when `dispatch` commits, before the network send, so a call whose `dispatch` committed before the `overrun` may still be sent after it (a process suspended between the two). Its cost is inside the "already dispatched" allowance of (iii) and it is not a breach. Final spend can then exceed the cap by at most the overruns of calls whose `dispatch` committed before that `overrun` committed. So the in-app cap is a hard admission limit and, under the configured prices, a hard spend limit; it is not a provider-enforced limit. It is **not** hard against SQL injected into the app's own agency (which can insert ledger rows, §4.2); an AWS Budgets alert on Bedrock spend for the account is the independent backstop (an alert, not a cap). ## 4. Data model

Conventions: PK `id uuid` (v7, time-ordered); `created_at/updated_at timestamptz`; soft-delete `archived_at` where
records are referenced by history. **Tenant key** (TENANT_KEY) = `agency_id uuid not null`, listed explicitly in every
tenant-owned row below. **Money** = `bigint` minor units + `currency char(3)` (MON-01/02), exponent table
`currency(code, exponent)`. **Rates/returns** = `numeric(12,8)` fractions (never float in storage or JSON; serialised
as strings). **PII class**: C3 = restricted (IC no., DOB, address, income, holdings, policy/health details, IC images);
C2 = confidential (name, phone, email, notes); C1 = internal. C3 text fields that must be searchable are stored as
`ciphertext bytea` (AES-256-GCM, KMS-wrapped DEK per agency, `key_version int`) + `blind_index bytea` (HMAC-SHA-256
with a separate key) + `masked text` (e.g. `******-**-1234`).

**Tenant-consistent references (all tenant-owned tables).** Each tenant-owned table has `unique (agency_id, id)`. Every
column that references another tenant-owned table is a **composite foreign key** `(agency_id, <col>) references
<parent>(agency_id, id)` (shown below as `FK→parent`). Postgres FK checks bypass RLS, so a single-column FK would let an
agency-A row point at an agency-B parent; the composite FK makes that a constraint violation. Nullable references use
the default `MATCH SIMPLE` (a null `<col>` is allowed; a non-null one must match within the same agency). References to
global tables (below) are ordinary FKs. Django 5.2 has no composite foreign keys, so models keep a normal `ForeignKey`
for the ORM (`db_constraint=False`) and the migration adds the `unique (agency_id, id)` and composite FK with
`RunSQL`; a CI schema check (below) proves every such constraint exists.

**Pre-tenant lookups.** Login (email → user) and passkey discovery (credential id → user) must read `app_user` /

superuser with BYPASSRLS; it cannot connect). **Each returns exactly one opaque `bytea` and nothing else**: the row's
`login_blob_ct` / `lookup_blob_ct` for a known key, or, for an unknown key, a decoy of identical length derived
deterministically from the key with `guard.lookup_decoy_key` (so repeated calls cannot tell known from unknown). No

### 4.2 RLS policy and how the tenancy rules are met

Every tenant-owned table gets, in its migration:

```sql
ALTER TABLE t ENABLE ROW LEVEL SECURITY;  ALTER TABLE t FORCE ROW LEVEL SECURITY;
CREATE POLICY t_tenant ON t AS RESTRICTIVE FOR ALL TO skiw_app
  USING      (agency_id = (SELECT guard.current_agency()))
  WITH CHECK (agency_id = (SELECT guard.current_agency()));
-- targeted permissive policies, one per command the app needs (none for UPDATE/DELETE on append-only tables):
CREATE POLICY t_sel ON t FOR SELECT TO skiw_app USING (agency_id = (SELECT guard.current_agency()));
CREATE POLICY t_ins ON t FOR INSERT TO skiw_app WITH CHECK (agency_id = (SELECT guard.current_agency()));
CREATE POLICY t_upd ON t FOR UPDATE TO skiw_app USING (…same…) WITH CHECK (…same…);
CREATE POLICY t_del ON t FOR DELETE TO skiw_app USING (…same…);
```

`guard.current_agency()` returns NULL (deny) for an unset, malformed, forged or other-transaction token. The
`(SELECT …)` wrapper makes Postgres evaluate it once per statement as an InitPlan, so the HMAC runs once per query,
not per row, and `agency_id` indexes stay usable [A — confirm with `EXPLAIN` in the M4 tests]. `agency` (tenant root)
uses the same pattern on `id`, SELECT only.

**Tenant binding (unforgeable by `skiw_app` SQL).** The review showed that any custom setting such as
`app.agency_id` can be set by whatever SQL runs on the app's connection, including injected SQL. So the setting the
policies trust is a token, and only the verifier can turn it into an agency:

1. **Keys.** `tenant_token_key` (32 random bytes, versioned) lives in Secrets Manager; the app holds it in process
   memory, and the `migrate` task writes the same versions into `guard.tenant_mac_key`, which only the NOLOGIN owner
   `skiw_tenant_guard` can read. `approval_mac_key` follows the same pattern (app copy mints, `guard.approval_mac_key`
   verifies, §4.3). `tenant_source_key` and `login_blob_key` (app-only, never in the database) protect the
   tenant *sources* below; `audit_mac_key` (app-only) seals audit events. Rotation: new version added, both accepted until every web/worker task has restarted, old
   one retired; yearly and on suspicion.
2. **Minting (app only).** `with_agency(agency_id)` / `async_with_agency(agency_id)`: `BEGIN`; `SELECT
   pg_current_xact_id()` (assigns and returns the top-level transaction id); compute `token = v ‖ agency_id ‖ xid ‖
   HMAC-SHA-256(key_v, 'skiw-tenant-v1' ‖ current_database ‖ agency_id ‖ xid)` in Python; `SELECT
   set_config('app.tenant_token', token, true)`. One extra round trip per transaction. **No SQL function can mint a
   token.**
3. **Verifying (database).** `guard.current_agency()` — `SECURITY DEFINER`, `STABLE`, owned by `skiw_tenant_guard`,
   `SET search_path = pg_catalog, pg_temp`, all references schema-qualified (`pgcrypto` `hmac()` installed in schema
   `guard`), `REVOKE EXECUTE FROM PUBLIC`, `GRANT EXECUTE TO skiw_app` — parses `current_setting('app.tenant_token',
   true)`, requires the token's xid to equal `pg_current_xact_id_if_assigned()`, recomputes the MAC with key version
   `v` and compares by double-HMAC (comparison time leaks nothing), and returns the agency id or NULL. It returns only
   a uuid; it never returns or logs the key.
4. **Why injected SQL cannot switch tenant.** It can call `set_config('app.tenant_token' | 'app.agency_id', …)` with
   anything, but cannot produce a MAC for agency B without the key (not readable: no grant on the key table, no
   superuser, no file-read roles, no CREATE to plant functions). It can read the current token, but that names agency
   A. A token from any other transaction (a log, another request) fails the xid check. `COMMIT; BEGIN` inside the
   injection gives a new transaction with no valid token → every tenant table denies. Subtransactions/savepoints keep
   the top-level xid, so Django nested `atomic()` still works.
5. **Tenant sources are integrity-protected too.** The agency the helper mints for comes only from: the session (hashed
   key + data HMAC bound to it — §4.1 global tables), `bridge_session.row_mac`, Procrastinate `args_mac`, a
   decrypted login/credential blob (§4.1 pre-tenant lookups), or the deployment's agency list (worker periodic
   fan-out only, D5). SQL that edits or inserts those rows cannot make the app mint a token for agency B, because the
   app rejects any row whose MAC fails. (Without this, injected SQL could rewrite its own session's agency and let the
   app mint a valid token.)
6. **Job args are bound to the enqueuing tenant, not just to the app.** `jobs.enqueue_in_tx` takes no agency from
   its caller: it uses the agency of the enclosing `with_agency()`, confirms `guard.current_agency()` returns the same
   value on that connection, and checks every referenced id is visible under it before computing `args_mac`. So a web
   bug in agency A's request that passes agency B's id (or a B row id) raises at enqueue instead of producing a signed
   B job, and the worker's own `with_agency(B)` is reachable only from a job enqueued inside a verified B transaction.

**What this does and does not contain** (stated once here; T1 cites it). *Contained:* SQL executing as `skiw_app`
inside agency A's transaction — injected or buggy, sync or async path — cannot read, insert, update or delete any
other agency's rows in any tenant table, cannot forge the tenant sources above, cannot obtain password hashes or
account metadata of any agency through the pre-tenant functions, and cannot read the key material. Within agency A
it also cannot move any `external_action` row to `approved` without a genuine artifact the app minted for that exact
row, payload, approver, session and expiry after the person confirmed it (a genuine recent step-up or another
action's artifact does not suffice), cannot get one artifact sent twice, and so cannot get a draft executed (§4.3);
it cannot sign a job (no `args_mac` key) or forge an undetectable audit event (`event_mac`). *Not contained by
the database:* (a) everything inside agency A for the rest of that transaction — all advisers' books (the
intra-agency `scoped()` layer is app code, so injected SQL bypasses it), including: creating, editing (while
`draft`) and cancelling or superseding `external_action` drafts, and cancelling approved ones (denial of service, and
a person may later be shown — and may approve — a draft whose content injected SQL wrote; the confirmation screen
always renders the diff recomputed from the payload, never the stored `diff_json` alone, §4.3); inserting forged

at or before the newest S3 anchor is detected even if the editor recomputes later hashes, because the daily run checks the database's `hash` at every anchored `seq`

**Schema check (M4) — what counts as compliant.** Every table in every schema is exactly one of: (1) a **global
table** in the list in §4.1 (by schema-qualified name); (2) the **tenant root** `agency`, a named exception: `id` PK,
no `agency_id`, RLS enabled + forced, a restrictive policy with USING and WITH CHECK `id = (SELECT

**tenant-owned table**: `id` column, `agency_id uuid not null`, `unique(agency_id, id)`, RLS enabled + forced, the
restrictive policy with USING and WITH CHECK, permissive policies only of the template shape, and a composite FK for
every FK to a tenant-owned table. There is no composite-primary-key exception: key-only tables (`bridge_nonce`,
`setting`) have an `id`. Any policy predicate that reads `current_setting(…)` directly, rather than through
`guard.current_agency()`, fails the check. Fixtures in M4: one compliant table of each kind passes; an undeclared table

### 4.3 `external_action` (outbox): approval evidence, freeze, expiry and recovery

**Columns.** id, agency_id, target (`crm`), op (`create_task`,`update_task`,`upsert_insurance`,`add_asset`,
`cashflow_sync`,`create_client`[future]), status, payload_json, diff_json, base_snapshot_json (the CRM values of the
touched fields when the draft was built), payload_sha256 (set by trigger), prepared_by, prepared_via
(`ui`,`ai`,`import`), prepared_at, source_key (dedupes draft creation from the same source event), supersedes_id,
approved_by, approved_at, approved_payload_sha256, stepup_id, stepup_at, approval_expires_at, approval_id,
claimed_at, claim_token, send_started_at, executed_at, external_ref, verify_report_json, reconcile_report_json, resolved_by,
resolved_at, resolution (`reconciled_match`,`human_linked`,`human_not_applied`,`cancelled`).
FKs: FK→app_user(prepared_by, approved_by, resolved_by), FK→auth_stepup(stepup_id), FK→external_action(supersedes_id),
FK→outbox_approval(approval_id); uq(agency_id, source_key). No DELETE grant.

**Approval artifact (`outbox_approval`, §4.1).** A recent step-up proves only that the session's user re-verified a
factor; it is a prerequisite, never the authorisation. The authorisation is an artifact for one action:
1. **Confirm screen.** `outbox.approval` renders the diff by recomputing it from `payload_json` and
   `base_snapshot_json` (never from the stored `diff_json` alone; a mismatch blocks the draft as "inconsistent") and
   shows it with its `payload_sha256` and `diff_sha256` (SHA-256 of the canonical JSON of the rendered diff).
2. **Confirm request.** The person's "Approve" POST (CSRF-protected, AUTH-01 wrapper, §6 approve permission) carries
   the action id and the two hashes they were shown. The server, in one `with_agency()` transaction: locks the row
   (`FOR UPDATE`), requires status `draft` (or `approval_expired` / `outcome_unknown` for re-approval / Retry),
   recomputes both hashes and requires them to equal the posted ones (a draft changed since the screen was rendered is
   refused and re-shown); requires a step-up with purpose `outbox.approve`, ≤ 5 min old, whose `evidence_mac` verifies,
   whose user is the requester and whose `session_key_hash` equals the current session's; then inserts
   `outbox_approval` (action id, both hashes, approver, session hash, step-up id, `confirmed_at = now()`,
   `expires_at = now() + outbox.approval_ttl_min`) with `approval_mac` = HMAC-SHA-256 under `approval_mac_key`
   (version in `key_version`) over a length-prefixed encoding of `'skiw-approval-v1'`, the database name and every
   other column; and moves the row to `approved` with `approval_id`, `approved_by`, `approved_at = confirmed_at`,
   `approval_expires_at = expires_at`, `stepup_id`, `stepup_at`, `approved_payload_sha256` in the same transaction.
   Only this request path mints artifacts (lint: only `outbox.approval` imports the minting function;
   `outbox.executor` imports only the verifying function; no other module reads `approval_mac_key`).
3. **DB verification (trigger).** On every transition into `approved`, `external_action_guard` reads the artifact
   (under RLS) and rejects unless: `action_id = NEW.id`; `payload_sha256 = NEW.payload_sha256 =
   NEW.approved_payload_sha256`; `approved_by`, `stepup_id`, `confirmed_at = NEW.approved_at`, `expires_at =
   NEW.approval_expires_at` all match; `expires_at > now()`; the artifact's `session_key_hash` equals the step-up's;
   `NEW.approval_id` differs from `OLD.approval_id`; no `outbox_send` row references it; and
   `guard.approval_mac_ok(<artifact columns>, approval_mac)` returns true. `guard.approval_mac_ok` is `SECURITY
   DEFINER`, owned by `skiw_tenant_guard`, hardened like `guard.current_agency()` (§4.2 item 3), reads
   `guard.approval_mac_key`, requires the artifact's `agency_id = guard.current_agency()`, compares by double-HMAC and
   returns only a boolean (a verification oracle does not help forge an HMAC).
4. **Executor verification and single use.** Before it claims and again before the POST, `outbox.executor`
   recomputes `approval_mac` with its own key copy and re-checks every binding above against the row. In the
   transaction that commits `send_started_at` it inserts `outbox_send(approval_id, action_id, claim_token)`;
   `uq(agency_id, approval_id)` makes that insert fail for a second send on the same artifact, and the trigger rejects
   setting `send_started_at` unless an `outbox_send` row for `NEW.approval_id` and `NEW.claim_token` exists in the
   same transaction. A claim that returns to `approved` before sending (`send_started_at` null) leaves the artifact
   unused; any path after a send (`outcome_unknown` → Retry) needs a new artifact.
5. **Batch approvals.** A person may approve several actions within one step-up's 5-minute window; each action still
   needs its own confirm request and artifact (Q30 asks whether the owner wants a step-up per action instead).

**States and who may move them.** Module restrictions are code-level (import-linter: only `outbox.approval` writes
approval transitions, only `outbox.executor`/`outbox.reconciler` write execution transitions); permission checks are
in the action wrapper per §6 (AUTH-01/03); the DB trigger enforces legality and evidence for every caller.

| From → to | Actor | Conditions (DB-enforced unless marked app) |
|---|---|---|
| (new) → `draft` | user (UI), import job, AI tool (`prepared_via='ai'`) | — |
| `draft` → `approved` | a human user with approve permission for the client (app, §6) in the confirm request, after step-up | approval evidence complete (CHECK below) and a valid, unused approval artifact for this row and payload (trigger, "Approval artifact" item 3) |
| `draft` → `cancelled` / `superseded` | preparer or an approver | — |
| `approved` → `executing` | executor | `now() <= approval_expires_at`; sets claimed_at, claim_token |
| `approved` → `approval_expired` | executor or sweeper job | `now() > approval_expires_at` |
| `approval_expired` → `approved` | human re-approval with a **new** step-up | new evidence and a new artifact; payload unchanged; app re-reads CRM first and, if any touched field differs from base_snapshot, supersedes instead (new draft, new diff, new approval) |
| `approved` / `approval_expired` → `cancelled` | approver or owner | — |
| `executing` → `approved` | executor | only if `send_started_at is null` (nothing was sent, e.g. CRM session expired before the POST) |
| `executing` → `succeeded` / `verify_failed` | executor | `executed_at`, `verify_report_json` not null |
| `executing` → `failed` | executor | CRM returned a definite rejection (form error page) and a read-back shows the touched fields still equal base_snapshot |
| `executing` → `outcome_unknown` | executor (timeout, connection reset, 5xx, redirect-to-login on the POST) or recovery sweeper (stale claim with `send_started_at` set) | — |
| `outcome_unknown` → `succeeded` | reconciler (unique verified match) or a human linking a CRM record that passes read-back | resolution + resolved_by/at recorded |
| `outcome_unknown` → `approved` | human "Retry" after the reconciler reported "not applied", with a **new** step-up | new approval evidence and a new artifact (the old one has an `outbox_send` row) |
| `outcome_unknown` → `cancelled` | human ("handled in CRM manually") | resolution recorded |

**DB invariants.**
- CHECK: `status in ('approved','executing','outcome_unknown','succeeded','verify_failed','failed')` ⇒
  `approved_by, approved_at, stepup_id, stepup_at, approved_payload_sha256, approval_expires_at, approval_id` all not null **and**
  `approved_payload_sha256 = payload_sha256` **and** `stepup_at <= approved_at` **and**
  `approved_at - stepup_at <= interval '5 minutes'` **and** `approval_expires_at > approved_at` **and**
  `approval_expires_at <= approved_at + interval '24 hours'` (hard ceiling; the configured TTL may only be shorter).
- CHECK: `status in ('executing','outcome_unknown','succeeded','verify_failed','failed')` ⇒ `claimed_at` not null;
  `status in ('succeeded','verify_failed')` ⇒ `executed_at` and `verify_report_json` not null.
- Trigger `external_action_guard` (BEFORE INSERT/UPDATE): computes `payload_sha256 = sha256(payload_json::text)`
  (jsonb text output is canonical); rejects any change to payload_json, diff_json, base_snapshot_json, op, target,
  agency_id or prepared_* unless OLD.status = `draft`; rejects transitions not in the table above; allows approval
  columns to be written only on a transition into `approved`; on `approved → executing` rejects if
  `now() > approval_expires_at`; checks that `stepup_id` belongs to `approved_by` (same agency via composite FK, same
  user, `purpose='outbox.approve'`) and `stepup_at = auth_stepup.verified_at`; on a transition into `approved`
  verifies the approval artifact ("Approval artifact" item 3); on setting `send_started_at` requires the matching
  `outbox_send` row (item 4).
- What this proves, and its limit: the DB proves consistency and freshness of the recorded evidence **and** that an
  app-minted artifact exists for this exact row, payload hash and approver — it verifies `approval_mac` itself through
  `guard.approval_mac_ok`, so SQL running as `skiw_app` (injected or buggy) cannot move any row to `approved`, cannot
  reuse a genuine artifact or a genuine recent step-up for another action, and cannot get one artifact sent twice. The
  executor re-verifies the MAC and bindings before claiming and before the POST. `auth_stepup.evidence_mac` is still
  verified by `outbox.approval` (step-up authenticity). What remains outside this control is stated in §4.2 "What
  this does and does not contain" (draft tampering before a person views it; DoS by cancelling) and code execution in
  the app process, which holds `approval_mac_key` (T16/T17). An AI-prepared draft can never be approved by the AI:
  there is no AI principal in `app_user`, and the AI tool layer cannot call the confirm endpoint.

**Approval expiry.** `outbox.approval_ttl_min` (§8.1) sets the artifact's `expires_at` and so `approval_expires_at = approved_at + TTL` at approval. A job
that waits (CRM reconnect, pacing, outage) past expiry is moved to `approval_expired` and needs re-approval with a
fresh step-up as above.

**Crash-safe execution (no blind retry).** CRM-side idempotency keys are not known to exist (Q27), so a local key
cannot guarantee one POST. The executor therefore: (1) verifies the approval artifact (MAC and bindings), claims the
row (`approved → executing`) and commits; (2) takes the per-user CRM lock, reopens the CRM form (GET), and if the
session has expired returns the row to `approved` (nothing sent); (3) re-verifies the artifact and commits
`send_started_at = now()` together with the `outbox_send` row **before** the POST; (4) POSTs once; (5) on a definite response
reads back and sets `succeeded` / `verify_failed` / `failed`; on any ambiguous outcome sets `outcome_unknown`. A
recovery sweeper turns `executing` rows whose claim is older than `outbox.claim_timeout_s` into `approved` if
`send_started_at is null`, else `outcome_unknown`. Nothing ever re-POSTs automatically from `outcome_unknown`.

**Reconciler** (`outcome_unknown`, runs when a CRM session is available; result in `reconcile_report_json`):

| Op kind | Reconcile by | Unique match with all approved values | Values still equal base_snapshot / no candidate | Anything else |
|---|---|---|---|---|
| Update of an existing record (`update_task`, `upsert_insurance` on an existing policy, `cashflow_sync`) | Read the record by its CRM ref | `succeeded` (`reconciled_match`) | report "not applied"; human may Retry (new step-up) or cancel | human resolves |
| Create (`create_task`, `add_asset`, `upsert_insurance` create path, `create_client`) | Search the client's records created since `claimed_at` minus clock skew for the op's fingerprint (task: title + due date; asset: type + amount; policy: insurer + policy no.) and, if the owner approves Q27, a short `SKIW-<8 chars>` reference written in a free-text field | `succeeded`, `external_ref` linked | report "not found"; human may Retry or cancel | more than one candidate → human picks one (`human_linked`) or cancels |

`verify_failed` is never retried automatically either; the adviser and owner are alerted and a person resolves it.

## 5. Flows

**5.1 Login + 2FA.** (0) Before a tenant is known, the user is found only through `guard.auth_lookup_login` / `guard.auth_lookup_credential`, which return one opaque blob (§4.1 pre-tenant lookups); the app decrypts it in process; everything after that runs in `with_agency()` with the agency from the blob and then from the MAC-verified session. Every successful step-up writes an `auth_stepup` row with `evidence_mac` (evidence for §4.3 and D25). (1) Email + password → blob decrypt + Argon2id verify in process (a decoy blob takes the same path with a dummy verify); account `status` read under RLS only after a successful verify; uniform error and timing (AUTH-05); rate limit 5 fails / 15 min / account and 20 / 15 min / IP, stored in Postgres (AUTH-06). (2) Second factor required: passkey (WebAuthn, user verification required) or TOTP (±1 step) or recovery code (single use). (3) New session id, `__Host-` cookie, CSRF token rotated; `audit_event(login.success)`. (4) First login after migration forces passkey enrolment; owner/admin cannot finish without one. Failures: 10 consecutive fails → account soft-lock 30 min + owner alert; lost factors → owner-performed reset with step-up, audited, all sessions revoked.

**5.2 Connector connect — CRM (captcha, no stored password).** (1) Adviser opens Connections → "Connect CRM". (2) Worker-free sync call: server creates a fresh HTTP session to the CRM (via NAT fixed EIP), GETs the login page, fetches the captcha image, stores the half-open cookie jar encrypted in `connector_session(status=needs_login)` with 5-min expiry, returns the captcha as a no-store image. (3) Adviser types username, password and the captcha (a human always types it; we never OCR it). (4) Server posts login; on success stores only the cookie jar (encrypted), status `connected`, `expires_at` = observed/assumed lifetime [O] Q7; password object discarded, never logged (scrubber + test). (5) Health check job every 15 min (configurable) does one cheap authenticated GET while within working hours; on 302-to-login → `expired`, UI light turns amber and Today shows "Reconnect CRM". Failures: wrong captcha → new captcha; 3 failed logins in 15 min → stop, tell the user (avoid CRM lockout); CRM unreachable → `error` with backoff 1/5/15 min.

**5.3 Connector connect — FAME and ePartner (bridge).** (1) Adviser installs the store-distributed extension (force-installed if Workspace). (2) Pairing: Account → Browser Bridge → "Pair this browser" (step-up) → app page passes a one-time 128-bit pairing code (valid 2 min) to the extension via `externally_connectable` messaging restricted to the app origin → extension generates non-extractable P-256 key, sends public key + code → server stores `bridge_device`. (3) Adviser logs into FAME (with their OTP) / ePartner (GE's own RSA password flow) **in their own tab**; the extension detects a usable session but never transmits tokens/cookies to our server. (4) Status lights: FAME/ePartner "ready" when the extension reports a live tab session (boolean only). ePartner idle 10 min → extension re-primes with a single allow-listed GET while the adviser is present; if expired, it asks the adviser to log in again (no credential replay). FAME 403 from adviser's own network is shown as an error, never retried through another route.

**5.4 Bridge job lifecycle.** (1) A feature (e.g. "Refresh holdings") inserts `bridge_job(job_type, params)` in the same transaction as the request (EVT-01), and in that transaction calls `pg_notify('bridge_wakeup', <user uuid>)` (delivered only on commit); params validated against the job type's schema (e.g. FAME account id regex). (2) The device's long-poll (D26) is woken by its web process's shared listener (≤ 25 s; otherwise returns 204 and the extension re-polls; MV3 service worker kept alive by the open fetch + `chrome.alarms` 30 s). No transaction or pooled connection is held while waiting; authorization, nonce and lease each run in a short `async_with_agency()` transaction with the tenant taken from the MAC-verified `bridge_session`; the waiter is registered before every queue check (D26 (3)), so a job committed during the poll is never missed. (3) Lease: `UPDATE … SET status='leased', lease_device_id, lease_until=now()+90s WHERE status='queued' AND user_id=$me … FOR UPDATE SKIP LOCKED` — one job at a time per user, `not_before` enforces 5–10 s pacing and an hourly cap (config). (4) Extension maps job type → URL template from its **own built-in** allow-list (GET only), runs it in the adviser's tab context, posts `{job_id, status, raw|json}` signed. (5) Server verifies signature, device not revoked, job leased to that device, lease unexpired, size ≤ 2 MB, content type; stores raw encrypted (TTL 7 days), parses in the worker with a hardened parser (no network, no entity expansion, time limit 5 s, memory cap), validates each field (types, regex, money → minor units), writes `parsed_json`. (6) Retry: lease expiry → back to `queued`, attempts+1, backoff 30 s / 2 min / 10 min, max 3 → `failed` (dead-letter, admin "retry" button, EVT-05). Results for unknown/expired/other-device jobs → 409 + audit `bridge.result.rejected`. Device silent > 2 min with queued jobs → UI "Open Chrome with the bridge" banner.

**5.5 ePartner import → confirm → CRM write → read-back verify.** (1) Adviser clicks "Import from ePartner" for a client → bridge jobs `epartner.policy_list` then `epartner.policy_detail` × n (paced). (2) Parser (port of `epartner.py`, same tests) → ~26 fields per policy → upsert local `policy` rows (source=`epartner`). (3) Diff against CRM insurance/assets (read via CRM connector) → system builds `external_action` drafts (`upsert_insurance`, `add_asset`, optional `create_task`) with option values resolved through `crm_option_map` (unknown display text → draft blocked, "needs mapping"). (4) Adviser reviews a side-by-side diff (recomputed from the payload, with its payload and diff hashes) and, after a step-up no older than 5 min from the same session (an `auth_stepup` row), clicks Approve; the confirm request re-checks both hashes and mints the action-bound `outbox_approval` artifact, and the trigger verifies it while moving the row to `approved` with `approved_payload_sha256`, `approval_id` and `approval_expires_at` (§4.3 "Approval artifact"); the payload is frozen from here. (5) Executor job verifies the artifact, claims the row, takes the per-user CRM lock, reopens the CRM edit form, merges only the approved fields into the full form, re-verifies the artifact and commits `send_started_at` with the single-use `outbox_send` row, posts once, then **re-reads the record** and compares every approved field. Match → `succeeded`; mismatch → `verify_failed`, alert the adviser and owner, no automatic retry (avoid double-corruption). CRM session found expired when reopening the form (before any POST) → row returns to `approved` with a "Reconnect CRM" prompt; if reconnect happens after `approval_expires_at`, the row becomes `approval_expired` and needs re-approval with a fresh step-up. Timeout, connection loss, 5xx or a redirect-to-login on the POST itself, or a worker crash after `send_started_at` → `outcome_unknown`: the reconciler reads back per §4.3; nothing is re-posted unless a person chooses Retry after the reconciler reports "not applied". The local `source_key` only dedupes draft creation; it is not a guarantee of a single POST.

**5.6 Closed-won → client creation + Drive folder + IC OCR.** (1) Card moved to Closed-won by a person (with a step-up while `drive.write_policy=stepup_required`, D25) → **one transaction** in `with_agency()`: lock the `lead` row (`SELECT … FOR UPDATE`); if a `client` with `source_lead_id` = this lead already exists, reuse it, otherwise insert it (name/phone from the lead, `display_code` from the configured pattern — Q28; `uq(agency_id, source_lead_id)` makes a concurrent second move a no-op); insert `pipeline_stage_event`; insert `drive_operation(create_folder)` with that `client_id` (not null), `triggered_by` = the person, `policy_at_trigger` and `stepup_id` (`uq(agency_id, client_id) where op='create_folder'` makes it one per client; an existing row is reused); enqueue its Drive job and a domain job with `jobs.enqueue_in_tx`. Nothing reaches Drive before this commits, and on rollback none of the rows or jobs exist. (2) The domain job creates an `external_action(op=create_client)` **draft** for the existing client — blocked until a CRM create-client capability exists (Doc1: none yet) [O] Q5; meanwhile UI shows "create in CRM manually, then link" with a CRM-ref field. (3) Optional IC scan: adviser uploads front/back image → S3 quarantine → ClamAV + magic bytes + re-encode → OCR (in-region option preferred; cross-border model only with TIA/consent, Q12) → extracted IC no./name/DOB/address shown for **human confirmation**; never auto-saved. On confirmation, a `drive_operation(upload_file)` row (D25, `triggered_by` = the confirming person) files the IC image to the Drive CCF folder — written as `waiting` with `depends_on_id` = the client's `create_folder` row if that folder is not yet `verified`; S3 copy deleted ≤ 24 h after the upload is verified. (4) The `create_folder` job (service account via WIF): first generates the file id and commits it to the row, then creates `<Shared Drive>/Clients/<client display code>/CCF` (no IC no. in folder names), reads it back, and in one local transaction marks the row `verified`, stores `drive_folder_id` on the client and moves its `waiting` dependents to `queued` (enqueuing their jobs). Failures: Drive 5xx → retry 3× with backoff (safe: same pre-generated id, D25); permission error or read-back mismatch → `failed`/`verify_failed`, dead-letter + owner alert; dependents stay `waiting` and the client page shows "Drive folder not created — Retry" (D25 retry rules).

**5.7 Scan inbox filing.** (1) Worker polls the Drive "Scans inbox" folder via the Drive changes API every 2 min (config). (2) New file → download to S3 quarantine → AV scan, type check, page render. (3) Classifier proposes client + form type (barcode/QR on our generated forms first; text match second; LLM last, pseudonymised, and only if gate G-AI allows it — D12) with confidence. (4) ≥ threshold and form generated by us (embedded instance id) → propose filing; otherwise `needs_human`. (5) A person clicks "Confirm filing" (choosing the client and, optionally, the case step it evidences; step-up while `drive.write_policy=stepup_required`, D25) → in that transaction: `scan_inbox_item.confirmed_by`, `case_step_id`, status `filing`, and a `drive_operation(move_file)` row (D25; `waiting` on the client's `create_folder` row if the folder is not yet verified). **The case step stays `open`**; the case view shows it as "Filing in progress". (6) The job moves the file into the client's CCF folder (`addParents`/`removeParents`, safe to re-apply) and reads its parents back. On `verified`, **one local transaction**: the row → `verified`; a `document` row (kind `scan`, storage `drive`, the Drive file id) is inserted; if a case step was chosen and is still `open`, it becomes `done` with `done_by` = the confirming person, `done_at` and `evidence_doc_id` = that document (a step already `done` is left unchanged, so completion happens once); the scan item → `filed`; audit. (7) Failure: Drive 5xx → 3 retries with backoff; permission error, missing folder or read-back mismatch → row `failed` / `verify_failed` with `last_error_class`, scan item → `filing_failed`, case step unchanged (`open`), adviser and owner alerted. The Scans inbox shows the item under "Filing failed" with the reason and two actions for a person with §6 edit permission on that client: **Retry filing** (re-queues the same row, attempts+1, same step-up policy, audited; safe because the move is absolute) and **Cancel filing** (row → `cancelled`, item → `needs_human`, step stays `open`). The case view shows the step as "Filing failed — open in Scans inbox". Never auto-moves a file or auto-ticks a step without confirmation in v1.

**5.8 AI chat with tools.** (0) Gate G-AI (D12): with no recorded owner decision, or a configured inference profile outside `ai.allowed_inference_profiles`, the adapter refuses the call and the UI shows "AI chat unavailable"; in "no client data" mode, steps (2) and the client-reading tools below are disabled. (1) User message → for **each** Bedrock call in the turn (≤ 1 + 6 tool rounds), `ai.cost.reserve()` in one short `with_agency()` transaction: take the **agency AI admission lock** — `pg_advisory_xact_lock` on (agency, `ai.admission`), one key per agency for all periods, so a month boundary cannot split admission from a pause — then `pg_advisory_xact_lock` on (agency, user, period) (fixed order, no deadlock); read the current `ai.pricing` version from the `setting` row in this transaction; if the agency is **paused for** that version (an `overrun` event of the agency, in any period, whose `price_setting_version` equals it — read under the lock, so it sees every committed overrun), refuse ("AI paused — pricing under review"); compute the **reservation bound** for this exact request: `bound_tokens_in` = UTF-8 byte length of everything sent as input (system prompt, messages, tool definitions and tool results, after pseudonymisation) + `ai.pricing.input_overhead_tokens` (provider-added message framing and tool-use system prompt), on the stated assumption that no billed input token covers less than one byte of the request [A — verify at M11: provider-reported input tokens ≤ this bound on the fixtures and on a sample of real calls]; `max_tokens_out` = `ai.max_output_tokens`, sent as the request's `inferenceConfig.maxTokens`, so the provider cannot return or bill more output; extended thinking and prompt caching are **not enabled** in v1 (no `thinking` field, no `cachePoint` blocks) — if either is enabled later, thinking tokens are output tokens inside `maxTokens` and cache-write/cache-read tokens are input-side tokens, both already covered because every input-side token is priced at the highest input-side rate; reserved = `ai.cost.to_minor`((`bound_tokens_in` × max(input, cache-write, cache-read price) + `max_tokens_out` × output price) × FX × (1 + `ai.pricing.reserve_margin_pct` / 100)), using the current `ai.pricing` version and the current dated `fx_rate`, both **frozen on the reservation** (`price_setting_version`, `fx_rate_id`), rounded **up** to the minor unit (the one rounding rule, `ai.cost.to_minor`, MON-04); chat never sends images (other LLM uses, Flow 5.6/5.7, bound image input by AWS's documented per-image token formula at the enforced maximum image size [A — verify at M11/M16]); sum `amount_minor` for the user and for the agency in the period (this sees open, dispatched and unknown reservations at their full reservation and overruns at their excess); if either sum + reserved exceeds its cap, refuse ("AI budget reached"); else insert the `reserve` event with a fresh `request_id` and `reservation_expires_at = now() + ai.reservation_ttl_s`, and commit. (1a) **Dispatch:** immediately before sending the request, a second short transaction takes the agency AI admission lock in **shared** mode (`pg_advisory_xact_lock_shared` on (agency, `ai.admission`); dispatches do not block each other, but they serialise against every reserve and every `overrun`), then `pg_advisory_xact_lock` on (agency, reserve id) (same order as everywhere else: admission lock first), and refuses (no call is made, no event is written; the turn ends with "AI budget reached — please retry", or "AI paused — pricing under review" for a pause) if any terminal event exists for the reservation, `now() > reservation_expires_at`, or the agency is paused for the reservation's frozen `price_setting_version` **or** for the current `ai.pricing` version (the pause is re-read here, under both locks, from committed rows); else inserts `dispatch` and commits; only then is the Bedrock request sent, exactly as it was bounded in (1) (a request that changes after reserve needs a new reservation). Because the `overrun` transaction (step 5) holds the admission lock exclusively, each dispatch is ordered entirely before an overrun (its call counts among the "already dispatched" of D12 (iii)) or entirely after it (it sees the pause, commits no `dispatch` marker and sends nothing). The exclusion does not extend through the network send: a call whose `dispatch` committed before the `overrun` may still reach Bedrock after the `overrun` commits; it counts among the "already dispatched" calls and its reservation, frozen prices and bound are unchanged. A reservation refused at dispatch is never sent; it stays counted until the sweeper `expire`s it at `reservation_expires_at` (no `dispatch` exists, and dispatch stays refused after expiry), so its ledger ends `reserve` + `expire` = 0. (2) Context builder pulls only fields the tool/question needs; pseudonymiser replaces IC/phone/email/account/policy numbers. (3) System prompt marks all tool output and document text as untrusted data. (4) Model may call allow-listed tools: `search_clients`, `get_client_summary`, `get_holdings`, `compute_irr`, `planner_project`, `list_tasks`, `draft_crm_task` (creates **draft** `external_action` only). No tool accepts a URL or raw SQL; arguments schema-validated; max 6 tool calls per turn. (5) After each call, compute actual = `ai.cost.to_minor`(Σ over every billed category in the response `usage` — input, output, cache-read, cache-write, and any category the adapter does not recognise, which is priced at the highest configured rate and also raises an alert — × the reservation's **frozen** prices and FX), with no margin, and store the counts in `usage_json`. If actual ≤ reserved, insert `settle` = actual − reserved (≤ 0). If actual > reserved (an assumption of the bound failed), one transaction first takes the agency AI admission lock **exclusively** (`pg_advisory_xact_lock` on (agency, `ai.admission`), the same lock as reserve; then the reservation's lock), then inserts `settle` = 0 and `overrun` = actual − reserved and commits — the `overrun` row *is* the pause, so the pause and the admission decision are one serial order: the excess is counted in the spend sums, reserve and dispatch refuse for the whole agency for that price version until the owner saves a new `ai.pricing` version (owner step-up action, audited, D23), reservations frozen on the paused version stay refused at dispatch even after re-pricing, and an incident alert fires with the reservation id and token counts (no text). A positive `settle` is never written (the trigger rejects it). A price or FX change between reserve and settle cannot produce a positive delta, because settle uses the prices and `fx_rate_id` frozen on the reservation; the change applies only to reservations made after it. (6) Response re-hydrates pseudonyms client-side only for display. Failure: a **definite pre-billing rejection** (Bedrock `ThrottlingException`, `ValidationException`, `AccessDeniedException`, listed in the `release_reason` allow-list [A — confirm at M11 that AWS does not bill these]) → for throttling, 1 retry under the same reservation (a new `dispatch` is not needed: the reservation is still dispatched and counted; the retry first repeats the step (1a) checks under the same locks, without inserting a second `dispatch`, and is not sent if they refuse), then friendly error and a `release` event (−reserved). **Any ambiguous outcome** (client timeout, connection reset, 5xx, process crash or suspension after `dispatch`) is never released: the reservation stays counted. A worker-scheduled sweeper (every minute, fanned out per agency, D5), for each `reserve` past `reservation_expires_at` with no terminal event, takes the same per-reservation advisory lock and: if no `dispatch` exists, inserts `expire` (−reserved) — safe because the dispatch step refuses after expiry, so the call can never be sent later; if a `dispatch` exists, inserts `unknown` (0, once) and leaves the full reservation counted. **There is no reconciler:** Bedrock model invocation logging is disabled (D17, UNI-09), no provider record is consulted, and a missing response is never treated as proof of no charge. An `unknown` reservation stays counted at its full reservation until its period ends (the budget is under-used, never exceeded; Q29); like every reservation it does not carry into the next period. There is no owner write-off. A late `settle` (or `settle` + `overrun`) from a resumed process after `unknown` is accepted (terminal), computed from the response that process actually received. The partial unique indexes make the terminal events mutually exclusive, so a second sweeper or a duplicate settle gets a conflict and does nothing. Nothing is ever updated or deleted (TEN-03).
