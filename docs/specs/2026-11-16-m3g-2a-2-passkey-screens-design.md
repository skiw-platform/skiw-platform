# M3g-2a-2 — passkey list, add, remove and the optional step after enrolment — design

- Date: 2026-11-16 · Author: Builder · Status: draft (revised after spec review Round 3)

- Supersedes: none. A slice spec under `docs/specs/2026-10-05-skiw-platform-stack-design.md` (v1.22); it changes no rule there. Plan row: `docs/plans/2026-10-31-m3-auth.md` §1 M3g (amended 2026-11-15, "Split in two"; this spec re-splits M3g-2a-2 in four, decision 11).

## 1. Goal
A signed-in staff member can see their passkeys, add one and remove one in the browser, and a new
user finishing first-time enrolment is offered a passkey once. The server side already exists
(M3g-1c, PRs 156/160); this is the browser half, plus the keyboard-focus fix the PR 161 Round 9
reviewer made a condition of M3g-2a-2 (P2 #1). Passkeys stay optional: an authenticator (TOTP)
always remains and nothing here is required to sign in or to finish enrolment.

## 2. Non-goals
- No server route, table, setting or dependency change. If one proves necessary the work stops and asks (server changes get their own PR).
- No authenticator (TOTP) or recovery-code screens (later M3 screens; the page leaves room).
- No passkey names or labels (owner, 2026-11-14): entries are told apart by added date and time.
- No real-browser or virtual-authenticator tests: M3g-2b. Vitest only here (DECISIONS "M3g-2a-1" [A]).
- No usernameless sign-in (parent spec Flow 5.1).

|---|---|---|---|
| 1 | **Security page, second nav item** (owner 2026-11-16). | One home for factor screens. | A card on Today. |
| 2 | **URL contract (owner 2026-11-16: hash).** Today is `/` (no hash); Security is `/#security`. Both nav items are real anchors (`href="/"`, `href="/#security"`) and `aria-current="page"` marks only the active one. The view derives from `location.hash` and follows `hashchange`, so click, Cmd/Ctrl-click, direct open, reload and Back/Forward all work with no server change. Only the exact hash `#security` selects Security; any other hash reads as Today and is not rewritten. A signed-out visitor to `/#security` sees sign-in; after a sign-in the hash is honoured (they land on Security). Sign-out and "Use a different account" clear the hash with `history.replaceState`, so the next person starts on Today. Enrolment keeps its own `/enrol#<token>` (the existing token removal runs first and is untouched). | FE-05 hard: links navigate. `shell` serves only `/` and `/enrol` (`app/config/urls.py:138-139`). | URL-less view (rejected by review); `/security` shell route (a server PR first). |
| 3 | **List.** `GET /api/auth/factors` (`passkey: [{id, created_at}]`, oldest first, `created_at` ISO UTC or null). Row text, one formatter in `web/src/passkey.ts`: `new Intl.DateTimeFormat("en-GB", {timeZone: "Asia/Kuala_Lumpur", day: "numeric", month: "short", year: "numeric", hour: "2-digit", minute: "2-digit", hour12: false})` → "Passkey, added 16 Nov 2026, 14:05" (owner 2026-11-16: date and time, Malaysia time; the timezone is the parent spec §4.1 constant, held once in `content.ts`). `null` → "Passkey, added time unknown". If two rows render the same text (same minute, or several nulls) a suffix " (n)" numbers them in the server's order (created_at, then id), so every row's text is unique. The row's accessible name and the removal confirmation use the identical text. **One list parser** (`parseFactors(reply)`, used by the first load and every reconciliation read): a valid answer is status 200 with a `passkey` array whose every entry has `id` a string matching the UUID form the server's remove route accepts (`uuid.UUID`, `app/accounts/views.py:431`), unique within the answer, and `created_at` either `null` or a string for which `Date.parse` is finite; unknown keys (top level or per entry) are ignored. Any other readable 200 body is the ordinary list-load error: no rows, no Add or Remove control built from that answer, no request, no logging, and the formatter is never called on an unparsed value. | Same-day additions must be distinguishable (review P2). | Date only; browser-local time (owner declined). |
| 4 | **Add, try-first step-up.** "Add a passkey" calls begin (`POST /api/auth/factors/passkey`). `403 stepup-required` → the `StepUp` dialog (`factor.change`, D7/AUTH-09), then begin once more; a second `stepup-required` after a verified dialog is a generic error (no loop). Begin 200 with `options` → creation ceremony (decision 5) → confirm. | Server enforces; avoids a second code right after enrolment (PR 159). | Always prompting first. |
| 5 | **Registration wire format (manual conversion, no `toJSON`/`parseCreationOptionsFromJSON`: Chromium-only, as DECISIONS "M3g-2a-1" decided for assertion).** Options from py_webauthn JSON (`generate_registration_options`, attestation `none`, resident key preferred, user verification required): convert to bytes exactly `challenge`, `user.id` and every `excludeCredentials[].id` (base64url, padding optional); pass `rp`, `user.name`, `user.displayName`, `pubKeyCredParams`, `timeout`, `authenticatorSelection`, `attestation` and each exclude entry's `type`/`transports` through unchanged. Any of those three binary fields missing or not a string → `failed` (nothing is prompted). Credential back: `navigator.credentials.create({publicKey, signal})` must return a `PublicKeyCredential` whose `response` has `attestationObject`; the body is exactly `{credential}` where credential = `id` (text), `rawId`, `type`, `response.clientDataJSON`, `response.attestationObject` and `response.transports` (from `getTransports()` when that method exists, else omitted), `authenticatorAttachment` (omitted when null) and `clientExtensionResults`, all binary values unpadded base64url. These are the fields py_webauthn's `parse_registration_credential_json` reads (server fixture `app/accounts/tests/authenticator.py:80-88`); no assertion field (`authenticatorData`, `signature`, `userHandle`) is sent. `NotSupportedError` → `unsupported`; any other error, a cancel, a timeout → `failed`. | The review's P1: the boundary must be exact. | Sharing the assertion encoder unchanged. |
| 6 | **One operation lifecycle for add and remove** (a small module-level runner in `web/src/passkey.ts`, outside any component). (a) *Before* the mutation is sent, leaving the page (navigation, hashchange, unmount, sign-out, Cancel, Escape) aborts begin and the prompt and sends nothing. (b) *Once confirm / remove is sent* it carries no signal and always runs to completion, even if its screen has gone: it consumes the answer (`api.post` keeps a usable `csrf`), and when the answer is lost, truncated, 5xx, malformed or token-less it performs `readSession()` itself; only a result that gives a listed state **and** a non-empty token counts. Until that, **no further protected POST is sent** (the next action first re-reads the session). (c) A departed screen is never updated; the shared token is. (d) **Single flight, by owner of the controls.** Outside the step-up dialog, while one factor operation is active (ceremony, sent mutation, reconciliation) every Add, Remove and inline-confirm control is disabled and a repeated activation is ignored, so a second begin cannot replace the first challenge; **only one inline removal confirmation may be open** (opening another closes the first and returns its focus). While `StepUp` is open the outer page (header, nav, Sign out, Security content) is `inert` and unavailable to assistive technology, focus is contained in the dialog (Tab and Shift-Tab wrap among its code field, Confirm, passkey and Cancel), and those four controls use `StepUp`'s own busy state, not the single-flight lock; Cancel and Escape close it and return focus to the Add or Remove control that opened it. (e) **Sign out is behind the same gate.** From the moment confirm/remove is sent until reconciliation ends, Sign out is disabled (status: "Finishing your change…"). Navigation may leave the screen but never bypasses the gate: `api.logout()` itself refuses to send while a sent mutation is unreconciled. If reconciliation ends unresolved (no listed state with a non-empty token) Sign out is enabled again, and activating it first tries `readSession()`; if that still fails no logout is sent and the status says "We could not confirm your session. Reload the page." (the reload re-reads the server state). (f) **Ambiguous results never claim more than the client knows, and never retry.** *Add:* success is claimed only from an exact success answer (status 200, `next: "added"`, a usable `csrf`, and `factor_id` a UUID, which the page keeps as this attempt's identity); the server's list is then read and shown. A lost, truncated, 5xx or malformed answer is **not** resolved by any newly seen id in the list (another session or a stale list can add one, so a list difference is not proof): the page reads the list again, shows it, and says "We could not confirm the new passkey. Check the list below." It does not say "added" or "not added", sends no second begin or confirm by itself, and the enrolment offer does not advance (it stays with that message, Add re-enabled and Skip available). The offer needs no list baseline: it reads nothing before begin and never infers success from the list. *Remove:* the selected id is the identity: absent from a **successfully parsed** list → "Passkey removed"; present → "The passkey was not removed. Try again." *Reconciliation-list failure* (unreadable, non-200, or failing the parser) is unresolved, never proof of anything: status "We could not load your passkeys. Reload the page.", no list shown from it, no success or failure claimed. Other list changes are shown as the list shows them and not described. The success answers pass `api.rotated(answer, "added" \| "removed", "signed_in")`. | AUTH-13, UNI-03; the stale-token class PR 161 closed. | Per-component state that unmount discards. |
| 7 | **Remove.** Row "Remove" → visible label "Remove", accessible name "Remove " + the row text (`aria-labelledby` naming the button and the row's text node, e.g. "Remove Passkey, added 16 Nov 2026, 14:05 (2)"), → inline confirmation "Remove <row text>?" (Remove, Cancel; Cancel and Escape return focus to that row's Remove button; the confirmation text is the row text, decision 3) → `POST /api/auth/factors/passkey/remove {id}`; `403 stepup-required` → `StepUp`, then once more. `404 not-found` and `409 last-factor` (not reachable for a passkey) → status "That passkey is no longer there." and a list read. Success → list read; focus goes to the page heading. | Owner 2026-11-16 (confirm first). | No confirm. |
| 8 | **Accessible async behaviour (A11Y-01/03, FE-70).** Loading: heading plus `<p role="status">Loading your passkeys…</p>`, list `aria-busy="true"`. One polite live region `security-status` (always in the DOM, empty until used) announces: loaded count, "Passkey added", "Passkey removed", unsupported, and every refusal/failure (cancel, timeout, refused, network, load error); failures are text in that region, not `alert`. During an operation the active control reads its busy label ("Waiting for your passkey", "Removing") and all list controls are disabled (decision 6d); the heading and nav stay operable; Sign out follows decision 6(e), and everything outside `StepUp` follows 6(d) while the dialog is open. Focus: after a success → the page heading (`tabIndex=-1`, always mounted); after a failure or cancel → the control the person used (re-enabled and focused); after a removed confirmation Cancel → that row's Remove; the focus never goes to a node the next render removes. `NotSupportedError` at run time (browser lost support after the page showed Add): Add is hidden, the status says "This browser cannot use passkeys.", Remove stays, and focus goes to the page heading (on the enrolment offer: to Skip), never to Add. | Review P1 #4. | Visual text only. |

The code screen keeps its rule that a 409 `no-passkey` moves focus to the code field. | Round 9 condition for M3g-2a-2. | Focus to status text. |

## 4. Data model
None. No table, column, key, migration or setting. Browser state only: the list is read on each visit
and after every change and kept in component state, never in storage.

## 5. Flows
**5.1 Open Security (2a).** Anchor or URL `/#security` → heading "Security", `role=status` loading → `GET /api/auth/factors`. Unreadable/non-200 → "The list could not be loaded." + Try again (focus on it); 401 → sign-in. Empty → "No passkeys yet." Loaded → rows (decision 3) and the polite count announcement.

**5.2 Add (2b).** Add → single-flight on → begin → [403 → StepUp → begin once] → creation ceremony → confirm → `rotated` (exact success carrying `factor_id`) → list read → "Passkey added", focus heading. Cancel/timeout/`passkey-refused`/`failed` → "The passkey was not added. Try again." (one text for all, AUTH-05), focus Add. `signed-out` 401 → sign-in. Lost/ambiguous confirm → decision 6(b),(f): "We could not confirm the new passkey. Check the list below."

**5.3 Remove (2c).** Remove → confirmation → remove → [403 → StepUp → once more] → `rotated` → list read → "Passkey removed", focus heading. Lost/ambiguous → 6(b),(f).

**5.4 After enrolment (2d).** Decision 10; an ambiguous add stays on the offer (decision 6(f)).

**5.5 Leaving.** Decision 6(a)–(c) at every point; a hashchange to Today while a ceremony is open is "leaving". Unmount after send: the operation finishes and reconciles, the departed screen is untouched.

## 6. Permissions
Every signed-in user may list, add and remove their **own** passkeys, as the server decides (`auth.factors`, `auth.factor-change`; closed role catalogue owner, general, unit_manager, adviser, staff in parent §5/permission matrix: no role differs here). Add and remove need a fresh `factor.change` step-up (D7, AUTH-09). The browser enforces nothing; no other user's factor id and no tenant field is ever sent (TEN-11).

## 7. Threat model
| Threat | Control (with concrete numbers) | How it's tested |
|---|---|---|
| Add/remove without a fresh extra check | Server `403 stepup-required`; page repeats once after a verified dialog, never loops (max 1 repeat) | Vitest: 403 → dialog → one repeat; second 403 → error, no third POST |
| Wrong creation/credential shape breaks every add | Decision 5 exact conversion; confirm body exactly `{credential}` | Vitest: fake authenticator receives `Uint8Array` for `challenge`, `user.id`, each exclude id; exact confirm body (keys listed); missing/non-string binary field → `failed`, no prompt; no assertion fields sent |
| Stale CSRF after add/remove rotates the token | `api.rotated`; lost/malformed answer → `readSession()` (listed state + non-empty token) before any protected POST | Vitest matrix: missing/empty/lost/truncated/5xx for added and removed; held-answer tests below |
| Leaving mid-operation strands the token or the challenge | Decision 6(a)–(f) | Held-answer tests: leave before begin, during prompt (nothing sent), after send (finishes, token updated, no screen update), failed session read (no later POST), repeated activation (one begin); ambiguous add (stale initial list, an unrelated new id with this attempt uncommitted, concurrent additions, a retained exact-success `factor_id`) → "could not confirm", never "added" from the list, no second mutation; ambiguous remove committed and uncommitted; reconciliation GET failing or malformed → "could not load", no claim; the same add paths from the enrolment offer (stays, no advance) |
| Challenge, credential, options leak | Live only in the call; nothing stored, logged, or in history/DOM (UNI-09) | `untouched()` assertions as in `passkey.test.tsx` |
| Learning why an add failed (AUTH-05) | One message for cancel, timeout, refused, failed | Vitest: the four causes → same text |
| Other sessions survive a factor change | Server ends them (AUTH-07); server tests exist (M3g-1c) | Server layer only; the browser slice proves just that it takes the rotated token |
| Wrong credential retired | Unique row text, repeated in the confirmation (decision 3) | Vitest: two same-minute rows, two nulls, UTC/day boundary, DST-free fixed zone; confirmation text equals the selected row |
| Sign out sends a stale token mid-operation | Decision 6(e): logout refused while a sent mutation is unreconciled; unresolved read → no logout, reload advice | Held-answer tests: Sign out after send, no `/api/auth/logout` before reconciliation, then it uses the reconciled token; unresolved read sends nothing |
| Malformed but readable factor list crashes the page or targets a bad id | Decision 3 parser; invalid → load error, no controls | Vitest: *rejected* (controlled load error, no controls, no mutation request, no exception): non-array `passkey`, malformed/empty/duplicate id, non-string or unparseable `created_at`; *accepted* (rows render): `created_at: null` and unknown keys at either level |
| Modal not modal (focus or Sign out reachable behind StepUp) | Decision 6(d): outer page `inert`, focus contained | Vitest mounts StepUp from Add and Remove: outer controls unavailable, dialog controls usable, Escape/Cancel restore origin focus; M3g-2b adds browser keyboard/axe |
| Wrong action chosen from identical "Remove" buttons | Decision 7 accessible name = Remove + unique row text | Vitest: every Remove button has a distinct name; activate by name, confirmation and request id match the row |
| Keyboard/screen-reader user loses place or gets no news (A11Y-01/03) | Decision 8 | Vitest: loading, live-region text per outcome, disabled set, focus after every success/refusal/cancel/unsupported path; M3g-2b: keyboard, axe, overflow in both projects |

## 8. Configurable values
No business value. All words in `web/src/content.ts` (FE-22). The step-up window is the server's
`SKIW_STEPUP_MAX_AGE_MIN` (1 to 5, parent D7); the page reads no number. The display timezone
`Asia/Kuala_Lumpur` (parent §4.1) is one constant in `content.ts`, not a user setting.
