## 3. Per-PR files and design

### M4c-1 — migrator SET-only membership (Q1 (a))

**Why it is needed** [V PG17 `GRANT`, `CREATE FUNCTION`, `ALTER FUNCTION`; M3 plan Risk 1]:
- Changing an owner requires being able to `SET ROLE` to the new owner.
- Replacing a function requires ownership, "including being a member of the owning role".
- `CREATE OR REPLACE` keeps the existing owner.

`skiw_migrator` is a member of no role, and `roles.sql` aborts on any membership except `skiw_backup` in `pg_read_all_data` [V `roles.sql:34-53`]. So no migration can create, replace or drop a `guard` object that a NOLOGIN role owns.

**Change.** Before the DO block, add `GRANT skiw_tenant_guard TO skiw_migrator WITH INHERIT FALSE, SET TRUE;`, and the same for `skiw_auth_lookup`.
- One role per GRANT, because that is what the `check-hardening` parser reads [V `hardening.py:407`].
- INHERIT FALSE means no implicit privileges. SET TRUE means only an explicit `SET ROLE` [V PG17 `GRANT`]. BYPASSRLS applies only after `SET ROLE`.
- The DO allow-list gains exactly these two pairs.
- `check-hardening` derives its expected memberships and their options from `roles.sql` [V `hardening.py:398-422`], so only its tests change.

**Tests.**
- `test_live_role_set.py`:
  - the migrator is in exactly these two roles, with admin f, inherit f, set t;
  - no other role is a member of either;
  - `skiw_app` is in no role;
  - BYPASSRLS is held only by `postgres`, `skiw_auth_lookup` and `skiw_backup`;
  - a migrator without `SET ROLE` sees no FORCE-RLS row.
- `check-hardening` fails on a planted third membership, and on `INHERIT TRUE`.
- Running `roles.sql` twice changes nothing [A7].

**Runbooks.**
- **Hosts:** run `bootstrap-db apply` before the first M4c-2a deploy [V `bootstrap_db.py:138-152`]. Without it, the migration fails with "permission denied to set role" and the old digest keeps serving [V `deploy.py:7-11, 561`].
- **Local:** `10-roles.sh` is a `docker-entrypoint-initdb.d` script [V `docker-compose.yml:11`], so it runs only on an empty data directory [A]. Existing volumes need `make clean` (`local-dev.md`).

**Semgrep** (`semgrep/tenancy-boundaries.yml`, with fixtures):

**Where the lookups live.** M3e's `guard.auth_lookup_login` and M3g's `guard.auth_lookup_credential` are created in `app/accounts/migrations/`, as the M3 plan puts them in `accounts` (M3 plan §3 M3e, M3g). Each body reads `guard.lookup_decoy_key` and inserts into `security_event`.
- The existing `auth-tables-accounts-only` rule already allows `/app/accounts/migrations/` [V `semgrep/auth-tables-accounts-only.yml`, `paths.exclude`]. It stays unchanged.
- So `tenancy-boundaries` allows `/app/accounts/migrations/` on purpose for the `guard.*_key` pattern, with a comment in the rule that names M3e and M3g.
- **Fixture line.** `semgrep/tenancy-boundaries.py` carries a `# ruleid:` line with the lookup's SQL shape (`SELECT key FROM guard.lookup_decoy_key …`), so the pattern is proved to flag it outside the allowed paths. The fixture file cannot sit under `app/accounts/migrations/`, so the path allowance itself is proved by M3e's real migration passing `make lint`.

**Migration `tenancy/0001_guard`.** It uses only `migrations.RunSQL`, because `migration_labels` treats any project `Operation` subclass as a contract migration [V `migration_labels.py:9-12, 62-64`]. In order:
1. `CREATE SCHEMA guard`.
2. `CREATE EXTENSION pgcrypto WITH SCHEMA guard` [A1].
3. Grant USAGE on `guard` to `skiw_app` and to the two NOLOGIN roles.
4. Create `guard.tenant_mac_key(version int pk check 1–999999, key bytea not null check octet_length ≥ 32, created_at, retired_at)` through `as_owner('skiw_tenant_guard', …)`, so `skiw_tenant_guard` owns it and the reverse `DROP` runs as the owner too.
5. Create `guard.lookup_decoy_key(version, key)` with the same checks, through `as_owner('skiw_auth_lookup', …)`.

**No grant on either key table to anyone**: not to `skiw_app` or `skiw_readonly` (§4.1), and not to `skiw_migrator`. H4's "written only by the `migrate` task" is met by M4c-3, which writes both tables after an explicit `SET LOCAL ROLE` to the owner. So a plain migrator connection (for example `pg_dump -t guard.tenant_mac_key`) cannot read them, and every read by the migrator is an explicit `SET ROLE`, issued only through `tenancy.ddl` (`as_owner`, `owner_role`), called from `tenancy/keys.py` and migrations (§9 item 2). `skiw_backup` keeps `pg_read_all_data`, and H6 excludes the data from dumps.

**`test_queue_grants.py`.** `test_every_table_is_in_the_closed_global_list` lists every relation outside `pg_*` and `information_schema` and requires an exact match [V `app/jobs/tests/test_queue_grants.py:61, 74-77, 98-100`]. M4c-2a is the first PR to add an unlisted table, so its expected set gains `tenant_mac_key` and `lookup_decoy_key`. M4c-6a replaces this set (below).

**Helper `tenancy.ddl.as_owner(role, statements, reverse)`.** It returns one `RunSQL` that:
1. grants CREATE on `guard` to the role (the new owner needs it [V PG17 `ALTER FUNCTION`]);
2. runs `SET LOCAL ROLE`;
3. runs the statements;
4. runs `RESET ROLE`;
5. revokes CREATE.

Rules for its use:
- `role` must be one of the two NOLOGIN names.
- M3e and M3g create, replace and drop their lookups through it.
- The role is always set explicitly, so nothing relies on inherited ownership [A2].
- Each statement is its own list item, because M3c-1 found that `lintmigrations` flags a multi-line `CREATE TABLE` and a reverse `DROP TABLE` [V `docs/DECISIONS.md:483`] [A3].

**Tests** (`test_guard_schema_live.py`):
- **Owners:** each key table is owned by its role, and `guard` by the migrator.
- **CREATE on `guard`:** after `migrate`, only the migrator has it.
- **Key tables (TEN-02):** `has_table_privilege` is false for every privilege on both, for `skiw_app`, `skiw_readonly` and `skiw_migrator`. This includes `has_table_privilege('skiw_migrator', 'guard.tenant_mac_key', 'SELECT')` and the same for `guard.lookup_decoy_key`. INHERIT FALSE means the membership adds nothing to this check.
- **No CREATE anywhere:** `skiw_app` has CREATE on no schema (extends `app/tests/test_live_db_roles.py:63`).
- **Extension:** `pgcrypto` is in `guard`.
- **Helper:** `as_owner` refuses any other role.

### M4c-3 — `migrate` writes the key tables

**Trigger.** A `post_migrate` receiver in `TenancyConfig.ready()`, for sender tenancy only.
- **Where the signal fires.** `migrate --plan` returns before any signal [V `django/core/management/commands/migrate.py:241-256`]. Every other run emits it, even when nothing is applied (`:380`).
- **Who runs `migrate`.** `skiw-deploy` runs it on every forward deploy [V `deploy.py:82, 288, 561`]. `make migrate` runs it in CI [V `Makefile:114-117`].
- **Not affected.** `migration_labels` uses no database [V `migration_labels.py:1-3`].
- **Role check.** The step refuses unless `session_user = current_user = 'skiw_migrator'`. It checks this before the first `SET ROLE`, because after it `current_user` is the owner.

**`tenancy.keys.write_guard_keys()`** runs as one transaction. The migrator holds no grant on either key table (M4c-2a), so every statement, the compares included, runs as the table's owner, which the spec allows:
1. `SET LOCAL ROLE skiw_tenant_guard`, then the `tenant_mac_key` writes below;
2. `SET LOCAL ROLE skiw_auth_lookup`, then the `lookup_decoy_key` writes below;
3. `RESET ROLE`, then commit.

The role switch goes through `tenancy.ddl.owner_role(cursor, role)`, a small context manager with the same two-name allow-list as `as_owner()`. `as_owner()` itself returns a `RunSQL` operation, so it cannot serve a `post_migrate` receiver.
- **`tenant_mac_key`:**
  - a missing version is inserted, and the same bytes are left alone;
  - **different bytes for an existing version stop `migrate`**, with a message that names the key and version, never the value (UNI-09);
  - a version that is no longer listed gets `retired_at = now()`, which `current_agency()` refuses.
- **`lookup_decoy_key`** holds exactly the file's versions: changed ones are refused, unlisted ones deleted.
- **No key bytes leave the database.** Comparisons run in SQL, and nothing is logged.

**Readers.** `SKIW_TENANT_TOKEN_KEYS` and `SKIW_LOOKUP_DECOY_KEYS` are lazy `partial(env.versioned_keys, …)`. `max_version` 999 999 matches the CHECK [V `app/config/env.py:121`].

**Wiring.**
- **Compose:** `migrate` gains `TENANT_TOKEN_KEY_FILE` and `LOOKUP_DECOY_KEY_FILE`; the secrets are already mounted [V `compose.yml:130`]. A Compose test checks that every `*_FILE` names a secret the service mounts.
- **Local:** `make .env` appends two `v1:` lines [V pattern `Makefile:95-98`].
- **Scanning:** gitleaks already covers both names [V `.gitleaks.toml:11-12`].

**Runbooks (UNI-16).**
- **`host-rebuild.md`:**
  - rotation is: add a version, deploy, restart, retire;
  - after a restore, `migrate` rewrites both tables, because dumps exclude them;
  - a rollback runs no `migrate` [V `deploy.py:14-15`].
- **`local-dev.md`:** the two `.env` lines.

**Seam:** wiring and runbooks / key writes. The `SET ROLE` steps and `owner_role` add ≈ 20 lines to the key-write half.

**Tests** (`test_key_writes_live.py`, running `migrate` in a subprocess):
- **Idempotent:** keys are written, and a second run is a no-op.
- **Changed key:** `migrate` exits ≠ 0, the table is unchanged, and no key text is printed.
- **Unlisted version:** retired (MAC) or deleted (decoy).
- **Bad key file:** a missing or malformed file fails.
- **`--plan`:** writes nothing.
- **Wrong role:** `skiw_app` is refused.
- **As the owner:** after the step, `current_user` is back to `skiw_migrator`. A plain migrator `SELECT` on either key table, with no `SET ROLE`, fails with "permission denied", so no standing grant carries the writes.
- **Helper:** `owner_role` refuses any role but the two NOLOGIN names.

### M4c-4a — `guard.current_agency()` and the token

**Token** (`tenancy/token.py`). Format: `v<n>.<agency uuid>.<xid>.<base64url MAC>`.
- The MAC is HMAC-SHA-256 under key version n, over length-prefixed fields: `skiw-tenant-v1`, `current_database()`, the agency id (16 bytes) and the xid (8 bytes, big-endian).
- The fields are §4.2 item 2. The encoding is mine [A].

**`guard.current_agency()`** (`tenancy/0002`, created via `as_owner('skiw_tenant_guard', …)`).
- **Declaration:** plpgsql, `STABLE`, `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, all names schema-qualified.
- **Steps:**
  1. Parse `current_setting('app.tenant_token', true)` with one anchored regex.
  2. Require the xid to equal `pg_current_xact_id_if_assigned()`.
  3. Load the key version, which must not be retired.
  4. Recompute the MAC with `guard.hmac(…, 'sha256')`.
  5. Compare by double HMAC.
  6. Return the agency id.
- **Failure:** any failed step returns NULL. The function never raises, never logs, and uses no `EXECUTE`.
- **Grants:** `REVOKE EXECUTE … FROM PUBLIC; GRANT EXECUTE … TO skiw_app`.

**Tests:**
- Python and SQL agree on a fixed vector.
- TEN-12 row:
  - `proowner = 'skiw_tenant_guard'::regrole`;
  - `proacl` is the owner plus `skiw_app` only;
  - `prosecdef` is true;
  - `proconfig` pins `search_path`;
  - `provolatile = 's'`;
  - `prosrc` contains no `EXECUTE`.
- M3e and M3g check their lookups the same way, with `proowner = 'skiw_auth_lookup'::regrole`.

### M4c-4b — `with_agency()`

**`tenancy.binding.with_agency(agency_id: uuid.UUID)`** (sync).

It refuses two things:
- an argument that is not a UUID;
- an open `atomic` block, because nesting could re-mint the token for another agency on the same xid.

Then, in order:
1. Open `transaction.atomic()`.
2. Read the xid and the database name.
3. Mint the token under the newest key.
4. Run `set_config('app.tenant_token', %s, true)`.
5. Yield.

A nested `atomic()` inside the block keeps the xid (§4.2 item 4). The token is never logged.

**Start-up.**
- `config/asgi.py` and `runworker` call `SKIW_TENANT_TOKEN_KEYS()` next to the existing key checks [V `app/config/asgi.py:17-19`, `runworker.py:20-21`].
- `x-app-env` gains `TENANT_TOKEN_KEY_FILE`; the secret is already mounted [V `compose.yml:54`].
- `docker-compose.yml` passes `TENANT_TOKEN_KEY` to `app` and `worker`.

**Tests** (as `skiw_app`):
- Under `with_agency(A)`, `current_agency()` returns A.
- It returns NULL for all of these:
  - no token;
  - random text;
  - a B-shaped token with a bad MAC;
  - a truncated token, or one with extra fields;
  - an unknown or retired key version;
  - a real token replayed from another transaction;
  - `set_config('app.agency_id', B, true)`;
  - `COMMIT; BEGIN` without the helper.
- Nesting `with_agency` is refused.
- Web and worker refuse to start without the key, and print no key text.

### M4c-5 — `agency` root (Q2 (a))

**Model and policy.**
- `Agency` is created with `CreateModel`: `id` uuid, `name`, `timezone` (default `Asia/Kuala_Lumpur`) and `data_region` (default `MY` [A]).
- Then a §4.1 root-template `RunSQL`:
  - ENABLE + FORCE;
  - a restrictive `FOR ALL TO skiw_app` policy, `USING`/`WITH CHECK (id = (SELECT guard.current_agency()))`;
  - a permissive SELECT policy;
  - a SELECT-only grant.

**Seed.** `tenancy.seed.seed_deployment_agency(conn, id, name)` runs in the migrate step after the key writes, in its own transaction as the migrator (the key-write transaction has committed and reset the role). Only the table owner can run `NO FORCE`. It is one migrator transaction:
1. `SET LOCAL lock_timeout = '5s'`
2. `LOCK TABLE agency IN ACCESS EXCLUSIVE MODE`
3. `NO FORCE ROW LEVEL SECURITY`
4. read every `agency.id`
5. decide:
   - the table is empty: `INSERT` the configured agency;
   - the configured id is present: do nothing;
   - otherwise: raise. The message names the configured id and PROJECT §9's second-agency gate. `migrate` exits ≠ 0.
6. `FORCE ROW LEVEL SECURITY`
7. assert `relforcerowsecurity`
8. commit

Rules for the seed:
- The read in step 4 must come after `NO FORCE`. Under FORCE the migrator sees zero rows, so an earlier read would always see "empty" and insert the new id.
- A raise rolls the whole transaction back. DDL is transactional, so the rollback also restores FORCE.
- The `NO FORCE` lift is needed because under FORCE the owner is bound by RLS, and no policy names the migrator.
- The seed never updates or deletes.

**Why "only into an empty table", not "refuse any other id".** PR 82 R1 P2's stricter rule (refuse when any row has another id) would break the live suite.
- `make test-live` re-runs `make migrate` [V `Makefile:37-39`], and `django_db_setup` never flushes [V `app/jobs/tests/conftest.py:15-19`].
- M4c-3's and M4c-5's tests also run `migrate` in a subprocess, after agencies A and B are committed in the same session.
- The rule used here closes the same hole. The operator changes `SKIW_DEPLOYMENT_AGENCY_ID` on a host that already holds X: the table is not empty and lacks Y, so `migrate` refuses.
- Invariant: outside tests, the migrate step is the only writer of `agency`, and it inserts only into an empty table. So a host holds at most one row.

`tenancy.seed.insert_agency(conn, id, name)` is the test-only twin: lock, `NO FORCE`, `INSERT … ON CONFLICT (id) DO NOTHING`, `FORCE`, assert, commit. It has no one-agency check, because the A/B fixtures need two agencies.

**Host config** (non-secret): `SKIW_DEPLOYMENT_AGENCY_ID` and `_NAME`.
- They live in `infra/host/env/{ci,staging,production}.env` and are passed to Compose `migrate` and `x-app-env`.
- Exactly one uuid is allowed while the second-agency gate is locked (PROJECT §9). A list or a malformed id fails `migrate`. A changed id on a host that already holds an agency fails the seed (above).
- The builder generates the uuids. The owner gives the names.

**Local and CI config.**
- `.env.example` carries a fixed dev uuid and `Local agency`.
- `make .env` copies `.env.example` [V `Makefile:95-96`], and `make test-live` depends on `.env` [V `Makefile:37`]. So CI needs no workflow change [V `.github/workflows/ci.yml:45`].
- `local-dev.md` covers older `.env` files.

**`/readyz`.** `database_ready()` [V `app/jobs/startup.py:34-42`] also runs `with_agency(<deployment agency>)`. It requires `current_agency()` to match, and the agency row to be visible. A key mismatch then fails the deploy check and the deploy switches back, instead of every read silently returning no rows.

**`test_queue_grants.py`.** The exact-match test gains `agency` as the one named root table, because the schema check that classifies it arrives in M4c-6b.

**Seam:** table and seed / readyz.

**Tests** (`test_agency_live.py`):
- **Seed:** idempotent, and a failure injected after `NO FORCE` leaves FORCE on.
- **Second agency:** X is the configured agency, which `make migrate` already seeded. Run `migrate` in a subprocess with `SKIW_DEPLOYMENT_AGENCY_ID` = Y. Then:
  - `migrate` exits ≠ 0;
  - Y is absent and the set of agency ids is unchanged (the test DB also holds A and B, so the test does not assert "only X");
  - `relforcerowsecurity` is true.
- **Empty table:** this branch runs on every fresh database, which is CI's first `make migrate`; the seed test above then finds X.
- **Isolation:** B's row is invisible under A, and `skiw_app` INSERT, UPDATE and DELETE are denied.

### M4c-6a — policy template and global list

**`TenantModel`.** An abstract base with `agency_id = UUIDField()` and `UniqueConstraint(agency_id, id)`, so `makemigrations --check` catches drift. ORM FKs use `db_constraint=False` (spec §4).

**Tests:**

### M4c-6b — schema check

**`check(conn, schemas=None, extra_allowed=())`.** Every relation of kind r, p, v, m or f outside `pg_*` and `information_schema` must be exactly one of:
- a listed global table (an existing table must be on the list; a listed table need not exist, as in M4c-6a);
- the `agency` root shape;
- a tenant table, which needs all of these:
  - `agency_id uuid not null`, `id`, and `unique(agency_id, id)`;
  - ENABLE + FORCE;
  - a restrictive policy with both USING and WITH CHECK;
  - template-shaped permissive policies only, meaning role `skiw_app` and the exact predicate as `pg_policies` deparses it [A4];
  - the FK to `agency`;
  - a composite FK for every FK to a tenant table.

These are always violations:
- `current_setting` in a predicate;
- a `true` predicate;
- a PUBLIC policy;
- an unlisted view.

**`manage.py check_tenancy_schema`.** It prints the table and the reason, never data. It runs last in the migrate step, so a bad schema fails CI and stops a deploy before the switch. `extra_allowed` (`jobs_probe`, `files_probe`) is used in tests only.

**Runbook text (`host-rebuild.md`).** On a host the check runs after the migrations are applied. If it fails there, the bad table stays in the database, because migrations are never reversed, and the old digest keeps serving. CI runs the same check first, so this needs a missed CI result. The fix is a forward migration that makes the table compliant (or drops it), then a new deploy. Do not run a reverse migration on the host.

**Fixtures.** Each case is DDL in a scratch schema, inside a migrator transaction that is rolled back.
- **Pass:** a compliant tenant table, a listed global, the real `agency`, and the real schema.
- **Fail:**
  - an undeclared table without `agency_id`;
  - no `unique(agency_id, id)`;
  - an `agency`-shaped table under another name;
  - a single-column FK;
  - a `current_setting('app.agency_id')` policy;
  - three of my own cases: RLS not forced, a permissive `USING (true)`, an unlisted view.

**`make db-test`** runs `pytest -m live app/tenancy` plus the check. PROJECT §7's "pending M4" line becomes this command, with the owner's yes in the PR.

### M4c-7a — TEN-08 harness

**Cases.** `tenancy/tests/isolation.py` defines `IsolationCase(table, insert(cursor, agency_id, parents) -> id, commands, parents)`. Each app registers its cases in `<app>/tests/isolation_cases.py`.

## 6. Rollback, host and CI impacts

**Migrations (UNI-15).** They only add objects, with exact reverses while no host holds real data.
- Reversing `tenancy/0001` drops the key tables, and the next forward `migrate` rewrites them.
- A code rollback does not undo M4c-1's membership. Removing it is a reviewed `roles.sql` change plus `bootstrap-db apply`.

**Code rollback.** A rollback to an M3c digest runs on the new schema, because no M3c code reads `tenancy`. It runs no `migrate`, so the keys and the agency row are kept.

**Host changes:**

## 7. Risks / what the reviewer should look at first

1. **Membership (Q1).** The `migrate` container can `SET ROLE skiw_auth_lookup`, which carries BYPASSRLS.
   - Mitigation: that container is one-off, started only by `skiw-deploy`, and is the only holder of the migrator password [V `secrets.py:52`].
   - Check: `INHERIT FALSE`, the drift guard, and that no app path holds the migrator credential.
   - The migrator holds no grant on the key tables. It reads them only after an explicit `SET ROLE`, issued only through `tenancy.ddl` (`as_owner`, `owner_role`), called from `tenancy/keys.py` and migrations. Check the M4c-2a privilege test.
2. **Seed (Q2).** It must be one locked transaction that re-forces before commit, and inserts only into an empty table.
   - ACCESS EXCLUSIVE is taken on `agency` on every deploy, while the old digest still serves. Every tenant table has an FK to `agency`, so every tenant-table write takes a key-share lock on the agency row and queues behind the seed for up to `lock_timeout` (5 s). A long open transaction makes the deploy fail cleanly instead. At about 5 users this is acceptable. A later PR can skip the lock when the row is already there.
   - `lock_timeout` makes a stuck deploy fail cleanly instead of stalling writes. Check the rollback test.
   - Check that the id read comes after `NO FORCE`, and the second-agency test.
3. **`current_agency()`.** Check:
   - the regex anchoring;
   - the xid check;
   - that retired keys are refused;
   - the double-HMAC compare;
   - no `EXECUTE`;
   - NULL on bad input, never an error.
4. **Schema check gaps.** A gap ships a tenant table without RLS. Check the fail fixtures and the deparse match [A4].
5. **Key mismatch fails open.** Without the `/readyz` check, a stale key would show up only as empty reads.
6. **xid per transaction.** One is assigned even for read-only requests [A6].
7. **Data migrations on FORCE tables.** They see no rows as the migrator (§9 item 10).
8. **Size.** See §1.

## 8. Owner questions (at most two options each; builder pick last)

### Q1 — How do `guard` objects come to be owned by `skiw_tenant_guard` / `skiw_auth_lookup`?

**Blocks:** M4c-1, M4c-2a, M3e and M3g.

**Facts:** The migrator cannot `SET ROLE` to either role today. M3e, M3g and M9 must create definer functions, and later replace or drop them. Only the owner, or a role that can `SET ROLE` to the owner, may do that [V PG17].

**Option (a): SET-only membership.** `skiw_migrator` gets `INHERIT FALSE, SET TRUE` membership in both roles, and migrations use `SET LOCAL ROLE` through `as_owner()`. Every schema change stays in Django migrations.
- **Cost:**
  - The migrator can act as `skiw_auth_lookup` (BYPASSRLS), and this leaves no DDL trace.
  - `pg_dump --role=skiw_auth_lookup`, run as the migrator, would succeed. G-S1's plain migrator dump still fails.
  - The migrator can read both key tables by `SET ROLE` to the owner. It holds no standing grant on them, so a plain migrator connection cannot read them, and each read is an explicit `SET ROLE` (M4c-2a, M4c-3; §9 item 2).
- **Limit of the cost:** the migrator already owns every table and can `NO FORCE` or `DISABLE` RLS by DDL. So it gains no data it could not already reach.

**Option (b): postgres socket step.** `infra/host/db/guard_owners.sql` runs as superuser via `bootstrap_db.psql_script` [V `bootstrap_db.py:51`; call site `deploy.py:433`], from `skiw-deploy` and from `make migrate`. It runs after `migrate`, and before it whenever an object must be handed back for a replace.
- **Cost:**
  - Superuser SQL runs on every deploy. Today `skiw-deploy` uses `postgres` only for two read-only statements (PROJECT §9 TEN-10).
  - Each guard object is defined in two places.
  - Reverse migrations need the same step.
  - A crash between steps leaves definer functions owned by the migrator.

**Pick: (a).** It has fewer moving parts, everything stays in migrations, and the added reach is one the migrator already has as owner.

### Q2 — How does the deployment agency row get in?

**Blocks:** M4c-5 and M3e (the invite command).

**Facts:** §4.1 says `agency` "writes only via ADMIN_TX_HELPER", but `with_admin_operation` needs `audit_event`, which arrives in M5. Under FORCE RLS the migrator can insert nothing. The agency list is host config (PROJECT §8).

**Option (a): the `migrate` step inserts it.** The step inserts the one host-config agency, insert-only and only into an empty table, in one locked `NO FORCE`/`FORCE` transaction. If the table holds an agency and not the configured id, it refuses and rolls back, so a changed id cannot add a second agency. Tests create agencies A and B with `insert_agency`, the test-only twin without the one-agency check. The spec is amended (§9 item 3).

**Option (b): `bootstrap-db apply` inserts it.** It inserts the row once as `postgres`. Local and CI then need another path, and tests need yet another way to create agencies.

**Pick: (a).**
