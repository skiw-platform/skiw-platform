# Runbook — local development

Applies from M0a. Other runbooks: [README](README.md); deployment, rollback and restore are skeletons until M1.

## Prerequisites
- `uv` (installs Python 3.12 from `.python-version`), Docker with Compose, GNU make.
- Node 24.21.0 and pnpm 11 for the web shell. Use `fnm` (`fnm install` then `fnm use`; it reads `.node-version`). `make` refuses other Node majors (`make check-node`).
- Once per clone: `make hooks` and `brew install gitleaks`. The pre-push hook then scans the commits you push for secrets and blocks the push if gitleaks is missing.
- First end-to-end run only: `pnpm -C web exec playwright install chromium`.

## First run
1. `make install` — creates `.venv` from `uv.lock` and installs the web packages from `pnpm-lock.yaml`.
2. `make dev` — builds the web shell, copies `.env.example` to `.env` if missing, starts Postgres 17, runs `make migrate` (the worker needs the queue tables), then builds the image and starts the app and the Procrastinate worker.
3. `curl http://127.0.0.1:8000/healthz` returns `ok` (HTTP 200); `curl http://127.0.0.1:8000/readyz` returns `ok` (200) only when the database answers as `skiw_app` and no migration is unapplied, else `not ready` (503); `http://127.0.0.1:8000/` shows the shell.

| `make test` | pytest (no database needed) and vitest |
| `make web-build` / `make web-dev` | production build of the shell into `web/dist` / Vite dev server with `/healthz` and `/api` proxied to `:8000` |
| `make e2e` | builds the shell, starts the database and migrates, starts the app (not the worker), runs Playwright on desktop and mobile widths (axe, keyboard, overflow, no-JS, console errors) |
| `make test-live` | starts the database, migrates as `skiw_migrator`, then runs the `live` tests as `skiw_app`: role checks, `jobs.enqueue_in_tx` commit/rollback/visibility and refusals, the queue-grant audit and the worker lifecycle; the file-store harness (`app/documents/tests/test_harness_live.py`: five crash points, concurrent attempt, damaged clean file) on a `files_probe` table it creates through `MIGRATION_DATABASE_URL` and drops at the end; the tenancy isolation harness (`app/tenancy/tests/test_isolation_live.py`, TEN-08) and the row-level forged-tenant, leak and EXPLAIN tests (`test_row_level_live.py`, TEN-09) on a `tenancy_fixture` schema each module drops, builds and drops again. An interrupted run can leave `files_probe`, `jobs_probe` or the harness's `USING (true)` table `tenancy_fixture.leaky` behind, and the next `make migrate` then fails the schema check naming it: drop it as `skiw_migrator` (`DROP TABLE public.files_probe;`, `DROP SCHEMA tenancy_fixture CASCADE;`) or run `make clean`. A leftover compliant pair (`tenancy_fixture.parent`, `.child`) passes the schema check; the next live tenancy run drops the schema before its first test |
| `make db-test` | starts the database, `make migrate` (which ends with the schema check), the live tenancy tests (`pytest -m live app/tenancy`: isolation harness, row-level forged, leak and EXPLAIN tests, schema-check fixtures, tenant binding), then the schema check again on what they leave |
| `make host-test` | host tooling unit tests and the `infra/host/compose.yml` config tests in `infra/host/tests` (no Docker daemon; the Compose tests need the `docker compose` CLI, skip without it locally and fail in CI) |

About 1.5 minutes with a warm build cache |
| `make secrets-test` | proves `.gitleaks.toml` flags each secret key name (generated values; skips without gitleaks locally, fails in CI) |
| `make audit` | `make secrets` (gitleaks, needs `brew install gitleaks`), `make audit-python` (pip-audit), `make audit-web` (pnpm audit) |
| `make image-scan` | builds the image and scans it with Trivy (needs `brew install trivy`) |
| `make hooks` | enables `.githooks/pre-push` (secret scan of pushed commits) |
| `make db-up` | starts only the database and waits until healthy |

## Environment variables
Locally and in CI these come from `.env` (copied from `.env.example`; never committed). On the Hostinger hosts
they come from the host secret files and the Compose environment instead (below). The app fails to start if
its secret key source (`DJANGO_SECRET_KEY`, or `DJANGO_SECRET_KEY_FILE` on hosts) or `DATABASE_URL` is missing.
- `DATABASE_URL` is the runtime URL and uses `skiw_app`. The `app` container and any host-run app or test use it (TEN-02).
- `MIGRATION_DATABASE_URL` uses `skiw_migrator`. Only `make migrate` reads it, and it injects it as `DATABASE_URL` for that one process (TEN-01).
- The `worker` container (`python app/manage.py runworker`, which checks migrations and then runs `procrastinate worker`) also connects as `skiw_app`, with only the queue grants of spec §4.1 (migration `jobs.0001`). It keeps finished jobs (`delete_jobs = "never"`); there is no cleanup yet.
- Hosts read secrets from files, not the environment (spec §8.4 H4): `DJANGO_SECRET_KEY_FILE` (`v<n>:<base64>` lines; the newest version is `SECRET_KEY`, older ones `SECRET_KEY_FALLBACKS`) replaces `DJANGO_SECRET_KEY`, and `DATABASE_PASSWORD_FILE` (one line) supplies the password that `DATABASE_URL` then must not carry. Setting both forms, or a malformed file, stops startup. Local `.env` values keep working.
- `SKIW_SESSION_ABSOLUTE_H` (whole hours, 1 to 72; `12`) and `SKIW_SESSION_IDLE_MIN` (whole minutes, 1 to 1440; `30`) are required by every settings import: the `app` and `worker` containers, `make` tooling (`TOOL_ENV`), CI and the host Compose services (spec D6, §8.1). A missing or out-of-range value stops startup without printing it. An existing `.env` made before M2b needs both lines from `.env.example`. Only the absolute lifetime is enforced so far; M3 adds the idle timeout, and M5 moves both values into `setting`.
- `TENANT_SOURCE_KEY` (`v<n>:<base64>` lines, each at least 32 bytes; hosts use `TENANT_SOURCE_KEY_FILE` instead, and setting both stops startup) is the key that MACs every session row (spec §4.1 `django_session`, M2c). `make .env` appends a random `v1:` line, so no value is committed; an existing `.env` made before M2c needs one: `printf 'TENANT_SOURCE_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. Settings import does not read it (`migrate` has no key); `config.asgi` and `runworker` refuse to start without a valid one, and the session store reads it on first use. The newest version signs, every listed version verifies: replacing the line (or dropping a version) logs out every local session, which is harmless locally.
- `LOGIN_BLOB_KEY` (same line format, version at most `v65535`; hosts use `LOGIN_BLOB_KEY_FILE`) is the key for the login and credential lookup blobs (spec §4.1; the blob code lands in M3b-2). `make .env` appends a random `v1:` line; an existing `.env` made before M3b needs one: `printf 'LOGIN_BLOB_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. `config.asgi` and `runworker` refuse to start without a valid one.
- `TENANT_TOKEN_KEY` and `LOOKUP_DECOY_KEY` (same line format, version at most `v999999`; hosts use `TENANT_TOKEN_KEY_FILE` and `LOOKUP_DECOY_KEY_FILE`) are the sources of the two guard key tables (spec §4.1 `guard.tenant_mac_key`, `guard.lookup_decoy_key`; M4c-3). After every `migrate` (not `migrate --plan`), `tenancy.keys` writes them as the tables' NOLOGIN owners in one transaction: a new version is inserted, an unlisted one is retired (`tenant_mac_key`) or deleted (`lookup_decoy_key`), and a version whose bytes changed, or a retired version listed again, stops `migrate` with a message that names the key and version only. `make .env` appends a random `v1:` line for each; an existing `.env` made before M4c-3 needs both, or `make migrate` fails with `TENANT_TOKEN_KEY (or TENANT_TOKEN_KEY_FILE on hosts) is required and not set`: `printf 'TENANT_TOKEN_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env` and `printf 'LOOKUP_DECOY_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. Replacing a line's value later stops `make migrate`; locally, `make clean` (deletes the local database volume, all local data) or a new, higher version line gets past it. `app` and `worker` also take `TENANT_TOKEN_KEY` (M4c-4b): `with_agency()` mints the tenant token under its newest version, and both refuse to start without a valid key. `LOOKUP_DECOY_KEY` has no other reader yet (the lookups, from M3e).
- `SKIW_DEPLOYMENT_AGENCY_ID` (exactly one lowercase uuid) and `SKIW_DEPLOYMENT_AGENCY_NAME` (1 to 200 printable characters; quoted in `.env`, which `make` sources in a shell) name the one deployment agency (M4c-5). After every `migrate`, right after the key writes, `tenancy.seed` inserts it into an empty `agency` table, leaves it alone when it is already there, and stops `migrate` if the table holds another id, so a changed id can never add a second agency (PROJECT §9). `/readyz` also binds `with_agency()` to it and answers 503 unless the verifier gives that agency back and its row is visible. `.env.example` carries a fixed local uuid and `"Local agency"`; an `.env` made before M4c-5 lacks both, and `make migrate` then fails with `SKIW_DEPLOYMENT_AGENCY_ID must be exactly one lowercase uuid`: copy the two lines from `.env.example`. A database where `make test-live` ran on M4c-5-1 alone holds the test agencies A and B but no deployment agency, and `make migrate` then stops with the second-agency message: `make clean` resets it. `make test-live` keeps the agencies the tests add (A and B) next to it, and `make clean` deletes them with the local database.
- The interim auth values `SKIW_ARGON2_*`, `SKIW_AUTH_*`, `SKIW_STEPUP_MAX_AGE_MIN`, `SKIW_TOTP_SKEW_STEPS`, `SKIW_LOGIN_PENDING_MIN` and `SKIW_ENROL_LINK_MIN` (owner Q6 (a), M3b; values and meaning in `.env.example`, bounds in `app/config/settings.py`) are required by every settings import, like the session lifetime. An existing `.env` made before M3b needs those twelve lines from `.env.example`. Nothing reads them yet: the Argon2 values from M3b-2, the others from M3c on.
- CSRF (spec T6, M2d): `CsrfViewMiddleware` checks every non-GET/HEAD/OPTIONS request; nothing may switch it off (Semgrep `no-csrf-exempt`). The token is in the HttpOnly `__Host-csrftoken` cookie and in the shell's `<meta name="csrf-token">`; the SPA sends it back as `X-CSRFToken` (from M3). A refusal is a 403 with `X-Skiw-Csrf: rejected` and a short code (`token-missing`, `token-invalid`, `origin`, `referer`, `no-cookie`). Every view is mounted with `config.routes.route(path, view, name=, methods=, auth=)`, never `path()` (Semgrep `urls-route-only`); a new route also needs a request fixture in `app/tests/csrf_fixtures.py`, or `make test` fails the CSRF gate (`app/tests/test_csrf_gate.py`). `make e2e` runs against `http://localhost:8000` (WebAuthn, M3, refuses an IP address as RP ID); Chromium keeps the `__Host-csrftoken` Secure cookie on that plain-HTTP origin and sends it back (`web/e2e/shell.spec.ts`, desktop and mobile, M3a).
- `DJANGO_BEHIND_CADDY=1` (set only in `infra/host/compose.yml` for `web` and `worker`) makes Django trust `X-Forwarded-Proto: https` (`SECURE_PROXY_SSL_HEADER`), because on hosts Caddy overwrites that header on every request. From M3c-2 it also makes the login throttle take the client IP from `X-Forwarded-For` (`SKIW_BEHIND_CADDY`, `accounts.auth.throttle.client_ip`), which Caddy replaces the same way. Never set it locally or anywhere a client can reach Django without Caddy: a client could then mark a plain request as secure and pick its own per-IP throttle key.
- TLS: `DATABASE_URL` may carry `sslmode`, `sslrootcert`, `sslcert`, `sslkey`, `sslcrl`; other options are rejected. `DJANGO_REQUIRE_DB_TLS=1` is an opt-in check that refuses any `sslmode` other than `verify-full` or `verify-ca`; use it for any database reached over a network you do not control. The planned Hostinger hosts do not set it: the database is only on host-internal Docker networks and spec §8.4 H6 drops TLS there. Local values are placeholders, not secrets.

## Known local conflicts
- The database is published on host port **5433** (`SKIW_DB_PORT`), because 5432 is often taken by another local Postgres.
- The app is published on `127.0.0.1:8000`.

## Background jobs
- Enqueue only with `jobs.enqueue_in_tx(task, **ids)` inside `transaction.atomic()`. Direct `.defer()` / `.defer_async()` / `.batch_defer*()` anywhere else fails `make lint` (Semgrep rule `semgrep/jobs-no-direct-defer.yml`; `.semgrepignore` keeps tests in scope).
- Tasks are registered only through `jobs.registry.job`. Until M4 the only task is the probe `jobs.tasks.noop`.
- Startup gate (spec D16): the web entrypoint (`config.asgi`) and `runworker` refuse to start, with an `unapplied migrations` error, when any migration is unapplied or `django_migrations` cannot be read as `skiw_app`. Run `make migrate` (as `skiw_migrator`) first; the gate never changes the schema.
- Worker logs: `docker compose logs -f worker`. A permission error there means a queue grant is missing: rerun `make migrate`, and see spec §4.1 before adding any grant.

## Rebuilding the database roles
Roles are created only on the first start of an empty volume (`docker/postgres/10-roles.sh`, which runs `infra/host/db/roles.sql`, the same file the hosts use). After changing either, run `make clean` and `make dev`. The M1e change added `skiw_readonly`, `skiw_backup`, `skiw_tenant_guard` and `skiw_auth_lookup` and made `skiw_migrator` own the schema: run `make clean` once. The postgres image runs `docker-entrypoint-initdb.d` scripts only when the data directory has no `PG_VERSION` file (`/usr/local/bin/docker-entrypoint.sh` in the pinned 17.11 image), so an existing volume keeps its old roles. The M4c-1 change gives `skiw_migrator` `INHERIT FALSE, SET TRUE` membership in `skiw_tenant_guard` and `skiw_auth_lookup`: run `make clean` once, or `make test-live` fails `test_live_role_set.py` and, from M4c-2a, `make migrate` fails with `permission denied to set role`.

## CI
`.github/workflows/ci.yml` runs the `checks`, `security`, `image` and `host` jobs on every pull request and on pushes to `main`. See [ci.md](ci.md) for the jobs, how to run each gate locally and the GitHub Free plan limits. The production image builds the web shell in a Node stage and fails if `web/dist/.vite/manifest.json` is missing, malformed, or names a missing file (`python -m shell.verify_dist`); `docker compose` still bind-mounts `./web/dist` over it for local runs.
