# Runbook — local development

Applies from M0a. Other runbooks: [README](README.md); deployment, rollback and restore are skeletons until M1.

## Prerequisites
- `uv` (installs Python 3.12 from `.python-version`), Docker with Compose, GNU make.
  Use the `uv` version CI and the `Dockerfile` pin (0.11.24; `brew install uv` may give a newer one). A newer `uv` rewrites the `uv.lock` header (`revision`), so a lockfile change you did not intend means the wrong `uv` ran.
- Node 24.21.0 and pnpm 11 for the web shell. Use `fnm` (`fnm install` then `fnm use`; it reads `.node-version`). `make` refuses other Node majors (`make check-node`).
- Once per clone: `make hooks` and `brew install gitleaks`. The pre-push hook then scans the commits you push for secrets and blocks the push if gitleaks is missing.
- First end-to-end run only: `pnpm -C web exec playwright install chromium`.

## First run
1. `make install` — creates `.venv` from `uv.lock` and installs the web packages from `pnpm-lock.yaml`.
2. `make dev` — builds the web shell, copies `.env.example` to `.env` if missing, starts Postgres 17, runs `make migrate` (the worker needs the queue tables), then builds the image and starts the app and the Procrastinate worker.
3. `curl http://127.0.0.1:8000/healthz` returns `ok` (HTTP 200); `curl http://127.0.0.1:8000/readyz` returns `ok` (200) only when the database answers as `skiw_app` and no migration is unapplied, else `not ready` (503); `http://127.0.0.1:8000/` shows the shell.

## Environment variables
Locally and in CI these come from `.env` (copied from `.env.example`; never committed). On the Hostinger hosts
they come from the host secret files and the Compose environment instead (below). The app fails to start if
its secret key source (`DJANGO_SECRET_KEY`, or `DJANGO_SECRET_KEY_FILE` on hosts) or `DATABASE_URL` is missing.
- `DATABASE_URL` is the runtime URL and uses `skiw_app`. The `app` container and any host-run app or test use it (TEN-02).
- `MIGRATION_DATABASE_URL` uses `skiw_migrator`. Only `make migrate` reads it, and it injects it as `DATABASE_URL` for that one process (TEN-01).
- The `worker` container (`python app/manage.py runworker`, which checks migrations and then runs `procrastinate worker`) also connects as `skiw_app`, with only the queue grants of spec §4.1 (migration `jobs.0001`). It keeps finished jobs (`delete_jobs = "never"`); there is no cleanup yet.
- Hosts read secrets from files, not the environment (spec §8.4 H4): `DJANGO_SECRET_KEY_FILE` (`v<n>:<base64>` lines; the newest version is `SECRET_KEY`, older ones `SECRET_KEY_FALLBACKS`) replaces `DJANGO_SECRET_KEY`, and `DATABASE_PASSWORD_FILE` (one line) supplies the password that `DATABASE_URL` then must not carry. Setting both forms, or a malformed file, stops startup. Local `.env` values keep working.
- `SKIW_SESSION_ABSOLUTE_H` (whole hours, 1 to 72; `12`) and `SKIW_SESSION_IDLE_MIN` (whole minutes, 1 to 1440; `30`) are required by every settings import: the `app` and `worker` containers, `make` tooling (`TOOL_ENV`), CI and the host Compose services (spec D6, §8.1). A missing or out-of-range value stops startup without printing it. An existing `.env` made before M2b needs both lines from `.env.example`. Only the absolute lifetime is enforced so far; M3 adds the idle timeout, and M5 moves both values into `setting`.
- `TENANT_SOURCE_KEY` (`v<n>:<base64>` lines, each at least 32 bytes; hosts use `TENANT_SOURCE_KEY_FILE` instead, and setting both stops startup) is the key that MACs every session row (spec §4.1 `django_session`, M2c). `make .env` appends a random `v1:` line, so no value is committed; an existing `.env` made before M2c needs one: `printf 'TENANT_SOURCE_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. Settings import does not read it (`migrate` has no key); `config.asgi` and `runworker` refuse to start without a valid one, and the session store reads it on first use. The newest version signs, every listed version verifies: replacing the line (or dropping a version) logs out every local session, which is harmless locally.
- `LOGIN_BLOB_KEY` (same line format, version at most `v65535`; hosts use `LOGIN_BLOB_KEY_FILE`) is the key for the login and credential lookup blobs (spec §4.1; the blob code lands in M3b-2). `make .env` appends a random `v1:` line; an existing `.env` made before M3b needs one: `printf 'LOGIN_BLOB_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. `config.asgi` and `runworker` refuse to start without a valid one.
- `TENANT_TOKEN_KEY` and `LOOKUP_DECOY_KEY` (same line format, version at most `v999999`; hosts use `TENANT_TOKEN_KEY_FILE` and `LOOKUP_DECOY_KEY_FILE`) are the sources of the two guard key tables (spec §4.1 `guard.tenant_mac_key`, `guard.lookup_decoy_key`; M4c-3). After every `migrate` (not `migrate --plan`), `tenancy.keys` writes them as the tables' NOLOGIN owners in one transaction: a new version is inserted, an unlisted one is retired (`tenant_mac_key`) or deleted (`lookup_decoy_key`), and a version whose bytes changed, or a retired version listed again, stops `migrate` with a message that names the key and version only. `make .env` appends a random `v1:` line for each; an existing `.env` made before M4c-3 needs both, or `make migrate` fails with `TENANT_TOKEN_KEY (or TENANT_TOKEN_KEY_FILE on hosts) is required and not set`: `printf 'TENANT_TOKEN_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env` and `printf 'LOOKUP_DECOY_KEY=v1:%s\n' "$(openssl rand -base64 32)" >> .env`. Replacing a line's value later stops `make migrate`; locally, `make clean` (deletes the local database volume, all local data) or a new, higher version line gets past it. `app` and `worker` also take `TENANT_TOKEN_KEY` (M4c-4b): `with_agency()` mints the tenant token under its newest version, and both refuse to start without a valid key. `LOOKUP_DECOY_KEY` has no other reader yet (the lookups, from M3e).
- `SKIW_DEPLOYMENT_AGENCY_ID` (exactly one lowercase uuid) and `SKIW_DEPLOYMENT_AGENCY_NAME` (1 to 200 printable characters; quoted in `.env`, which `make` sources in a shell) name the one deployment agency (M4c-5). After every `migrate`, right after the key writes, `tenancy.seed` inserts it into an empty `agency` table, leaves it alone when it is already there, and stops `migrate` if the table holds another id, so a changed id can never add a second agency (PROJECT §9). `/readyz` also binds `with_agency()` to it and answers 503 unless the verifier gives that agency back and its row is visible. `.env.example` carries a fixed local uuid and `"Local agency"`; an `.env` made before M4c-5 lacks both, and `make migrate` then fails with `SKIW_DEPLOYMENT_AGENCY_ID must be exactly one lowercase uuid`: copy the two lines from `.env.example`. A database where `make test-live` ran on M4c-5-1 alone holds the test agencies A and B but no deployment agency, and `make migrate` then stops with the second-agency message: `make clean` resets it. `make test-live` keeps the agencies the tests add (A and B) next to it, and `make clean` deletes them with the local database. From M3d-1a it also keeps the `app_user` rows the isolation harness commits under A and B, and from M3d-1b their `user_factor` and `session_revocation` rows (a few per run; `skiw_app` may not delete users or revocation markers), and `make clean` deletes those too. `make migrate` creates the `citext` extension in `public` (`accounts.0004`, for `app_user.email`).
- `SKIW_WEBAUTHN_RP_ID` and `SKIW_WEBAUTHN_ORIGIN` (M3g) are the passkey relying party. The RP ID is a lowercase hostname (no scheme, port, trailing dot or IP address); the origin is compared exactly with the one the browser reports, so it must be `https://<RP ID>`, and only an RP ID of `localhost` may use `http` or a port. Unset, the origin is `https://<RP ID>`. `.env.example` sets `localhost` and `http://localhost:8000`, so open the app at exactly `http://localhost:8000` for a passkey ceremony (not `127.0.0.1`). The `app` container needs both and checks them at start-up (`config/asgi.py`); the worker, `migrate` and tooling never read them. An `.env` made before M3g lacks both, and every `docker compose` command then stops with `required variable SKIW_WEBAUTHN_ORIGIN is missing a value`: copy the two lines from `.env.example`. **Changing the RP ID invalidates every passkey registered under it** (the authenticator binds each credential to it); users then sign in with TOTP and add a passkey again.
- The interim auth values `SKIW_ARGON2_*`, `SKIW_AUTH_*`, `SKIW_STEPUP_MAX_AGE_MIN`, `SKIW_TOTP_SKEW_STEPS`, `SKIW_LOGIN_PENDING_MIN`, `SKIW_ENROL_LINK_MIN` (owner Q6 (a), M3b) and `SKIW_PW_MIN_LENGTH` (owner 2026-11-05, M3e-3b; values and meaning in `.env.example`, bounds in `app/config/settings.py`) are required by every settings import, like the session lifetime. An existing `.env` made before M3b needs those lines from `.env.example`; one made before M3e-3b needs the `SKIW_PW_MIN_LENGTH=12` line.
- `SKIW_ASYNC_DB_POOL_MAX` (optional, whole number 1 to 8; unset means 4) caps the connections `tenancy.async_binding.async_with_agency()` opens per process, as `skiw_app` from `DATABASE_URL` (spec D26, M4c-8). The pool opens on first use, and nothing uses it before the bridge long-poll (M14), so no Compose file or host env file sets it yet. A value outside the bounds stops every settings import without printing it.
- CSRF (spec T6, M2d): `CsrfViewMiddleware` checks every non-GET/HEAD/OPTIONS request; nothing may switch it off (Semgrep `no-csrf-exempt`). The token is in the HttpOnly `__Host-csrftoken` cookie and in the shell's `<meta name="csrf-token">`; the SPA sends it back as `X-CSRFToken` (from M3). A refusal is a 403 with `X-Skiw-Csrf: rejected` and a short code (`token-missing`, `token-invalid`, `origin`, `referer`, `no-cookie`). Every view is mounted with `config.routes.route(path, view, name=, methods=, auth=)`, never `path()` (Semgrep `urls-route-only`); a new route also needs a request fixture in `app/tests/csrf_fixtures.py`, or `make test` fails the CSRF gate (`app/tests/test_csrf_gate.py`). It must also be an `accounts.auth.wrapper.authorized_action` handler, or be listed with its reason in `PUBLIC_ROUTES` (`app/tests/test_route_registry.py`, reviewer sign-off), or `make test` fails the route registry test (AUTH-02, M3d). A wrapped route names its `permission` (a catalogue or self-service code) and its `line` (`insurance`, `investment` or `any`; no default) and is listed with both in `ACTIONS` in the same test (reviewer sign-off); no route may register `staff.manage` yet (slice spec Decisions 26, 29; M4r-2b-i). On each request to a catalogue code the wrapper reads the user's grants once, with no cache, so a tick or assignment change holds from the next request. It keeps the grants whose assignment line matches the route's `line` (an action on `any` matches every grant, a grant on `both` every action); a self-service code reads none. A refusal by this step is a 403 with a JSON `error` and no logout: `forbidden` means no second factor, or no grant of the code on a matching line (a line refusal never asks for a step-up); `stepup-required` means every matching grant needs a step-up and this session has no fresh evidence for any of their purposes. A grant that needs one (the step-up column of the slice spec §6.1, for example `outbox.approve`, or `device.revoke` at `agency`) is kept only while `stepup.recent()` finds evidence of this session for that grant's purpose, at most `SKIW_STEPUP_MAX_AGE_MIN` old; the wrapper reads it once per purpose on every request and caches nothing. Evidence of another purpose or another session of the same user does not count. `POST /api/auth/stepup` (and the passkey step-up) accepts `factor.change` and the seven catalogue purposes (`stepup.PURPOSES`); `drive.write` is not one (docs/DECISIONS.md, 2026-11-26 M4r-3a and 2026-11-27 M4r-3b). Focused live test, after `make db-up` and `make migrate`: `set -a; . ./.env; set +a; uv run pytest -m live app/accounts/tests/test_wrapper_roles_live.py`; it ticks each step-up pair and checks none, stale, another purpose and another session (403 `stepup-required`), then a step-up through the real route (200 with exactly that grant). Only `accounts` imports `accounts.auth` (import contract, Decision 11). Only `accounts/access/`, the accounts migrations and the tests touch `role`, `role_permission`, `user_role`, `org_unit` and `permission`, as models or SQL (Semgrep `roles-access-only`, AUTH-12; its limits are in docs/DECISIONS.md, 2026-11-26 M4r-2b-ii). `make e2e` runs against `http://localhost:8000` (WebAuthn, M3, refuses an IP address as RP ID); Chromium keeps the `__Host-csrftoken` Secure cookie on that plain-HTTP origin and sends it back (`web/e2e/shell.spec.ts`, desktop and mobile, M3a).
- Restricted reads (M4r-4b, M4r-4c): a model built on `accounts.access.scope.ScopedModel` is read only through `scoped(model, signed)` (Semgrep `scoped-only`), called afresh in each request, inside that request's `with_agency()`, and evaluated there. It returns rows of `signed.agency_id` only: an `agency` grant gives all of them, `own` the rows whose `SCOPE_OWNER` is the user, `team` the rows owned by anyone with any assignment in the grant's unit or below it; several grants add up, and no grant gives no rows. A grant counts only on a line that matches the model's `SCOPE_LINE` (Decision 9, through the same table as the route line, `catalogue.LINE_MATCHES`): an `insurance` grant sees no `investment` model and the reverse, a `both` grant every model, and a model with `SCOPE_LINE = None` every grant line; this applies to `agency` grants too, after the route's own line check. Outside a transaction it raises `TransactionManagementError`; evaluated after `with_agency()` has closed, it returns no rows (RLS). A cycle under a team unit, a subtree more than 32 levels deep counting the unit (`ORG_MAX_DEPTH`), or a unit RLS cannot see raises `ScopeIntegrityError` (`cycle`, `depth`, `anchor`) instead of returning a QuerySet, so no record is read. It is logged at ERROR on `django.security.scope` as `scope integrity: <reason>, agency <id>, unit <id>`; no live route calls `scoped()` yet (only test routes do), so nothing turns that into a response. The team members are read when `scoped()` is called, so a QuerySet kept for later keeps the old set. The filter also bounds `update()` and `delete()` on the returned QuerySet, but not writes by key (`create()`, `save()` by id, `bulk_create(update_conflicts=True)`): the first restricted record type's spec must say how writes are checked (docs/DECISIONS.md, 2026-11-28 — M4r-4b). Focused live test, after `make db-up` and `make migrate`: `set -a; . ./.env; set +a; uv run pytest -m live app/accounts/tests/test_access_scope_live.py app/accounts/tests/test_scope_routes_live.py`; each module creates the test-only `scope_probe`, `scope_probe_insurance` and `scope_probe_investment` tables as `skiw_migrator` and drops them afterwards (a leftover is dropped at the start of the next live run).
- `DJANGO_BEHIND_CADDY=1` (set only in `infra/host/compose.yml` for `web` and `worker`) makes Django trust `X-Forwarded-Proto: https` (`SECURE_PROXY_SSL_HEADER`), because on hosts Caddy overwrites that header on every request. From M3c-2 it also makes the login throttle take the client IP from `X-Forwarded-For` (`SKIW_BEHIND_CADDY`, `accounts.auth.throttle.client_ip`), which Caddy replaces the same way. Never set it locally or anywhere a client can reach Django without Caddy: a client could then mark a plain request as secure and pick its own per-IP throttle key.
- TLS: `DATABASE_URL` may carry `sslmode`, `sslrootcert`, `sslcert`, `sslkey`, `sslcrl`; other options are rejected. `DJANGO_REQUIRE_DB_TLS=1` is an opt-in check that refuses any `sslmode` other than `verify-full` or `verify-ca`; use it for any database reached over a network you do not control. The planned Hostinger hosts do not set it: the database is only on host-internal Docker networks and spec §8.4 H6 drops TLS there. Local values are placeholders, not secrets.

## Known local conflicts
- The database is published on host port **5433** (`SKIW_DB_PORT`), because 5432 is often taken by another local Postgres.
- The app is published on `127.0.0.1:8000`.
- A second checkout (another worktree) uses its own `COMPOSE_PROJECT_NAME` and `SKIW_DB_PORT` in its `.env`. A passkey ceremony needs the origin the browser shows: if that checkout serves the app on another port (a local Compose override; `docker-compose.yml` publishes 8000), set `SKIW_WEBAUTHN_ORIGIN=http://localhost:<port>` and `E2E_BASE_URL=http://localhost:<port>` to match and keep `SKIW_WEBAUTHN_RP_ID=localhost`; with the default file only one checkout can run the app at a time.

## Background jobs
- Enqueue only with `jobs.enqueue_in_tx(task, **ids)` inside `transaction.atomic()`. Direct `.defer()` / `.defer_async()` / `.batch_defer*()` anywhere else fails `make lint` (Semgrep rule `semgrep/jobs-no-direct-defer.yml`; `.semgrepignore` keeps tests in scope).
- Tasks are registered only through `jobs.registry.job`. Until M4 the only task is the probe `jobs.tasks.noop`.
- Startup gate (spec D16): the web entrypoint (`config.asgi`) and `runworker` refuse to start, with an `unapplied migrations` error, when any migration is unapplied or `django_migrations` cannot be read as `skiw_app`. Run `make migrate` (as `skiw_migrator`) first; the gate never changes the schema.
- Worker logs: `docker compose logs -f worker`. A permission error there means a queue grant is missing: rerun `make migrate`, and see spec §4.1 before adding any grant.

## Rebuilding the database roles
Roles are created only on the first start of an empty volume (`docker/postgres/10-roles.sh`, which runs `infra/host/db/roles.sql`, the same file the hosts use). After changing either, run `make clean` and `make dev`. The M1e change added `skiw_readonly`, `skiw_backup`, `skiw_tenant_guard` and `skiw_auth_lookup` and made `skiw_migrator` own the schema: run `make clean` once. The postgres image runs `docker-entrypoint-initdb.d` scripts only when the data directory has no `PG_VERSION` file (`/usr/local/bin/docker-entrypoint.sh` in the pinned 17.11 image), so an existing volume keeps its old roles. The M4c-1 change gives `skiw_migrator` `INHERIT FALSE, SET TRUE` membership in `skiw_tenant_guard` and `skiw_auth_lookup`: run `make clean` once, or `make test-live` fails `test_live_role_set.py` and, from M4c-2a, `make migrate` fails with `permission denied to set role`.

## CI
`.github/workflows/ci.yml` runs the `checks`, `security`, `image` and `host` jobs on every pull request and on pushes to `main`. See [ci.md](ci.md) for the jobs, how to run each gate locally and the GitHub Free plan limits. The production image builds the web shell in a Node stage and fails if `web/dist/.vite/manifest.json` is missing, malformed, or names a missing file (`python -m shell.verify_dist`); `docker compose` still bind-mounts `./web/dist` over it for local runs.
