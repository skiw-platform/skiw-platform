## What changed
`accounts.auth.second_factor.attempt(request, candidate)` checks one second-factor code for the user a password step left pending (not an enrolment's). Six ASCII digits are a TOTP code, anything else a recovery code. Order: pending state, `throttle.factor_reserve` (count before the check; `limited` over the limit or while the factor lock holds), then in one `with_agency()` transaction the user must still be `active` and the code is compared. TOTP replay is decided by a conditional `UPDATE … WHERE sign_count < step` (row count), recovery codes by `recovery.consume`. A user with no TOTP row runs `totp.accept` on a throwaway secret. A verified code clears the pending state and gives its attempt back; the result is `Passed(user_id, agency_id, factor)` or `unavailable` / `limited` / `wrong_code`. A fault before the comparison gives the attempt back; a fault after a wrong comparison keeps the count (`_Seen.wrong`). No recovery-use revocation marker. DECISIONS "M3f-3c-1c". +444 over 3 files (code 118, tests 314 in 27 live tests, docs 12). No route and no caller; it does not feed the factor lock yet.

## Decisions worth keeping
- Only a fault before the comparison gives the attempt back. A failure an attacker can provoke must not hand every guess back; `_Seen.wrong` is set inside the transaction right after the comparison, so a fault while leaving it keeps the count. A fault after a right code rolls the use back, gives the attempt back, and the code still works.
- The count is global and taken outside `with_agency()`; all tenant reads and writes are inside it, with the agency from the MAC-verified pending session.
- The losing parallel submission of a right code comes back as `wrong_code` and is counted (a double-click costs one count); to be documented with 3c-1d.
- A recovery use writes no revocation marker (a use of the factor, not a change to the set; AUTH-07).
- Per-attempt factor evidence belongs in `audit_event` (M5); the only factor event is `factor.locked`.

### [P3] A spent code if `login()` fails after `attempt` returns `Passed` (for 3c-2)
- Category: resilience (guidance)
- Evidence: on success, `attempt` has already committed the TOTP step update or the recovery-code `DELETE`, and it calls `factors.clear_pending(request)` before returning. The caller then runs `login()`.
- Failure scenario: `login()` raises (the `cycle_key` session write fails; PR 129 R1 P3 #3). The user then has no pending state and has spent the code: a recovery code is gone for good, and a TOTP code is refused until the next step. They must sign in again with their password.
- Why it matters: it is rare and costs the user one of ten recovery codes, not a security issue. It is worth one line, so nobody "fixes" it later by releasing or restoring the code on a login failure, which would reopen replay.
- Required correction: in 3c-2, record this as accepted in DECISIONS (or the route's docstring), and call `login()` immediately after `Passed` with nothing in between.
- Owner: builder · Status: open (3c-2, optional)

**Design calls [A], reviewer answers:**
1. **Kind by shape (six ASCII digits is TOTP, otherwise a recovery code):** confirmed.
   - No input picks the kind, and a 16-symbol recovery code can never be six digits.
   - `recovery.normalise` refuses non-ASCII, overlong (`INPUT_MAX`) and wrong-length input before any query, so odd input (NUL bytes, 5000 characters, Arabic-Indic digits) is a plain `wrong_code`, not a 500.
2. **TOTP and recovery codes share the one per-user budget and lock:** confirmed. Separate budgets would double the guesses.
3. **`unavailable` for a user who is no longer `active`, with the attempt given back:** confirmed. Nothing was compared. 3c-2 must answer `unavailable` the same way for every cause (AUTH-05).
4. **The conditional update decides replay, and `last` stays as a second layer:** confirmed.
   - `UPDATE … WHERE sign_count < step` and its row count make one of two parallel submissions lose.
   - Dropping `last` is equivalent, as the PR says: the update refuses a stored step or an older one by itself.
   - The losing parallel submission of a *right* code comes back as `wrong_code` and is counted. That is harmless, but say so when 3c-1d documents the run (a double-click costs one count).

**Code read (beyond the self-check):**
- The order is pending state → reserve → `with_agency()` → active check → compare.
- `factor_reserve` raises inside an atomic block, so `attempt` can't be called from one.
- Every tenant read and write is under `with_agency(state.agency_id)`, and the agency comes from the MAC-verified session.
- The no-TOTP-row path runs `totp.accept` on a zero secret and ignores the result (spy test). It saves no step and leaks nothing the attacker doesn't already know after the password step.
- Nothing is logged. The candidate is never stored.
- Flow 5.1 (2) also names a passkey as a second factor. That is not in this slice (plan M3g), and the PR doesn't claim it.
