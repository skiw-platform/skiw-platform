## What changed
Adds `webauthn` 3.0.1 (with four transitive packages; `cbor2` held at 6.1.5), `SessionStore.take`, and `accounts/auth/passkey.py`: the single-use challenge and the registration and assertion primitives (user verification required, algorithms pinned, attested id equal to `rawId`, every refusal `None`). Adds a software test authenticator, unit and live tests, and an import-linter contract that keeps `webauthn` inside `accounts`. No route, table, migration or setting. +861/−1 over 10 files (over the 600 rule; the owner chose one PR).

## Why
Plan M3g and owner Q8 (a): optional passkeys, with TOTP still required. The challenge and ceremony checks are the security core of the passkey server half, so they were built and reviewed alone before any route uses them.

- Use `py_webauthn`, do not own CBOR, COSE or attestation parsing; the library defaults user verification to off, so it is required in the options and both verify calls.
- Both zero sign counts are accepted (most synced passkeys send 0); the single-use challenge is then the replay guard, which is why P2 #2 matters.
- `SessionStore.take` refuses to run inside a transaction; the library's messages are dropped and nothing is logged.
- Recorded in DECISIONS "M3g-1" and "M3g-1a-2".

### Nits (no action required)
- The "ES384, not pinned" case (`alg -35`) does not test the pin. py_webauthn 3.0.1 has no `-35` at all; its `COSEAlgorithmIdentifier` has `-36` (ES512) but no ES384. So the key is refused as an unknown algorithm, and would be with or without `ALGORITHMS`. Widening the shared constant is still caught, by the options test, which pins `pubKeyCredParams` exactly (I checked: setting `ALGORITHMS` to every library algorithm fails it). What stays untested is the verify call alone losing `supported_pub_key_algs` (R1 P1, equivalent while the library default matches). Using `-65535` (RSA with SHA-1, which the library knows and the pin is really against) with an RSA key would cover it.
- Mutant R4 (settings read inside the `try`) survives, because no test calls a verify function with the relying-party settings broken. The start-up check (`config/asgi.py`) refuses to serve in that state, so this is defence in depth only.
