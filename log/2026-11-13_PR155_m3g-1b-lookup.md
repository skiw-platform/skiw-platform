### What I checked
- **The function against `auth_lookup_login` (0009), line by line.** The template is the same:
  - plpgsql, `VOLATILE STRICT SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`;
  - owner `skiw_auth_lookup` via `as_owner`; EXECUTE revoked from PUBLIC and granted to `skiw_app`;
  - a key check that raises for every id;
  - the decoy built before the lookup, under the oldest key, in counter mode with a distinct label (`skiw-decoy-credential-v1`);
  - one event with no detail; a bytea equality qualified as `OPERATOR(pg_catalog.=)`.

  The hardening test pins owner, `prosecdef`, `proconfig`, ACL, return and argument types, volatility and strictness exactly. STRICT means a NULL id returns NULL, which `_call` turns into a `RuntimeError`.
- **Decoy.** It is 60 bytes. A test pins `DECOY_LENGTH` = `LOOKUP_BLOB_LENGTH` = `OVERHEAD` + `CREDENTIAL_SIZE`. The decoy is stable, differs per id and per prefix, matches a Python reference, and does not change when a newer key version is added. A retired id gives exactly the unknown-id decoy. The label and the 4-byte counter are both fixed length, so the HMAC input is unambiguous.
- **Retired filter.** `retired_at IS NULL` is equivalent, as the builder says: `user_factor_retired_no_secret` already forces a retired row's blob to NULL. Keeping it as the stated M3h-6 rule is right.
- **Grant.** `SELECT (credential_id, lookup_blob_ct, retired_at)` and no table privilege. `test_queue_grants` lists every column grant of the lookup role, so a widened grant fails there; my mutant S7 (adding `user_id`) was killed. The forward grant runs before `as_owner` creates the function, and the reverse runs in the opposite order.
- **Row checks.**
  - `sign_count` is `NOT NULL` (`db_default=0`), so the `≤ 2³²−1` clause cannot be NULL and let a row through.
  - A NULL `credential_id` makes `Length(...)` NULL, but `credential_id__isnull=False` is FALSE, so the AND is FALSE and the row is refused (the `no-id` test).
  - TOTP's use of `sign_count` as its step is not affected: `passkey_only_columns` leaves `sign_count` alone.
  - No code outside the passkey module writes a passkey column today (`git grep`), so existing TOTP and recovery rows satisfy `passkey_only_columns`.
- **Blob binding.** `open_credential` uses the credential id as AAD, so a blob moved to another row does not open (tested). Every key version is tried either way (`blob._open`).
- **Reverse story (the builder's question 3).** Keeping `last_challenge_at` on reverse is right, and consistent with 0014. A reverse and re-apply must not reset the replay guard. D16 makes the dump the real rollback, and an old release ignores a nullable extra column. `ADD COLUMN IF NOT EXISTS` is load-bearing for the re-apply: mutant S5 (plain `ADD COLUMN`) fails the forward migrate.
- **Migration atomicity.** In my probe the forward migrate failed on a bad row, and it left the database at 0014 with nothing half-applied.

### Findings

#### P3 #1 — test gaps: equal work and the reversed grant (no action required before merge)
Three mutants survived, and I confirmed each was really installed by reading `pg_proc` / `information_schema` while it was in place:
- **S2:** the decoy loop moved after the `SELECT … INTO stored`.
- **S3:** the decoy built only for a miss (the loop moved inside `IF stored IS NULL`). A known id then skips both HMAC blocks.
- **S1:** the column grant not revoked on reverse. At 0014, `skiw_auth_lookup` still held SELECT on the three `user_factor` columns, and the reversal test passed.

S2 and S3 contradict the DECISIONS sentence "known and unknown ids do the same SQL work". That property is what the builder's question 1 asks about, and nothing tests it. The body says "equal work shown structurally, as M3e-1b". 0009 has the same gap, so this is inherited.

Why it is P3 and not higher:
- AUTH-05 is not a hard rule.
- Credential ids are random values held by the authenticator, so an existence oracle on them is worth little.
- In 1d, the work after the lookup differs between a real id and a decoy anyway (DECISIONS [A]).

Cheap pins, for 1c or 1d or a test-only PR:
- A catalog test on `prosrc` of both lookup functions. It should check that `LOOP` comes before `INTO stored` / `INTO found`, and that the loop is not inside the `IF`.
- One assertion in `test_accounts_0015_reverses_and_reapplies…` that at 0014 the lookup role has no `user_factor` column privilege.

#### P3 #2 — forward notes for 1c and 1d (no action here)
- **1c: unique-key refusal.** A duplicate credential id (another agency's, or a retired one) is refused by the global key. Map that `IntegrityError` to the ordinary registration refusal. Don't let it surface as a 500 or a distinct message, and don't log the constraint detail: it echoes the id. The id is not secret, but this keeps responses uniform across tenants.
- **1d: length bound.** The function has no length bound of its own and HMACs whatever id it is given. 1d must call `lookup_credential` only with an id that has passed `_credential_id` (1 to 1,023 bytes). The route is pre-tenant and unauthenticated in effect.
- **1d: event volume.** Each lookup commits one `passkey.lookup` event, as `login.lookup` does. The 1d route should sit behind the same throttle as password sign-in, so the event table can't be flooded.
- **1d: the binding notes in DECISIONS.** The owner match with the pending session (an empty `allowCredentials` admits any discoverable credential), `own_transaction`, the strict `<` on `last_challenge_at` in the conditional update, and the stale-save replay test (PR 154 R1 P2 #2) are the conditions to check in the 1d review.

### Nits (no action required)
- `test_no_decoy_key_is_an_error_for_known_and_unknown_ids_alike` relies on `add_factor`'s all-zero 60-byte `BLOB` default, through `bytes(LOOKUP_BLOB_LENGTH)`. That is fine, but a one-word comment would save a reader the lookup.
