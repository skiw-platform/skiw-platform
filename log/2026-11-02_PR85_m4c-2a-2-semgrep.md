### Findings

### [P3] The new no-session regex fails open, with no error, on a SQL string longer than about 10,000 characters
- Category: security control (lint boundary), robustness
- Rule: TEN-09 (hard; this is its lint guard); UNI-04
- Evidence: `semgrep/tenancy-boundaries.yml:66` (the new regex, with nested `(?:(?!set_config\s*\().)*` groups inside a negative lookahead). In a scratch git repo, I wrote strings of `"SELECT 1, " × n` and then `set_config('app.x', %s, false)`, and ran `uvx semgrep==1.179.0`:
  - n = 900 (about 9,000 characters): flagged.
  - n = 1,000 to 4,000 (10,000 to 40,000 characters): **not flagged**, and Semgrep reports `errors: []`.
  - A 400-line PL/pgSQL-style body (about 19,000 characters) that ends in `PERFORM set_config('app.x', v, false);`: **not flagged**.
  - The Round 1 regex (`5175bb29`), run in the same pass under another rule ID, flags all of these.

  So this is a regression for long strings. It looks like the engine's backtrack limit, and Semgrep treats that as "no match".
- Failure scenario: a later migration writes a long guard function in one `RunSQL` string, more than 10 KB. The body has a session-level `set_config(…, false)`. `make lint` passes.
- Why only P3: today the longest string literal in `app/` is under 1,500 characters (I checked every `.py` file with `ast`). The real TEN-09 control is the M4c-4b runtime test that no `app.*` setting survives `COMMIT`.
- Required correction: a ≥ 12,000-character SQL string that ends in `set_config(…, false)` is flagged. Two ways:
  - (a) Add the Round 1 regex back as a second branch (`pattern-either`). It is linear and catches every flat `false` / `'f'` / `'false'` / `0` at any length. **My pick**, because it is the smallest change.
  - (b) Make the long branches atomic or possessive (`(?>…)`, `*+`), so the engine does not backtrack.

  Add a fixture `ruleid` line with a long string, or a note in DECISIONS with the limit if the fixture gets too large.
