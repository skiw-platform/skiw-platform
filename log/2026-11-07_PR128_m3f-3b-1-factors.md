### Findings

### [P2] The factor throttle checks, then verifies, then records, so parallel guesses all pass the check
- Category: material risk
- Rule: AUTH-06; spec Flow 5.1 (1)–(2) (5 fails / 15 min / account; second factor required)
- Evidence: `app/accounts/auth/factors.py:125` `throttle.factor_blocked(state.user_id)` is a plain `SELECT count` (`app/accounts/auth/throttle.py:122-133`). The code is checked at `factors.py:136` and the failure is recorded only afterwards (`factors.py:140`, `record_factor_failure` → `UPSERT`). Nothing reserves the attempt before verifying. The PR body and DECISIONS say "3c-1 reuses it for the sign-in code". Found by reading the code; I wrote no concurrency probe.
- Failure scenario: someone with the password and a login pending session (3c-1) sends N concurrent second-factor requests in one window. Every request reads `count < 5` before any failure is written, so all N codes get checked. Each window allows `limit + parallelism` guesses instead of 5. The TOTP check is cheap (no Argon2 to slow a burst), and ±1 skew gives 3 valid codes in 10⁶. A burst of about 1 000 per 15-minute window is about 0.3 % per window, which adds up over a day. In *this* PR the path is enrolment only: whoever holds an enrolment pending session already sees the secret, so nothing is gained here. That is why this is P2 and not P1.
- Why it matters: the docstring (`throttle.py:122-126`) and DECISIONS design call (2) state a per-user limit that holds against a password holder. It does not hold under concurrency, and the next PR builds the sign-in factor on top of it.
- Required correction: before verifying, make the attempt count atomic. For example, `UPSERT … RETURNING count` first, refuse as `limited` when the returned count is over the limit, and verify only when it is not. Or take a per-user advisory or row lock across check and record. Then decide whether a success may undo its own reservation (today a success is never counted, so a reserve-first design counts successes too; record the choice). Add a parallel test: K > limit concurrent wrong codes for one user give at most `SKIW_AUTH_FAILS_PER_ACCOUNT` `wrong_code` answers, and the rest are `limited`.
- Owner: builder
- Verification: in 3c-1's review, re-read `factor_blocked` / `record_factor_failure` and their callers, and run the parallel test as `skiw_app`.
- Disposition: deferred to M3f-3c-1 (`accounts.auth.second_factor.attempt`). 3c-1 must not merge with the check-then-record shape.
- Status: open

### [P3] The claim that two enrolments "take turns" is only tested sequentially
- Category: test gap
- Rule: plan §4 M3f row (no explicit requirement); module docstring `factors.py:18-19`
- Evidence: `test_a_second_confirmation_of_the_same_secret_is_refused` runs the two confirmations one after the other and copies one session, so both carry the same factor id (a PK clash would also stop a second insert). A mutant without `select_for_update()` would survive. Two *different* sessions that each called `begin_totp` (two browsers, two factor ids), confirmed in parallel, are not exercised.
- Failure scenario (if the lock is ever dropped): both read `invited`, both insert a TOTP row, and the user ends up with two live TOTP secrets plus recovery codes from whichever `generate` ran last. The other browser has already shown ten codes that no longer exist.
- Required correction: a live parallel test. Two sessions, two `begin_totp` calls, both confirm at once: exactly one `Enrolled`, exactly one `totp` row, ten recovery rows.
- Owner: builder · Status: open (optional; can ride with 3b-2)

### [P3] The pending deadline starts at the password step and enrolment never extends it (note for 3b-2)
- Category: material risk (UX)
- Evidence: `pending()` enforces `PENDING_UNTIL`, which `start_pending` sets to `SKIW_LOGIN_PENDING_MIN` = 5 min (DECISIONS M3b-1) when `redeem` succeeds. `begin_totp` does not refresh it. M3 has no QR code (plan §2), so the user types a 32-symbol secret by hand.
- Failure scenario: a user who is slow to type the secret gets `unavailable`. Their link is spent and their password alone signs nobody in, so they need a new invite from the operator (host-rebuild.md "Enrol a user" covers re-inviting).
- Required correction: in 3b-2, decide and document what the route does on expiry mid-enrolment (an operator re-invite, or a value), and say so in the runbook. While there, update the stale `host-rebuild.md:401` "until they enrol a second factor (M3f, M3g)" to v1.22 (TOTP required, passkey optional).
