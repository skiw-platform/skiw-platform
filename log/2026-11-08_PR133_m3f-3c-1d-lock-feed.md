## What changed
`second_factor.attempt` now feeds the factor soft-lock: every wrong code (TOTP or recovery), including one whose transaction then failed on leaving, calls `throttle.factor_failed(user, email, ip)`; a verified code calls `throttle.factor_reset(user)`. Ten wrong codes in a row, across any number of windows, lock both kinds and the right code for `SKIW_AUTH_LOCK_MIN` and write one `factor.locked` event. A fault before the comparison and an `unavailable` result touch neither the run nor the lock. The email comes from the `app_user` row read under `with_agency(state.agency_id)` (kept in `_Seen`), never from request input. `factor_failed` and `factor_reset` refuse an open transaction (shared `_outside_transactions`). The docstring and the runbook call the alert the M3 stand-in for the owner alert (owner Q4 (a)) and give a log check and a `security_event` query, and say there is no password change yet. DECISIONS "M3f-3c-1d". +209/−26 over 6 files (code about 40, tests 157, docs about 29). No route and no caller yet.

## Decisions worth keeping
- The run is fed by wrong codes in `attempt`, not by attempts in `factor_reserve`: a right code or a fault before the comparison must not count toward a lock. A guess whose commit failed still feeds the run, for the reason its count is kept.
- The lock's event email is the `app_user` row's, under `with_agency()`; the IP is `throttle.client_ip(request)`.
- A double-click on a right code costs one count; ten in a row lock the user. Accepted: a lock a guess can dodge is worse.
- The lock's "alert" is the M3 stand-in (an event and a warning nobody is sent) until the Q4 (a) alert path exists.

### Findings

### [P3] The runbook can't show whether locks repeat "for one user"
- Category: documentation
- Rule: UNI-16; reviewer §7
- Evidence:
  - The runbook says "if locks repeat for one user … tell Ying". Its checks, though, are a `grep` of a warning that names no user, and `SELECT count(*), max(at) FROM security_event WHERE kind = 'factor.locked'`, which counts every user together.
  - The event holds only `email_hmac` (`host-rebuild.md`, "Ten wrong codes in a row").
- Failure scenario: two users each locked once look the same as one user locked twice, so the operator can't apply the rule as written.
- Required correction: group the query by user, e.g. `SELECT encode(email_hmac, 'hex'), count(*), max(at) FROM security_event WHERE kind = 'factor.locked' GROUP BY 1 ORDER BY 2 DESC`. Then say that the hash can't be turned back into a name, so the operator learns who it is from the user (they will be the one locked out) or from Ying.
- Owner: builder · Status: open (optional; next runbook touch, e.g. 3c-2)

No prompt-injection text found in the PR body, commit message, code, tests or docs.

**Design calls [A], reviewer answers:**
1. **Feed the run from wrong codes in `attempt`, not from attempts in `factor_reserve`:** confirmed. Otherwise a right code or a fault would count toward a lock.
2. **A guess whose commit failed still feeds the lock:** confirmed, for the same reason the count is kept (PR 130 R1 P3 #1). If `factor_failed` itself raises on that path, the exception chains and the count still stands, which is the conservative outcome.
3. **A double-click on a right code costs one count:** confirmed. A lock that a guesser could dodge would be worse, and ten double-clicks in a row is not a realistic user.
