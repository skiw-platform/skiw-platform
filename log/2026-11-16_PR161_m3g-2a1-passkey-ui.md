### Findings

#### P2 #1 — after a failed passkey, keyboard focus is lost to the page body (A11Y-01)
- **Evidence:** the real-browser probe, both widths.
  - Focus the passkey button, press Enter, and let the ceremony fail. `document.activeElement` is then `BODY`, and one Tab lands on "Use a different account".
  - The cause: the button is disabled while busy (the focus fixup rule moves focus to the body), and the failure branch of `SecondFactor.passkey()` doesn't refocus. The code path and the 409 path both call `codeRef.current?.focus()`; this branch does not.
  - `StepUp.passkey()` has the same branch (inferred; the dialog isn't mounted yet).
- **Impact:**
  - Nothing is visibly focused after the failure.
  - A keyboard user loses their place: Chrome continues from the old button's position, and other browsers may restart at the top.
  - The message is still announced by the polite region, and nothing is lost.
- **Severity: P2,** dropped from the guardrail default of P1. A user can only own a passkey once M3g-2a-2 ships the add screen, so no real user can reach this path before then, and keyboard use still works.
- **Correction:** in both screens' failure branches (`failed`, 401, 400, 429, network), put focus back on a sensible control, for example the passkey button once it is re-enabled, or the code field as on 409. Add a vitest assertion and include it in M3g-2b's keyboard run.
- **Disposition:** deferred to **M3g-2a-2** (before any user can register a passkey). Owner: builder.

#### P3 #1 — enrolment drops the one-time recovery codes when the token can't be confirmed
- **Evidence:**
  - `EnrolSetup.confirm` shows the codes only if `rotated(...)` succeeds. If the success body has codes but no usable `csrf`, and the session read also fails, the page shows the generic error and the codes are gone; the server keeps only hashes. DECISIONS records this as a choice ("the person can regenerate them after signing in").
  - My mutant V3 (show the codes on 200 + `next` + codes, the pre-R8 rule) **survived** all 118 vitest. So no test pins the drop, and nothing depends on it.
- **Why I'd change it:** showing the codes sends no request, so it needs no token. The token problem only matters for the next POST, which the App's normal session read on Today already resolves. Regenerating needs a step-up, which is an avoidable extra step for a narrow fault.
- **Suggested fix:** show the codes whenever the confirm is exactly 200 + `next: "signed_in"` + a codes array, and reconcile the token separately (or on the next screen). Keep the "no protected POST on the old token" rule.
- **Severity: P3.** It's a pathological branch, it fails safe, and it's documented.
