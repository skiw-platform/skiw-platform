### [P1] The first response asks for `_absolute_expiry` before the plan creates it
- Category: defect
- Rule: spec D6; owner Q2 decision; UNI-02
- Evidence: plan:61 says `create_model_instance()` sets `_absolute_expiry` for a new row, while `get_expiry_age()` reads that attribute. In Django 5.2.17 `SessionMiddleware.process_response()`, a modified non-empty session calls `request.session.get_expiry_age()` **before** it calls `request.session.save()`; only that later save reaches `create_model_instance()`. The M2b test view at plan:134 creates exactly this first-save path.
- Failure scenario: an anonymous/new session is modified. Its first response reaches `get_expiry_age()` with no `_absolute_expiry` yet, so the request errors or computes a different deadline than the row later written. The first session cookie and the restart probe cannot be created reliably.
- Why it matters: this is the creation path for every first session and breaks the M2 acceptance flow before the non-sliding guarantee can be exercised.
- Required correction: define one idempotent “ensure absolute deadline” operation used by sync and async paths. The first call from `get_expiry_age()`/`get_expiry_date()` must create the deadline once; `create_model_instance()` must write that exact value, and a loaded store must reuse the row value. Add an HTTP-level frozen-clock case proving the first response's cookie deadline equals the new row's deadline, followed by the existing non-sliding saves/expiry checks.
- Owner: builder
- Verification: inspect the corrected call order; in M2b run the first-response, sync/async save, cycle and frozen-clock tests against the custom store.
- Status: open

### [P1] The plain-Django CSRF inventory still cannot detect a method change on an existing route
- Category: material risk
- Rule: spec T6; owner 2026-10-27 CSRF-gate decision; UNI-03
- Evidence: plan:95–101 correctly states that Django URL patterns expose no method metadata. For a plain route, the explicit test manifest itself declares `methods=["GET"]`; the proposed URL walk can prove only that the route name/path exists, not that production code still accepts GET only. The “safe” check then sends unsafe methods **without** a CSRF token and expects 403, which `CsrfViewMiddleware` returns before either a GET-only view's 405 or a mutating view's handler. The inventory therefore uses its own declaration as the only method source.
- Failure scenario: an existing plain view named `client-detail`, declared safe/GET-only in the manifest, later gains PATCH without changing its URL pattern or manifest. The route-set comparison is unchanged and the no-token PATCH still returns 403, so CI passes without moving the route into the cookie-auth mutation cases. If that view also has a non-source-visible exemption/alternate auth failure, the test can accept a non-CSRF 403 without proving the gate.
- Why it matters: Round 1 required a mechanically complete route/method inventory; route identity alone does not establish method completeness.
- Required correction: make accepted methods independently machine-readable in production code (for example a project route wrapper/attribute that both dispatch and the test consume), or make the manifest the production route-registration source rather than a test-only declaration. For every safe plain route, send a **valid CSRF token and fully authenticated fixture** for each unsafe verb and require 405; for every cookie mutation, require the valid-token request to reach the expected handler/validation outcome and verify missing/wrong/cross-origin failures are specifically CSRF rejections. The planted regression must also change an existing safe route's accepted methods, not only add a new route.
- Owner: builder
- Verification: modify an existing safe route to accept a parameterised PATCH without updating the inventory and show the completeness gate fails; then restore it and run all cases.
- Status: open
