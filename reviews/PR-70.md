### [P1] The 12-hour “absolute” session lifetime can silently become sliding
- Category: spec/guardrail mismatch
- Rule: spec D6; owner Q2 decision; UNI-02
- Evidence: plan:91 says M2 “sets `expire_date` from the absolute value,” but defines no immutable session start/absolute-expiry field or fixed-datetime `set_expiry()` operation. The M2 tests at plan:111–142 contain no clock-controlled assertion that later session saves leave the original absolute deadline unchanged. In installed Django 5.2.17, `SessionBase.get_expiry_date()` uses `timezone.now() + SESSION_COOKIE_AGE` when no fixed `_session_expiry` datetime exists; an integer passed to `set_expiry()` is documented and implemented as inactivity duration.
- Failure scenario: a session created at 09:00 is modified at 20:30. A normal save recomputes `expire_date` as “now + 12 h,” keeping the session valid until 08:30 the next day rather than expiring at 21:00. Frequent mutations can extend it indefinitely, violating D6 and the owner's Q2 choice.
- Why it matters: absolute lifetime is a session-security boundary, distinct from the idle timeout deferred to M3.
- Required correction: specify the non-sliding mechanism (for example, store a fixed absolute-expiry datetime when the session is first created/login rotates it and preserve that value on every save). Add a frozen-clock live test that creates a session, advances close to 12 hours, modifies/saves it, proves the database and cookie deadline did not move, and proves the session is rejected after the original deadline. State how login/cycle/flush creates a new deadline and how M3's idle policy composes with it.
- Owner: builder
- Verification: inspect the revised design and test; in M2d, run the clock-controlled regression against the custom DB store.
- Status: open

### [P1] The CSRF behaviour gate has no complete route/method inventory
- Category: material risk
- Rule: spec T6; owner 2026-10-27 CSRF-gate decision; UNI-03
- Evidence: plan:93 says the test “walks every URL pattern” and then tests each route that accepts POST/PUT/PATCH/DELETE, but it does not define how the walk discovers accepted methods, constructs parameterised paths and valid-enough requests, or proves inventory completeness. Django 5.2.17 `URLPattern` has no HTTP-method metadata, and `require_http_methods()` wraps the view without attaching the allowed-method list. A token-auth exception list alone does not inventory cookie-auth mutations.
- Failure scenario: a future cookie-auth `PATCH /clients/<uuid>` route cannot be instantiated by the generic walker, or its method is not discoverable, so the route is skipped. It can then bypass CSRF while the gate remains green; sending blind POSTs to GET-only routes is also not proof because `CsrfViewMiddleware` rejects unsafe methods before the view's 405 logic.
- Why it matters: this gate is the owner's explicit replacement for a source-only `csrf_exempt` scan and is meant to prove every cookie-auth mutation, including django-ninja routes.
- Required correction: define one mechanically complete inventory contract, such as a generated manifest from django-ninja operations plus an explicit manifest for plain Django views, with route name, method and request/path fixture. Make CI compare the discovered mutating-route set with the union of cookie-auth cases and the reviewed token-auth list; fail on additions, removals, unresolved parameters, duplicate identities or a token-auth route that accepts a session cookie. Each cookie-auth case must show valid-token success (or the expected downstream validation response) and missing/wrong/cross-origin token refusal.
- Owner: builder
- Verification: plant one parameterised cookie-auth mutation that bypasses CSRF and show the gate fails; restore protection and show all inventory and behaviour cases pass.
- Status: open
