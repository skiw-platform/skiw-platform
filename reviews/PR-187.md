#### [P2] The race worker can keep pytest alive after the startup timeout

- **Category:** defect.
- **Rule:** M4r-1h race harness and DECISIONS M4r-1h-i choice 1, bounded failure and cleanup.
- **Evidence:** `app/accounts/tests/test_roles_races_live.py:59` starts a non-daemon thread. At line 65 it enters the Django transaction and opens its DB connection before it sets the server timeouts at line 66. The start wait and join are bounded at lines 85 and 119, but neither cancels a pending connection attempt. The connection config at `app/config/env.py:85` supplies no startup timeout.
- **Failure scenario:** The test database accepts the second connection but stalls while negotiating it. The start wait and join expire and the test fails, while the worker remains blocked before the SQL timeouts can take effect. Python waits for that non-daemon worker on exit.
- **Impact:** A stalled database can turn a bounded race failure into a suite or CI timeout. The SQL timeouts already cover the ordinary advisory-lock wait. This finding is limited to the test harness.
- **Required correction:** Bound the worker's database startup and make the timeout/teardown path terminate reliably. Keep the separate session and existing advisory-lock observation.
- **Owner:** builder.
- **Verification:** Exercise a controlled second-session startup stall and verify that the test process exits within a bounded interval. Rerun the 25 live race cases.
- **Disposition:** before merge.
- **Status:** open.
