### What I checked
- **User verification, origin and RP ID.** The library's source shows UV defaults to off in both verify calls; the code sets `require_user_verification=True` in both, and `userVerification: required` in both sets of options. The expected origin and RP ID always come from `settings.SKIW_WEBAUTHN()`, never from the request.
- **Algorithms.** Pinned to EdDSA, ES256 and RS256 in the options and at registration verify. py_webauthn 3.0.1's own default is the same three (`generate_registration_options.py:27`), so the pin only matters if a later library version widens the default. That is still worth having, because the library knows RSA-SHA1 (`algorithms.py:68`).
- **Ids.** `rawId` is strict base64url, round-trip canonical, 1 to 1,023 bytes, and equal to `id`. The attested id must equal `rawId` at registration (`verify_registration_response` does not compare them). An assertion must name the stored credential, and mutant P13 (dropping that comparison) is killed.
- **Sign count.** Both-zero is accepted, as WebAuthn allows; otherwise the count must rise (the library's rule). Tests cover 5→6, 0→3, 5→5, 5→4, 5→0 and a counter that stays zero.
- **`SessionStore.take`.** It locks the row, unseals, removes the value, re-seals and commits in its own transaction, and refuses to run inside another one. The in-memory copy is dropped, so this request's own end-of-request save cannot re-add the value. `take_challenge` consumes the challenge first and checks it afterwards (mutant P7, checking before taking, is killed). Four threads racing on one row produce one winner, and with the save removed (mutant P16) 10 tests fail.

Versions and licences match DECISIONS. `uv lock --check` passes; 21 new wheel and sdist hashes are in the lockfile. Holding `cbor2` at 6.1.5 rather than a six-day-old 6.2.1 is a sensible precaution, but only the lockfile holds it: a `uv lock --upgrade` would move it. ### Findings

### [P2] #1 A malformed registration raises `KeyError` instead of being refused
- Category: guardrail mismatch (UNI-03) and a wrong claim in DECISIONS
- Rule: UNI-03; DECISIONS "M3g-1a-2" (4): "py_webauthn 3.0.1 wraps every parse and check failure in a `WebAuthnException`, so only that is caught"; `test_a_malformed_registration_is_refused_without_raising`
- Evidence: I wrote a byte-level fuzz probe (scratch only) over both verify calls: about 2,000 registrations and 2,000 assertions per seed, four seeds, with bit flips, truncations, insertions and odd types. **`KeyError` escaped `verify_registration`** from `webauthn/helpers/decode_credential_public_key.py` lines 67, 68, 91 and 93. The library indexes the COSE map (`decoded_key[COSEKey.X]`) before its own "missing x" checks. Deterministic reproducer: a registration whose COSE key is `{1: 2, 3: -7, -1: 1}` (EC2 with no `x` or `y`) raises `KeyError: <COSEKey.X: -2>`. Assertions never raised (the stored key is the app's own). **No changed assertion was ever accepted**: every assertion the fuzz accepted was a mutation that left the bytes unchanged, which I checked by equality on four seeds.
- Failure scenario (from 1c on): a hand-crafted registration from a signed-in user's browser makes the add-passkey route raise. The result is a 500 and a logged traceback instead of the uniform refusal. It fails closed: nothing is stored, and the challenge was already consumed.
- Why P2, not P1: a failed guardrail rule defaults to P1. The impact is isolated: nothing calls these primitives yet, the failure is closed (no passkey is accepted), only a signed-in user can reach registration, and the challenge cannot be retried.
- Required correction: make "every refusal is `None`" true. Either catch `(WebAuthnException, KeyError, TypeError, ValueError)` around both library calls, or `Exception` with a one-line reason (a parser boundary on untrusted input; ruff's broad-except rule (BLE) is not selected). Add the COSE-key-without-coordinates case to the malformed-registration test, and correct the sentence in DECISIONS.
- Owner: builder · Verification: the reproducer returns `None`; my fuzz probe reports nothing escaping; a mutant that restores the narrow catch fails the new test.
- **Disposition: before merge.** 1c builds directly on this contract, and the builder asked about this exact catch.
- Status: open

### [P2] #2 A stale save writes a taken challenge back
- Category: material risk (recorded by the builder; now reproduced)
- Rule: AUTH-03/D7 replay resistance; DECISIONS "M3g-1a-2" Risks
- Evidence: a live probe (scratch only). Request B loads the session, which holds a `stepup` challenge. Request A takes the challenge. B then saves the session; I stood in for the wrapper's `SEEN_AT` bump with one changed key. A second take now **returns the same challenge**. This is not an exotic race: `wrapper.py:167-168` writes `SEEN_AT` on an authorized request at most once per `SEEN_STEP`, so any signed-in session that makes parallel API calls saves its whole stale copy. That makes the `stepup` and `register` purposes the likely ones. For `login`, the session key is cycled at sign-in (`login.py:91`), so a write-back lands on a row that is about to be deleted.
- Impact: a zero-counter passkey's assertion could be used twice within one session and the 5-minute deadline. The replay needs the assertion itself, which leaves only the victim's browser over TLS, so the practical risk is small. It still breaks "one challenge, one use".
- **Disposition: deferred to M3g-1b and M3g-1d**, as the builder planned. 1b's migration must include the challenge issue-time column on the factor row. 1d must compare it in the same conditional update as `sign_count`, and must add a live test of exactly this scenario: stale save, then replay of a zero-counter assertion, refused. Note for 1d: comparing issue times means a challenge issued earlier in another session and used after a later one is refused. That fails closed, but it should be named in 1d's DECISIONS entry.
- Status: accepted for now (the owner accepts by merging); to be verified in the 1d review.
