### [P3] HMAC values under `tenant_source_key` carry no key version, so a key rotation can break them
- Category: design gap
- Rule: spec T16 (key rotation); UNI-02
- Evidence: plan §3 M3f: recovery code `secret_ct` = "HMAC-SHA-256 under `tenant_source_key` (label `skiw-recovery-v1`)". §3 M3h: `evidence_mac` under the same key. §3 M3c: throttle `key_hmac`. The blob format in M3b carries a 2-byte version, and M2c seals carry `v<n>`. These three values carry none. The plan copies the M2c MAC input layout ("length-prefixed like M2c") but not the `v<n>:` prefix that M2c stores beside the MAC (`app/accounts/source_key.py:48`).
- Failure scenario: the operator rotates `tenant_source_key` to `v2` (T16). Every stored recovery code now fails, so a user who lost their passkey cannot recover. Every old `auth_stepup` row fails its MAC. Throttle counters reset (low impact).
- Required correction: in M3f and M3h, store the key version with each value (or verify under each listed version), and add a rotation test: a value made under `v1` still verifies when `v1` and `v2` are listed. For throttle keys, record that a rotation resets the counters.
- Owner: builder
- Disposition: deferred to M3f (recovery codes) and M3h (`evidence_mac`)
- Verification: rotation tests in those PRs.
- Status: open

### [P3] The revocation compare uses two clocks and `≥`, so a re-issued session can reject itself
- Category: ambiguity
- Rule: AUTH-07
- Evidence: plan §3 M3d: reject when "a user-wide row has `revoked_at ≥ _skiw_auth_at`". §3 M3f and M3h: a factor or password change "writes a user-wide revocation and re-issues the current session". The plan does not say whether `revoked_at` comes from Postgres `now()` (the transaction start) or from Python, nor which clock sets `_skiw_auth_at`.
- Failure scenario: `revoked_at` comes from the Python clock and `_skiw_auth_at` of the re-issued session is set in the same millisecond, or the DB clock runs ahead of the app clock. The re-issued session matches `revoked_at ≥ _skiw_auth_at` and the user is logged out right after a password change. With the clocks the other way, an old session issued just before the revoke survives.
- Required correction: in M3d, name one clock source for both values, and make the re-issued session's `_skiw_auth_at` strictly later than the marker (for example, set it from the marker row's `revoked_at` plus one tick, in the same transaction). Add a test with a frozen clock where both values are equal.
- Owner: builder
- Disposition: deferred to M3d
- Verification: M3d test.
- Status: open

### [P3] The enrolment link's single use and the account state are not fully defined
- Category: ambiguity
- Rule: AUTH-08
- Evidence: plan §3 M3e: the token covers "a fingerprint of the current `login_blob_ct` … so it stops working once used (the blob changes)". The plan does not say when `status` moves from `invited` to `active`, and the tests ("works once, expired, tampered, reused") have no concurrent case. Recovery codes do have one (M3f: "two parallel uses → one success").
