### Findings

### [P1] The fail2ban policy can report success while fail2ban remains stopped
- Category: defect.
- Rule: spec §8.4 H2; M1 plan §3 M1f / G7(b).
- Evidence: `infra/host/skiw_host/apply.py:253` only enables the fail2ban unit; `apply.py:56` uses `systemctl try-restart fail2ban`. The only unconditional service start is SSH (`apply.py:255`). Package installation is skipped when fail2ban is already installed (`apply.py:243–252`). The systemd documentation confirms that enable does not start a unit and try-restart leaves inactive units inactive: [systemd systemctl documentation source](https://github.com/systemd/systemd/blob/main/man/systemctl.xml).
- Failure scenario: fail2ban is already installed but stopped (for example, from a prior allowlist setup). Switch host policy to fail2ban. apply installs the enabled SSH jail and opens the SSH port to all sources, but only enables/try-restarts the inactive unit. It returns 0 and clears the pending file without activating the selected protection. A later no-change apply also does not start it.
- Verification performed: using the PR's Rig with an explicit service-state runner implementing documented start/restart/try-restart semantics, an allowlist → fail2ban switch returned 0 with fail2ban still inactive. Its only fail2ban commands were enable and try-restart. This is a semantic runner probe, not a claim of native systemd execution.
- Why it matters: the selected security policy is absent even though the installer reports success. Package post-install auto-start is not a sufficient convergence mechanism for an already-installed package.
- Required correction: when the selected policy is fail2ban, ensure its service is active, including when installed but stopped and when no config file differs. Keep this separate from the allowlist cleanup, where starting fail2ban is unnecessary. Add service-state regressions rather than only command-list assertions.
- Owner: Builder.
- Verification: with all packages installed and fail2ban initially stopped, selecting fail2ban must activate it before successful completion; stopping it after a successful run and applying unchanged files must recover it. Verify the allowlist transition and failed-start retry too.
- Status: open.

### [P2] A newer installed Docker version cannot converge to the reviewed pin
- Category: defect.
- Rule: M1 plan §3 M1f idempotent pinned-package installation; spec §8.4 H1; package drift/retry contract in `apply.py:233–252` and the host runbook.
- Evidence: `infra/host/skiw_host/apply.py:249–252` selects every version mismatch but invokes `apt-get install -y --no-install-recommends` without handling downgrades. `infra/host/tests/test_apply.py:345` tests an older installed Engine version only. [APT implementation](https://raw.githubusercontent.com/Debian/apt/main/apt-private/private-install.cc) rejects a downgrade with Assume-Yes unless allow-downgrades is set; see also [APT manual](https://manpages.debian.org/bookworm/apt/apt-get.8).
- Failure scenario: a host has a Docker Engine/CLI or Compose plugin newer than the committed pin (manual drift or a previously applied newer pin). apply selects the pinned lower version, APT exits 100, and apply exits 1 after installing host files. Repeating the same command fails identically; priority 1001 selects a downgrade but does not authorize APT's noninteractive downgrade operation.
- Verification performed: in a disposable, offline Debian container from cached image `d74eeac9a635`, installed an inert local package at 2.0 and requested local 1.0 using the PR's APT flags. APT printed “Packages were downgraded and -y was used without --allow-downgrades.” and exited 100. The same operation with the explicit flag exited 0. No host package or existing container was changed. The PR's Rig separately confirmed that newer Docker versions produce the same install command without the flag; its fake APT falsely succeeds.
- Why it matters: version drift recovery is incomplete. P2 rather than P1 because this case fails closed, is limited to hosts already carrying a newer version, and does not silently accept an unreviewed package or corrupt data.
- Required correction: implement a narrowly scoped path for returning the explicitly pinned Docker packages to their reviewed versions; keep unrelated OS package installation separate. Extend tests to both older and newer installed versions and a correct-version no-op, modelling APT's refusal rather than unconditional fake success. Update the runbook if the recovery procedure changes.
- Owner: Builder.
- Verification: newer-version drift converges successfully to each exact pin; matching versions run no APT; an installation failure remains retryable with its pending reloads intact.
- Disposition: before merge.
- Status: open.
