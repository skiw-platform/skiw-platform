### Findings

### [P2] A password change does not stop a login already past the password step with the old password
- Category: material risk (security)
- Rule: AUTH-07 (intent: an old credential stops working at the change); spec §9 M3h done-when (met literally)
- Evidence:
  - `factors.pending` (`factors.py:77-89`) checks only the pending deadline (`PENDING_UNTIL`).
  - `second_factor.attempt` never consults `session_revocation`.
  - `login()` then stamps `AUTH_AT = now`, later than the user-wide marker, so the new session survives it.
  - The builder states the gap in DECISIONS "M3h-4", "Accepted residue (follow-up offered)", and in the runbook bullet "Change the password".
- Failure scenario:
  - Someone has the user's old password and a second factor: a TOTP code phished in real time (the T5 risk the owner accepted), or a leaked recovery code.
  - That person passes the password step. Within the next 5 minutes (`SKIW_LOGIN_PENDING_MIN`), the user, suspecting the compromise, changes the password.
  - The attacker still completes the second factor and gets a fresh session that the change never revokes.
- Why it matters: a password change is the user's own response to a suspected compromise, and here it does not end an in-flight login that used the old password.
- Why P2 and not P1:
  - The window is at most 5 minutes and covers only a login already in flight.
  - The attacker also needs the second factor.
  - Every session that exists at the change is revoked, so AUTH-07's text is met.
- Why I still raise it: the builder recorded it as "accepted", but no owner acceptance is on record ("Decided by: builder"), and the fix is small.
- Required correction: in `second_factor.attempt`, before counting, refuse the pending state as `unavailable` when a user-wide marker for that user has `revoked_at >= pending start`. The start is `PENDING_UNTIL − SKIW_LOGIN_PENDING_MIN`, or store `PENDING_AT` in `start_pending`.
  - That one check covers M3h-5 and M3h-6 too, since every credential change writes the same user-wide marker.
  - Add a live test: password step, then a password change, then the second factor answers `unavailable`, and a fresh login with the new password still works.
- Owner: builder (or the owner, if they would rather accept it: record it in DECISIONS as an owner decision)
- Verification: the new live test, plus a mutant that drops the check being killed.
- Disposition: deferred to M3h-5 (the next credential-change PR, which needs the same protection)
- Status: open

### [P3] No test proves the CSRF token changes after a password change
- Category: test gap
- Rule: AUTH-13 (server half), DECISIONS "M3h-4" ("`login.reissue` … `rotate_token`")
- Evidence: in a scratch copy I removed `rotate_token(request)` from `login.reissue`. **The mutant survived:** all 21 tests in `test_logout_password_live.py` passed. `test_a_change_…` checks only that the body has a `csrf` key (`:128`). Logout has a real rotation test (`test_logout_rotates_the_csrf_token_and_the_old_one_is_refused`).
- Failure scenario: a later edit drops the rotation. The re-issued session keeps the pre-change CSRF token (`CSRF_USE_SESSIONS = False`, so the cookie is separate from the session key), and nothing fails.
- Required correction: mirror the logout test for a password change. The returned `csrf` differs from the old token, and the old token gets 403 `token-invalid`.
- Owner: builder · Disposition (P3): optional, M3h-5 (which also calls `reissue`) · Status: open

### [P3] The `revoked_at` time is the transaction's start, not the statement time the docstrings say
- Category: documentation (no defect)
- Evidence:
  - `revocation_model.py:24`: `revoked_at = models.DateTimeField(db_default=Now())`. Django's `Now()` is PostgreSQL `CURRENT_TIMESTAMP`, the transaction's start.
  - `revoke.py` module docstring: "`revoked_at` is the database's statement time".
  - `login.reissue` docstring: "after the marker's statement time".
- Consequence (correct, but worth stating):
  - Inside one transaction the order of `mark(None)` and `reissue` cannot matter. A mutant that swaps them survived (21/21), and is an equivalent mutant.
  - The "marker window" in DECISIONS (a sign-in completing during the change is not revoked) lasts for the whole transaction, including the wait on `hold`'s row lock, not just milliseconds. The transaction is short (Argon2 runs outside it), so the window is still small.
- Required correction: say "transaction start time" in both docstrings and in DECISIONS' window note.
- Owner: builder · Disposition (P3): optional · Status: open

### Design calls [A], reviewer answers
1. **`hold` before every re-issue (the resurrection race): confirmed.**
   - `SELECT … FOR UPDATE` on the user's row, then `revoked()` as a fresh statement. Under READ COMMITTED, B sees A's committed marker after A releases the lock.
   - The barrier test is real: my mutants that drop `FOR UPDATE` or the `revoked()` check each fail exactly one test, the race test, and it passed 5 of 5 repeated runs (no flakiness seen).
2. **`reissue` keeps the absolute deadline: confirmed.** `cycle_key()` carries the stored data, `start_new_lifetime` is never called, and the Semgrep rule is unchanged. The new `AUTH_AT` is the app clock, read after the transaction began, so the session outlives its own transaction's marker (see P3 #2 on why the order is safe).
3. **`own_transaction` and Argon2 outside a transaction: confirmed.**
   - Wrapper steps 1–4 are unchanged and commit first. The verify and the new hash run with no transaction open.
   - The one write transaction is `hold`, then the blob swap conditional on `login_blob_ct = sealed` (409 otherwise), then the user-wide marker, then `reissue`.
   - A concurrent login's rehash (`password_step._rehash`) is also conditional on the blob it opened, so a password set meanwhile wins in both directions. I checked this because an unconditional rehash would undo a change.
4. **Throttle reuse [A]: confirmed.**
   - It is the login form's own account, IP and lock keys, so a session thief gains nothing over anyone who knows the email.
   - The check-then-record pattern (`blocked`, then `record_failure`) is the same as the login password step's, not a new gap.
   - One Argon2 verify per attempt, with `dummy_verify` when the blob does not open or names another user. A short new password returns before any count or Argon2 and reveals nothing about the current one.
5. **No step-up for password change: confirmed.** D7's step-up list does not include it, and plan §3 M3h says "current password required".
6. **Size (+488 over 450): accepted.** Logout alone would ship `hold` and `reissue` with no caller and no way to test the race or the deadline.

### Code read (beyond the self-check)
- **Logout.**
  - The marker and `flush()` (the row delete) commit together in the wrapper's transaction. The empty session makes the middleware delete the cookie.
  - A re-inserted row is refused by the per-key marker (mutant without the marker: killed).
  - Body exactly `{}` through `wrapper.nothing`.
- **Failure inside the change transaction.** Django's `SessionMiddleware` does not save on a 500. A fault after `cycle_key()` therefore rolls back the new row, the old row's delete, the blob and the marker together, and the user keeps the old, unrevoked session and the old password. That state is consistent.
- **`hold` returns false** (revoked meanwhile, or user disabled): the session is flushed in the same transaction and nothing else is written.
- **`reissue`'s own per-key marker** is redundant after the user-wide one, but cheap, and it protects a future caller that forgets the order. A mutant that drops it is killed, by the "old row put back by SQL" case.
- **Spec M3h done-when:** logout leaves no usable row and a re-insert is rejected (tested); password change revokes the other sessions (tested). Met.
- **Audit:** no `audit_event` for a password change. That is consistent with plan §1 item 8 (audit events need M5; M3 writes `security_event` only); `account.locked` still fires at the lock.
