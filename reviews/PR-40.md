### [P1] Bootstrap exports the host superuser password into the psql environment
- Category: guardrail mismatch
- Rule: spec §8.4 H4; PROJECT.md §8 host-secret-store constraint (UNI-08 mapping).
- Evidence: `infra/host/skiw_host/bootstrap_db.py:33–35` constructs `PGPASSWORD="$(cat /run/secrets/postgres_password)" exec psql`; `apply` executes that shell at lines 85–94. H4 explicitly prohibits secrets in environment variables. The mock runner in `infra/host/tests/test_bootstrap_db.py:81–96` inspects the unexpanded argv/stdin, so it cannot detect the child process environment.
- Failure scenario: every host apply expands the real postgres password from the mounted secret file and exports the plaintext value to psql, even though only SCRAM verifiers appear on SQL stdin.
- Why it matters: this violates the approved storage/transport boundary for the bootstrap superuser credential. Absence from argv and Docker's configured environment is insufficient. PostgreSQL also discourages PGPASSWORD because process environments can be observable: [PostgreSQL 17 environment variables](https://www.postgresql.org/docs/17/libpq-envars.html).
- Required correction: authenticate without putting the password in any process environment or argv; use an appropriately protected file-based libpq credential mechanism, or an explicitly approved local-socket authentication design. Preserve the planned HBA restrictions and fail closed. Add a test that executes the authentication wrapper and checks the actual child environment as well as argv/output.
- Owner: Builder.
- Verification: rerun the wrapper with generated credentials and a child-process probe; no plaintext credential in its environment, argv, output, or persisted unprotected files; verify real socket authentication with the M1e-2 HBA design.
- Status: open.

### [P1] Successful role bootstrap preserves forbidden app-role memberships
- Category: defect
- Rule: TEN-02 (hard), spec §4.2 TEN-02 row / §8.4 H6, plan M1e closed role set.
- Evidence: `infra/host/db/roles.sql:8–17` accepts an existing `skiw_app` and resets attributes without revoking or rejecting memberships. Its only membership operation is the backup GRANT at line 24. The new role-set test checks an initially clean database (`app/tests/test_live_role_set.py:46–48`); it does not exercise bootstrap on a role with an unexpected membership.
- Failure scenario: an existing database has `GRANT pg_read_all_data TO skiw_app`. Running this PR's exact roles.sql exits 0, and the membership survives. In an isolated container using the repository's pinned PostgreSQL 17.11 image, I seeded that grant, applied roles.sql, observed `pg_has_role(..., 'MEMBER') = true`, then successfully executed `SET SESSION AUTHORIZATION skiw_app; SET ROLE pg_read_all_data` (exit 0, current_user = pg_read_all_data).
- Why it matters: a successful bootstrap does not establish the stated no-membership role boundary; predefined data-role access can defeat the intended table-level restrictions. The same unchecked mechanism can preserve membership in other privileged roles. ALTER ROLE does not remove memberships: [PostgreSQL 17 ALTER ROLE](https://www.postgresql.org/docs/17/sql-alterrole.html).
- Required correction: before reporting success, reconcile forbidden memberships or refuse atomically with a clear, non-secret diagnostic. Validate the permitted membership set, particularly zero memberships for skiw_app and only the intended backup membership. Do not silently drop unrelated roles or loosen grants.
- Owner: Builder.
- Verification: an isolated live test seeds an unexpected app membership, runs the actual bootstrap SQL, and proves it either removes the grant or refuses without committing a misleading partial success. A clean run and a clean second run must still pass.
- Status: open.
