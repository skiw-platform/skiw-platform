### [P2] The new runbook step can't be checked, and an emergency rotation silently voids every code
- Category: material risk (runbook, §7)
- Rule: UNI-16; reviewer §7 ("no checks that can't actually be run")
- Evidence: `docs/runbooks/host-rebuild.md:131-133` says "Keep the old version listed until every user
  has regenerated their codes". But `secret_ct` holds 32 bytes with no version, and `user_factor` has no
  creation time (`factor_model.py`). So no operator can tell when that point has been reached. The
  emergency path in the same section ("Removing the old version at once … wanted effect when the key may
  have leaked", lines 127-129) voids every user's recovery codes, with no signal to the app or to the
  users.
- Failure scenario: the key is suspected leaked, the operator follows the runbook, and the old version is
  removed. Weeks later an adviser who lost their phone types a printed code. It is refused, and nothing
  told them to regenerate. They then need an owner-performed factor reset (Flow 5.1).
  - A leak of `tenant_source_key` alone does not even endanger the codes: without the code itself, 80
    bits can't be brute-forced from the MAC. So voiding them is pure collateral damage.
- Answer to the PR's question: acceptable **for now**. No host has any recovery code, because there is no
  route until M3f-3 and M3i. It must be closed before any user can generate codes.
- Required correction (either one):
  - (a) Store the signing version in `secret_ct`, e.g. a 1-byte prefix (33 bytes). That fits the
    per-kind length CHECK that M3f-3 adds anyway. The runbook then gives an executable count:
    `SELECT count(DISTINCT user_id) … WHERE kind='recovery' AND get_byte(secret_ct,0)=<old>`.
  - (b) Keep 32 bytes, and make the runbook's emergency path say explicitly that every recovery code
    becomes void and that each user must be told to regenerate. Replace "until every user has
    regenerated" with a step an operator can actually run.
  - Plan A5 makes the recovery format a builder proposal for the owner and reviewer, so (a) needs no spec
    change. I recommend (a).
- Owner: builder.
- Verification: in M3f-3's diff, either the version prefix with its live test plus the runbook count
  query, or the reworded runbook.
- Disposition: deferred to M3f-3 (it must land before any route can generate codes).
- Status: open.

### What was checked (no finding)
- **Matches plan M3f line 100:**
  - 10 codes of 16 Crockford base32 symbols each (32^16 = 2^80, tested), drawn with `secrets.choice`.
  - One `user_factor` row per code.
  - HMAC-SHA-256 under `tenant_source_key`, label `skiw-recovery-v1`, over the length-prefixed user id
    and code.
  - Use is one `DELETE … RETURNING`.
  - Regeneration replaces all ten.
- **Concurrency:**
  - In READ COMMITTED, a second `DELETE` waits on the row lock, re-checks and finds no row. The live test
    shows 10 parallel uses give 1 success.
  - `generate` takes `FOR UPDATE` on `app_user` first, so parallel regenerations queue. Each later
    `DELETE` gets a fresh snapshot and sees the earlier commit, leaving exactly 10 rows (tested).
  - A use racing a regeneration either deletes the old row first or waits and then finds nothing. Both
    are correct.
- **Isolation (TEN-08/09):**
  - Scope is RLS plus `user_id`, and the MAC binds the user id.
  - A cross-user code, a cross-agency code, a MAC copied to another user and a generate for agency B (RLS
    WITH CHECK and composite FK) are all refused, and nothing changes (live, as `skiw_app`).
  - Both functions raise outside an atomic block (tested).
- **Normalisation (UNI-03):**
  - The length bound comes before `isascii()`, and `isascii()` before `upper()`. That order closes the
    `ı`→`I` path.
  - The `Untouchable` test proves no work is done on over-long input.
  - Tab, newline, Unicode hyphen, full-width and Cyrillic input are refused.
- **Keys:**
  - The newest version signs and every listed version matches. The live rotation test covers v1 working
    under v2, refused once v1 is removed (not deleted), and new codes signed by v2.
  - The label is prefix-free against the session and throttle labels. That matters because the throttle
    HMACs have no length prefix (tested).
- **Constant-time compare:** I accept the reasoning. Equality in Postgres on a keyed MAC leaks nothing
