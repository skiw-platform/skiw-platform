### Findings

### [P1] The pg_restore list process is not a whole-stream consumer

- **Category:** objective defect.
- **Rule:** H3 step 4 / plan M1g: a usable pre-migration dump must succeed before migration; UNI-03 external-tool contract.
- **Evidence:** `infra/host/backup/predeploy/predeploy.py:52–58,80–89` writes every archive chunk to `pg_restore --list`, treating its early exit as failure. `test_predeploy.py` supplies an in-memory Sink that consumes all input, unlike the real tool. Code/decision comments say the list command must read the stream whole.
- **Failure scenario:** a valid archive larger than the effective pipe/transport buffers. Reviewer generated a 5,882,234-byte synthetic custom-format archive using the exact pinned PostgreSQL 17.11 image. Running the production `stream()` against real `pg_restore --list` in a disposable container raised BrokenPipeError after the source had advanced 4,653,056 bytes; pg_restore itself exited **0** and produced a 454-byte TOC. The remaining archive was not forwarded to the second sink. The precise buffer threshold is not the relevant contract: a successful TOC reader may stop early.
- **Why it matters:** ordinary nontrivial backups fail, so pending-migration deployments cannot proceed. The small native sample and permissive fake miss this.
- **Required correction:** use a validation/fan-out arrangement compatible with real pg_restore consumption, preserving the complete encrypted stream and failure checking without assuming `--list` consumes table data. If claiming whole-archive validation, actually validate that content. Correct the fake and the corresponding code/decision description.
- **Owner:** Builder.
- **Verification:** real pinned pg_dump/pg_restore with an archive larger than pipe buffers must complete; decrypt/validate the complete encrypted output and compare contents. Cover genuine validator failure and early successful TOC completion. [PostgreSQL documents --list as a TOC listing](https://www.postgresql.org/docs/17/app-pgrestore.html), not a full data read.
- **Status:** open.

### [P1] Hash the encrypted dump without loading it all into memory

- **Category:** objective defect / resource failure.
- **Rule:** H3 dump-before-migration task correctness; H1 configured resource limits.
- **Evidence:** `predeploy.py:125` calls `hashlib.sha256(tmp.read_bytes())`. Compose bounds backup memory (`compose.yml:155`); staging is 128 MiB and production/CI 256 MiB in the env files.
- **Failure scenario:** encrypted dump exceeds available process memory, despite the earlier copy being streamed. In a disposable Python container with 128 MiB cgroup memory and a 96 MiB address-space allowance, reviewer substituted only the tool-writing stage with a synthetic 256 MiB sparse output. The real `main()` raised uncaught MemoryError at the checksum step and left `.20261022T092417Z.dump.age.tmp` (268,435,456 bytes). This isolates hashing from the already demonstrated pipe defect; it is not an end-to-end backup result.
- **Why it matters:** legitimate database growth blocks releases; memory failure also violates the promised partial-output cleanup. Raising the container limit just moves the threshold.
- **Required correction:** calculate the ciphertext hash incrementally with bounded reads. Preserve failure cleanup and avoid retaining a whole archive anywhere in Python memory.
- **Owner:** Builder.
- **Verification:** a synthetic encrypted file larger than the container's memory budget hashes successfully with stable bounded memory; compare its digest with an independent streaming checksum. Existing cleanup/error tests must still pass.
- **Status:** open.

### [P1] Make backup publication durable before returning the success line

- **Category:** material data-recovery risk.
- **Rule:** H3 step 4: the successful pre-migration backup is the prerequisite for a potentially irreversible migration.
- **Evidence:** `predeploy.py:124–141` chmods/links the encrypted output, writes/closes the checksum, unlinks the temporary name and immediately prints success. There is no fsync/fdatasync of either file or the output directory. Instrumenting the current successful unit-fake path produced exit 0 with zero fsync calls. The pinned age CLI also closes its output file rather than syncing it (`lazyOpener.Close` in [age v1.3.2 source](https://raw.githubusercontent.com/FiloSottile/age/v1.3.2/cmd/age/age.go)).
- **Failure scenario:** the deploy receives success, starts/commits migration, then the host loses power while backup data or directory entries are still only cached. The completed migration may survive while the backup or checksum does not. No power-loss experiment was performed; the missing durability barrier is directly established by the code and instrumentation.
- **Why it matters:** the intended pre-migration recovery point has not been made durable when permission to migrate is granted.
- **Required correction:** sync the completed encrypted file, checksum and necessary directory entries before reporting success; fail closed and withhold the success line on any synchronization/publication error. Keep publication and cleanup consistent with the completed-backup state.
- **Owner:** Builder.
- **Verification:** ordering/failpoint tests must show all required persistence barriers precede success, and that each sync/publication failure prevents migration eligibility. The [Linux fsync documentation](https://man7.org/linux/man-pages/man2/fsync.2.html) distinguishes file-data and containing-directory persistence.
- **Status:** open.

### [P1] Inspect destructive database operations inside migration wrappers

- **Category:** objective defect / guardrail mismatch.
- **Rule:** UNI-15; plan M1g contract-flag test.
- **Evidence:** `app/config/management/commands/migration_labels.py:41–44` checks only top-level operation instances. Reviewer created an unflagged migration containing `SeparateDatabaseAndState(database_operations=[RemoveField('thing', 'old')])`; `needs_flag()` returned **False**. The labels function lists contracts only when explicitly flagged.
- **Failure scenario:** an own migration wraps a drop/rename/alter in Django's standard database/state operation container. It passes the promised contract-flag test and contributes no contract marker, despite executing the destructive database operation.
- **Why it matters:** Part B's refusal will depend on correct contract metadata; this test is the guard against forgetting the flag. The current guard can miss a supported destructive operation solely because it is nested.
- **Required correction:** inspect supported nested database operations recursively (or reject unsupported wrappers in the guard) so these destructive operations still require `skiw_contract = True`. Keep harmless operations valid and flagged contracts in the emitted list.
- **Owner:** Builder.
- **Verification:** nested and directly listed examples of the five named destructive operations must be rejected without the flag and accepted/listed with it. Include a safe wrapped operation. [Django documents database_operations as executable operations within SeparateDatabaseAndState](https://docs.djangoproject.com/en/5.2/ref/migration-operations/#separatedatabaseandstate).
- **Status:** open.

- **Category:** objective documentation defect.
- **Rule:** UNI-16; Reviewer §7 executable operator runbooks.

- **Required correction:** provide a complete, consistent stdin-based command (no positional input filename) or explicitly provision the container-local file, plus the documented safe socket/password-file authentication and role selection. Include the Compose environment/image values needed to render it, and explicit success checking before continuing. Never place a password in argv/environment or the private age identity on the host.
- **Owner:** Builder.
- **Verification:** execute the documented command shape against a disposable synthetic database and verify restored rows; successful TOC listing alone is not proof that the restore command works.
