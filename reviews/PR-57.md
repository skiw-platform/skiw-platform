### Findings

### [P2] A dropped SSH session loses the host's journal and deploy-log line
- **Category:** material risk (in merged code; this PR adds the callers that can drop).
- **Rule:** spec §8.4 H3 step 11 (one line to the journal and the deploy log); UNI-16.
- **Evidence:** `infra/host/skiw_host/bootstrap_secrets.py:184–196`: `record()` prints to stderr
  **before** it writes the journal and the deploy log. Under the forced command, stderr is the SSH
  channel. When the client is gone, the print raises `BrokenPipeError` (Python ignores SIGPIPE).
  `deploy.py` `main` catches `OSError` and prints to stderr again, so the second error leaves
  uncaught. Then no journal line and no deploy-log line are written. The deploy itself finishes
  first, so the service is not affected. This PR adds two callers that can drop the session:
  `deploy-staging` (`timeout 3600`, a job timeout or a cancel) and `scripts/deploy-prod`
  (`DEPLOY_S = 3600`, network loss). Found by the builder's agent. I confirmed it by reading the
  code; I did not run it.
- **Failure scenario:** a slow pre-migration dump pushes a staging deploy past 3,600 s. CI kills
  `ssh`, and the host deploy completes. Then `journalctl -t skiw-deploy` and `deploy.log` have no
  line for it. The wrapper's timeout message tells the owner to read exactly that journal.
- **Why it matters:** the deploy record (step 11) is the audit trail for host changes. A rollback
  or a production deploy that leaves no line weakens it. The accepted-digest line is not affected.
- **Required correction:** write the journal and the deploy log first, then print to stderr last;
  treat a failed print (`BrokenPipeError`/`OSError`) as harmless. Add a test with a closed stderr.
- **Owner:** Builder.
- **Verification:** a test with stderr closed still writes both the journal line and the
  deploy-log line, with the right exit code.
- **Disposition:** deferred to the next PR (the pre-migration dump image fix, owner's choice
  2026-10-23), which must land before `SKIW_BACKUP_IMAGE` is set, so before any deploy can run.
- **Status:** open.

### [P3] "Runs on `main` are never cancelled" is not quite true
- **Evidence:** `ci.yml` `concurrency: group: ci-${{ github.ref }}`, `cancel-in-progress` false
  on push. In GitHub Actions, when a run queues in a group that already has a pending run, the
  pending run is cancelled (only the running one is protected). DECISIONS M1h (5), `ci.md` and
  `deploy.md` say runs on `main` are "never cancelled" and "a newer push waits". This is from the
  GitHub documentation as I know it; I did not run it here.
- **Effect:** three quick merges: the middle commit's run is cancelled before it starts, so that
  commit never gets an image. A running deploy is never cut, and order is kept, so this is safe.
  The wrapper refuses a cancelled run.
- **Suggested correction:** reword to "a running publish or deploy is never cancelled; a waiting
  run is replaced by a newer push".
- **Owner:** Builder. **Status:** open (non-blocking).
