### Findings

### [P2] The "staging lapses" steps leave a live DNS name and live credentials behind
- Category: material risk
- Rule: spec §8.4 H4 (secret rotation and "re-issued on recovery"), H12 G-VENDOR item 5 (disk wipe on
  termination, not yet answered), reviewer §7 (runbooks must be executable and complete)
- Evidence: `docs/runbooks/host-rebuild.md` (new section, PR lines 300–302): "**When staging lapses**,
  turn the staging deploy off: `gh variable delete SKIW_STAGING_DEPLOY …`". That is the only lapse
  step. What stays live:
  - **DNS:** staging's hostname (`SKIW_HOSTNAME`, and the DNS name in `SKIW_STAGING_SSH`, deploy.md
    lines 32, 173) still points at the old IPv4. A lapsed VPS frees that address.
  - **`ghcr_read_token`** on the staging disk: a classic PAT with `read:packages`, which "reads every
    package the issuing account can read" (plan G10), so it also pulls the production image.
  - **`alert_credential`**, the staging Telegram bot token (health-alerts.md line 109: each environment
    has its own bot).
  - The repository secret **`STAGING_DEPLOY_KEY`** (deploy.md line 183 lists it as the only secret).
  - The staging **UptimeRobot monitor** (health-alerts.md line 210, "one monitor per environment").
- Failure scenario: staging lapses. Hostinger gives the IPv4 to another customer. The DNS record still
  points there, so that customer can get an ACME certificate for the staging hostname and serve pages
  under the project's domain (a subdomain takeover). Separately, if Hostinger does not wipe the old
  disk (G-VENDOR item 5 is unanswered), the GHCR token on it can pull the private images (code, no
  client data), and the bot token can post to the owner's chat. The UptimeRobot monitor alerts every
  5 minutes until someone pauses it, which trains the owner to ignore alerts.
- What is already safe: production's staging check and the CI deploy pin staging's host key
  (`infra/host/skiw_host/deploy.py:116–118`, `StrictHostKeyChecking`), so a new owner of the IP cannot
  pass a production deploy or receive a deploy. Staging holds synthetic data only.
- Required correction: in "When staging lapses", **before** the term ends:
  1. turn the staging deploy off (as now);
  2. delete or point away the staging DNS records (site and SSH name);
  3. revoke the staging `ghcr_read_token` at GitHub (if production uses the same token, rotate
     production's too);
  4. revoke the staging bot token (BotFather `/revoke`);
  5. delete the `STAGING_DEPLOY_KEY` repository secret;
  6. pause the staging UptimeRobot monitor;
  7. destroy the VPS in the Hostinger panel, not only let it expire, and record the date.
  In "To bring it back", add the DNS step (point the staging names at the new IPv4 before `apply`, so
  ACME works) and un-pause the monitor.
- Owner: builder (runbook); the owner runs it.
- Verification: I read the new section in the follow-up docs PR.
- Disposition: **deferred to a docs PR merged by 2026-11-20, and in any case before staging is first
  allowed to lapse.**
- Status: open.
