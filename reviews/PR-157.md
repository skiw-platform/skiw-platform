### [P1] Credential discovery is inside the tenant transaction, contrary to the approved lookup boundary
- Category: guardrail mismatch
- Rule: spec §4.1 “Pre-tenant lookups” and Flow 5.1 (0); plan M3g assertion sequence; TEN-12
- Evidence: the spec requires credential discovery before a tenant is set and entry into `with_agency()` only after the blob is opened (`docs/specs/2026-10-05-skiw-platform-stack-design.md:237`, `:246`); the plan gives the same sequence (`docs/plans/2026-10-31-m3-auth.md:123`); the lookup contract says every call commits one event and therefore must run outside `with_agency()` (`app/accounts/auth/lookup.py:1-5`). The new path passes `match` as `second_factor.counted`'s callback (`app/accounts/auth/assertion.py:74-77`); `counted` invokes that callback inside `with_agency()` (`app/accounts/auth/second_factor.py:101-103`, `:135-143`), where `match` calls `lookup_credential` (`app/accounts/auth/assertion.py:89-95`). The new decision entry acknowledges that this goes against the lookup contract and that a later fault rolls back the lookup event (`docs/DECISIONS.md:1467`).
- Failure scenario: `guard.auth_lookup_credential` inserts `passkey.lookup`, then a database/configuration fault occurs while reading or updating `user_factor`. Because the lookup is part of `with_agency()`'s atomic block, the event is rolled back. The “each call commits one security_event” guarantee is false, and the approved pre-tenant-to-tenant boundary has been reversed without an owner-approved spec/plan change.
- Why it matters: this is a security-boundary requirement, not an implementation preference. The event is the durable evidence of use of the bypass function, including failed assertions.
- Required correction: keep the persistent factor reservation and lock check ahead of discovery, but execute `lookup_credential`, open/compare both owner IDs, and commit its event outside `with_agency()`; only then enter `with_agency()` for active-user, key, verification, and conditional-update work. Add a fault-path test proving a post-lookup failure does not erase the lookup event, while retaining the shared-budget/no-lookup-past-limit tests.
- Owner: builder
- Verification: inspect the new ordering and run the focused passkey, second-factor, lock, lookup, and tenancy live suites; force a post-lookup fault and verify the event remains committed.
- Status: open
