### What I checked
- **The migration.**
  - Two statements: `ADD COLUMN … NULL`, then `SET DEFAULT STATEMENT_TIMESTAMP()`. In PostgreSQL 11+, a default given in `ADD COLUMN` is stored as the missing value for every existing row; set afterwards, it applies only to new rows. So existing rows stay NULL, as the PR says. The builder's mutant for the one-statement form was killed by the first-apply test.
  - The column default reads `statement_timestamp()` on the review DB, which matches `Now()` in the model state; `makemigrations --check` and `lintmigrations --warnings-as-errors` pass.
- **The list.**
  - It is ordered `created_at ASC NULLS FIRST, id`: stable, a new passkey goes last, and an undated (older) one comes first.
  - The UTC rendering keeps microseconds always (`timespec`), so a time with zero microseconds keeps the same shape. The equal-times test uses exactly such a time.
  - TOTPs keep `{"id"}`, retired passkeys are not listed, and the exact body is tested.
- **The first-apply test** drops the column as its owner on the live DB, inside `try/finally` that re-migrates. If it failed between the drop and the re-migrate, `finally` still restores the column. Other tests' rows lose only their times, and no test depends on an older row's time.
- **Clock skew (why two of my mutants survived).** On my machine the DB container's clock is about 0.8 ms behind the host's (measured 9 times, −0.27 to −0.80 ms). The app's login time comes from the host, and the marker's from the DB. That is why the builder pins the enrolment order by order rather than by clock, and it explains S2 and S3 below. On a real host, the web and db containers share one Linux kernel clock, so production is not affected; nor is CI, which runs on one Linux kernel (inferred, not run).

### Findings

#### P3 #1 — the marker-before-`reissue` order in the factor and password changes is pinned only by the clock, not by order
- **Evidence:**
  - DECISIONS "M3g-2s-2" now states "every change writes it before `login.reissue`" as load-bearing.
  - Only the enrolment path got an order test. My mutants:
    - **S2**: in `factor_change._changed`, `reissue` before `mark`;
    - **S3**: in `password_change`, `reissue` before `mark`.
  - Both **survived** 98 live tests over the passkey change, factor change, factor remove, logout-and-password and passkey list suites.
- **Why:** with the DB clock 0.8 ms behind the app's, the mutated order still leaves the new session's login time after the marker's, so the re-issued session survives. On one shared clock, the existing clock-based tests should kill both (inferred).
- **Impact:** none today; the code has the right order. A future swap would fail closed (the user's own session signed out right after a change), not open. It could also pass on a skewed developer machine.
- **Suggested fix:** an order test like the enrolment one for `_changed` and for `password_change`: wrap `reissue`, and assert the user-wide marker exists when it runs. A follow-up is fine; this is older code (M3h-4, M3h-5).
- **Severity: P3.** No behaviour is wrong, and the gap is in code this PR doesn't change.

### Owner question 2 (PR body): make `created_at` immutable?
My advice is **no, not now**.
- `created_at` is display and order only; no security decision reads it.
- `skiw_app` can already update every other column of the row, including the public key and `retired_at`, so protecting this one column from the app role adds little.
- A trigger or a switch to column-level grants is more schema to maintain for no change in risk.
- **Condition:** revisit if any later code uses `created_at` to decide something (for example "the newest factor").
