### [P1] The role query ignores unexpected roles outside the skiw_ prefix
- Category: objective defect / spec mismatch.
- Rule: spec §8.4 H6 role-set test; plan §3 M1e/M1f; PROJECT §8 closed role set; TEN-02 mapping; UNI-03.
- Evidence: `infra/host/skiw_host/hardening.py:40–44` filters both roles and memberships by `rolname LIKE 'skiw\_%'`. H6 explicitly requires exactly the closed role set besides PostgreSQL's predefined pg_* roles, with only postgres superuser. The implementation never inspects postgres or a custom role with another prefix.
- Failure scenario: an additional `review_unexpected LOGIN SUPERUSER` role exists alongside all six compliant skiw roles. The query omits it and produces exactly the expected answer, so the entire hardening command passes.
- Verification performed: ran the shipped roles.sql and exact ROLES_QUERY in a disposable offline PostgreSQL 17.11 container. Baseline matched expected_roles. Created that extra LOGIN SUPERUSER role, independently selected its existence/login/superuser flags, then reran ROLES_QUERY: output was unchanged. Feeding the actual resulting output to actual hardening.main with the other host fixtures returned 0 and eleven PASS lines.
- Why it matters: a new privileged database identity remains invisible to the post-change/monthly security gate. Current HBA restrictions do not satisfy the separate required closed-role attestation.
- Required correction: inspect the complete role inventory, explicitly allow only the six application roles, postgres and the supported PostgreSQL predefined roles, and check the required superuser/BYPASSRLS constraints across that inventory. Do not treat any arbitrary prefix as proof that a role is allowed. Validate relevant membership drift as part of that complete policy. Update the runbook's narrower skiw-only claim.
- Owner: Builder.
- Verification: native Postgres baseline passes; unexpected non-skiw LOGIN and NOLOGIN roles, an extra superuser, and relevant privilege/membership drift fail. Preserve existing skiw-role attribute/settings tests.
- Status: open.

### [P1] Unexpected role settings are copied verbatim into diagnostics
- Category: objective defect / credential-disclosure risk.
- Rule: UNI-09; spec §8.4 H4/H7; the command's value-free output contract.
- Evidence: ROLES_QUERY at `hardening.py:40–41` includes the complete rolconfig values. `role_set` at `hardening.py:327–330` interpolates each unexpected raw row into the returned problem, which main prints. PostgreSQL documents rolconfig as role-specific configuration defaults and supports setting those defaults with ALTER ROLE: [pg_roles](https://www.postgresql.org/docs/17/view-pg-roles.html), [ALTER ROLE](https://www.postgresql.org/docs/17/sql-alterrole.html).
- Failure scenario: a role has an unexpected custom setting containing a credential, such as `app.review_secret`. Detecting that drift prints the credential in the FAIL role-set row instead of withholding it.
- Verification performed: in the same disposable PostgreSQL 17.11 instance, set skiw_app's custom setting to a generated inventory-secret value, reran the exact query, and supplied its actual output to actual hardening.main. The command returned 1, but its captured diagnostic contained the complete generated secret. The probe printed only a Boolean confirming the leak; no generated value is copied into this record or chat. No production secret was used or exposed.
- Why it matters: the checker itself can turn an unsafe configuration into a second disclosure through terminal capture, monthly-check logs or later alerts. Existing test assertions do not exercise secret-valued role settings.
- Required correction: parse the evidence for comparison but construct diagnostics only from controlled fields, such as a known role and the setting/attribute that differs. Never echo arbitrary database output, setting values or malformed rows. Withhold untrusted content on parse failure.
- Owner: Builder.
- Verification: add a regression with a freshly generated secret in a native-shaped rolconfig row; the check fails, identifies the setting or drift safely, and neither stdout nor stderr contains the value. Keep malformed query output value-free as well.
- Status: open.

### [P1] Short credentials are silently excluded from the environment gate
- Category: objective defect / security guardrail mismatch.
- Rule: spec §8.4 H4 forbids secrets in container environments; plan §3 M1f; UNI-07/08 and UNI-03.
- Evidence: `hardening.py:37,289–291` discards all secret strings shorter than 16 characters. Neither secret_store nor this check refuses such credentials. Existing `bootstrap_db.passwords` accepts any nonempty printable ASCII line, so a pre-existing shorter DB password is an accepted input, even though newly minted passwords are longer.
- Failure scenario: a correctly owned 0400 skiw_app_password contains an 11-character generated value, and a running container's DATABASE_PASSWORD holds that complete value. Both secret-store and container-env report PASS, as do the other nine checks.
- Verification performed: actual hardening.main with the normal Rig, that generated shorter file and matching Docker-shaped Config.Env returned 0 and eleven PASS lines. The secret was not printed.
- Why it matters: the gate certifies the no-environment-secret policy without checking an actual credential. Avoiding short substring false positives does not justify treating unsupported secret material as verified safe.
- Required correction: ensure every actual credential is covered. If retaining the documented 16-character substring-search floor, make an unsupported shorter credential fail closed with a value-free diagnostic, or use a suitable complete-value comparison for those credentials. Do not silently skip it and pass. This correction can preserve the cutoff for substring searching; no new business value is needed.
- Owner: Builder.
- Verification: short nonempty credentials copied into an environment must fail; long full-line and version-payload detection still fail; ordinary unrelated strings pass; unsupported/empty secret inputs cannot receive an unqualified PASS.
- Status: open. The proposed/recorded minimum is not approval to weaken the H4 assertion; PR #45 approval explicitly excluded this policy.
