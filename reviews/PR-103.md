### Findings

### [P3] #1 — Loggers outside `django.*` still print exception messages to stderr
- **Category:** privacy (log content), UNI-09
- **Evidence:**
  - `LOGGING` attaches the `stderr` handler only to `django.security` and `django.request`.
  - Every other logger propagates to a root logger with no handler, so Python's `lastResort` prints the
    record with the default `Formatter`, which includes the full traceback with its messages. The probe
    above shows this.
  - `procrastinate.worker` logs every failed job at ERROR with `exc_info` (`procrastinate/worker.py:240`).
  - Under gunicorn, `uvicorn.error` uses gunicorn's own formatter.
- **Failure scenario:**
  - A later job or worker-side path writes `app_user`, for example an invite or a sync, and hits
    `app_user_email_key`.
  - The worker logs `UniqueViolation … Key (email)=(person@…) already exists` to the container log.
  - Nothing on `main` does this yet: no job or request path reads or writes `app_user` before M3d-2,
    hence P3.
- **Required correction:**
  - Give the root logger the `stderr` handler at WARNING with the `plain` formatter, keeping
    `django.*`'s `propagate: False`. Every logger then goes through `NoExceptionText`.
  - Add a subprocess test on a non-`django` logger, for example `procrastinate.worker`, with the marker
    in a chained message.
  - Check that gunicorn's `uvicorn.error` handlers either don't fire for Django-handled errors or use the
    same formatter.
- **Owner:** builder · **Disposition:** deferred to M3d-2 (the first PR with request paths on
  `app_user`) · **Status:** open (deferred)

### [P3] #2 — The global `uq(email)` is not pinned
- **Category:** test gap
- **Evidence:**
  - `test_email_is_unique_and_matched_without_regard_to_case` inserts both rows in one agency.
  - A per-agency `UNIQUE (agency_id, email)` passes every test (mutant above).
  - So does a model edit that regenerates the migration, because `makemigrations --check` only compares
    the model with the migrations.
  - Spec §4.1 makes the global form load-bearing: M3e's `guard.auth_lookup_login(email)` returns one
    blob before the tenant is known.
- **Failure scenario:**
  - A refactor scopes uniqueness to the agency, and the tests stay green.
  - Once a second agency exists, the same email can then exist twice. The pre-tenant lookup becomes
    ambiguous, and it may return another agency's user's blob.
- **Required correction:**
  - Assert the catalog shape, for example as the migrator:
    `pg_get_constraintdef('app_user_email_key')` = `UNIQUE (email)`.
  - Or insert the same email under A and B and expect `app_user_email_key`, for example A committed by
    the harness, then B in a rolled-back `with_agency()`.
  - Do the same for `user_factor`'s global `uq(credential_id)` in M3d-1b.
- **Owner:** builder · **Disposition:** deferred to M3d-1b (the next PR, stacked on this one, with
  `user_factor`'s global unique) · **Status:** open (deferred)
