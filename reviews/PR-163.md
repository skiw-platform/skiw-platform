### Findings

### [P1] Sign out does not cancel a pre-confirm registration and can race its confirm

- Category: defect / auth lifecycle mismatch
- Rule: spec decision 6(a),(d),(e); AUTH-13
- Evidence: `web/src/App.tsx:76-88` calls `trusted()` and then logout without cancelling the factor operation. `web/src/passkey.ts:212-217` returns true during `ceremony`; `Security.tsx:53` aborts only when Security unmounts, which happens after logout finishes. Sign out is enabled during the ceremony (`App.tsx:101`), and Add has no lock for an in-flight sign-out (`Security.tsx:51`, `:144`).
- Reproduction: a disposable reviewer Vitest check held `credentials.create()` and then held the logout answer. Clicking Sign out sent `/api/auth/logout` while the registration signal was still not aborted. Resolving the prompt then produced this actual request order: begin → logout → passkey confirm → factors GET. The page announced “Passkey added” while logout was still pending. The check passed as a reproduction of the wrong behavior.
- Failure scenario: logout and a session-rotating factor confirm are simultaneously in flight, so their response/cookie/token ordering can disagree with the user's intent to leave. A new Add can also start while logout is in flight. The post-send logout hold cannot stop a logout already sent before confirm.
- Why it matters: the spec explicitly says sign-out before commit aborts begin/prompt and sends no confirm. This is the same shared-session race the runner and gate are meant to prevent.
- Required correction: serialize sign-out and factor operations in both directions. A sign-out intent must synchronously prevent any new factor operation and cancel an existing pre-send begin/prompt before logout can start; if confirm was already sent, keep the current reconciliation gate. Keep the exclusion until logout settles or its authoritative session recovery completes. Do not wait for component unmount to cancel the ceremony.
- Owner: builder
- Verification: held begin and held prompt tests activate Sign out, assert the signal aborts before logout and no confirm ever follows, even if the fake prompt resolves late. A held logout followed by navigation to Security/Add must not start begin. Preserve existing after-send token-order tests.
- Status: open

Runner phase and logout hold live only in JavaScript module memory (`passkey.ts:190-197`, `api.ts:39-49`). Existing leaving tests change `window.location.hash = ""`; they do not activate the Today link. PR 162 explicitly disclosed that Today performs a document reload and its review required reconsidering that behavior once mutations were introduced.
- Reproduction: Chromium against this exact checkout with fake session/options/credential and a held confirm request: activate Add, wait for “Finishing your change…”, then click the actual Today anchor. Result: `confirmSeen: true`, `documentReplaced: true`, runner `phase: idle`, `signOutEnabled: true`. The old confirm was never answered. This was a focused browser reproduction, not the deferred full browser matrix.
- Failure scenario: the ordinary navigation the page offers discards the only owner of the pending confirm/reconciliation and constructs a fresh, unlocked runner. It cannot fulfill the promised consume-answer/readSession lifecycle after departure or keep Sign out behind the unresolved mutation. A module outlives a component, not its document.
- Why it matters: this bypasses the central guarantee for a mutation that can rotate the session. The green hash-navigation test proves a different path.
- Required correction: make the application's ordinary Today/Security navigation retain the document and runner, while preserving real hrefs, modified-click/new-tab behavior, URL/history and Back/Forward semantics. Alternatively supply and prove an explicit document-replacement recovery protocol; a fresh empty module is insufficient. Define the separate reload/tab-close limitation honestly rather than claiming arbitrary document departure always reconciles in the old module.
- Owner: builder
- Verification: a real browser clicks Today during a held confirm/lost answer, proves the same operation remains owned and Sign out remains gated until an authoritative result/token read, and proves exact eventual logout token/request order. Retain direct-open/reload/history and modified-click checks. This specific demonstrated defect must be fixed now; the remaining browser matrix can stay in M3g-2b.
- Status: open

### [P2] Add unlocks before its reconciliation list read and permits overlapping UI completions

- Category: defect / resilience
- Rule: spec decision 6(d), 6(f), 8
- Evidence: `web/src/passkey.ts:264-266` enters idle/unresolved and returns before `Security.tsx:104-111` starts/finishes the refreshed factor list. The Add button's only lock is `ceremony`/`sent` (`Security.tsx:50-51`, `:144`). The list request has no attempt-generation check, only an unmount signal.
- Reproduction: a disposable reviewer Vitest check returned exact ADDED, held the subsequent factors GET and observed Add already enabled before that GET returned.
- Failure scenario: the person starts a second Add while the first refresh is pending. The first refresh can finish during the new prompt, overwrite its status and move focus; if its snapshot returns last, it can overwrite the second operation's newer list. This is not the promised single-flight user operation.
- Why it matters: stale rows/status and focus can contradict the latest action. P2 rather than P1 because the first confirm's session/token reconciliation has completed; this finding concerns UI/read ordering, not permission bypass or a demonstrated stale-token POST.
- Required correction: keep the relevant factor controls busy through the operation's required list refresh, including the unconfirmed-result path, or use explicit generations to ignore superseded completions while preserving the spec's single-flight UX. Do not hold logout unnecessarily after its token is trusted; distinguish the token gate from the UI operation lifetime. Coordinate mount reads with an operation still refreshing when a user returns.
- Owner: builder
- Verification: held list reads for added/unconfirmed outcomes cannot start another begin; deliberately reordered reads cannot overwrite the newer list/status or steal focus from a later operation. Failed reads release controls according to the specified unresolved/reload path.
- Disposition (P2 only): before merge
- Status: open
