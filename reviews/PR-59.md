### Findings

### [P2] The tests do not protect several storage safety checks
- **Category:** material risk (test gap on data-loss, tenancy and scan paths).
- **Rule:** spec §8.4 H5 (sweeper, verified open); UNI-03; PROJECT §9 files-volume rule.
- **Evidence:** reviewer mutation run on a scratch copy with a live database and real clamd
  (all 46 `app/documents/tests` pass at baseline). Each mutant below left all 46 green:
  1. `sweep_quarantine` also deletes sources of `pending` rows (`storage.py:262`): an upload that
     waits more than 1 h for its scan (clamd down, retries with backoff) loses its only copy.
  2. The same for `infected` (and so `failed`) rows; H5 keeps them for `retention.scans_quarantine`.
  3. `_verified` without the agency check `match[1] != str(row.agency_id)` (`storage.py:326`):
     a row whose `object_key` names another agency's directory is served.
  4. `open_verified` without the `clean` status check (`storage.py:237`).
  5. `ClamdScanner.scan` returning clean when sending fails (`clamd.py:49`): the path clamd takes
     when it closes the socket after a size-limit error.
  The code itself is correct today. 15 other mutants were killed (lock, step 2, fsyncs,
  `O_NOFOLLOW` on directories, size limit, 0600 mode, FOUND verdict, terminator, VERSION check).
- **Failure scenario:** M16 changes the sweeper or the download path (it must: re-encoding, the
  real table, the endpoint). A slip like mutant 1 deletes uploads that wait for a scan, and CI
  stays green.
- **Why it matters:** this PR is the H5 harness; M16 re-runs it as the proof. It must fail when a
  guarantee breaks, on the keep side as well as the remove side.
- **Required correction:** add tests that fail for each of the five mutants: (1)–(2) a `pending`,
  an `infected` and a `failed` source older than the sweep age stay; (3) a row whose `object_key`
  names another agency is refused and marked; (4) `open_verified` refuses a non-`clean` row;
  (5) a fake clamd that closes the socket during the stream gives a `ScanError`, never clean.
- **Owner:** Builder.
- **Verification:** I re-run the same five mutants; each must fail at least one test.
- **Disposition:** before merge.
- **Status:** open.

### [P2] clamd answers `stream: OK` for a file it did not fully scan
- **Category:** material risk.
- **Rule:** spec §8.4 H5 step 3, D14, T14; FILE-01.
- **Evidence:** the pinned image's own `/etc/clamav/clamd.conf` (read from
  `clamav/clamav:1.5.4@sha256:638d9020…`): "When AlertExceedsMax is set, files exceeding the
  MaxFileSize, MaxScanSize, or MaxRecursion limit will be flagged … `Heuristics.Limits.Exceeded`.
  Default: no". `infra/host/compose.yml:134–135` sets only `ConcurrentDatabaseReload`, and the
  EICAR test container sets nothing. So clamd stops scanning at a limit and still replies
  `stream: OK`, which `clamd.py:54` maps to clean. I read the config; I did not run a crafted file.
- **Failure scenario:** a PDF with more than 10 levels of nested embedded objects (the default
  `MaxRecursion`) is scanned only in part, gets `stream: OK`, and is published to `clean/`.
- **Why it matters:** H5 says a file becomes visible only after the scan passes. A partial scan
  that reports OK is a silent bypass of the only malware control.
- **Required correction:** set `CLAMD_CONF_AlertExceedsMax: "yes"` on the `clamav` service and in
  the live test container (and record it for the planned mounted `clamd.conf`). A FOUND name that
  starts with `Heuristics.Limits.Exceeded` must never be clean (infected or failed; record which
  in DECISIONS). Add a compose config assertion and a live test that pushes one limit low (for
  example `CLAMD_CONF_MaxRecursion` or `MaxScanSize` in the test container) and expects no clean
  verdict.
- **Owner:** Builder.
- **Verification:** the compose test asserts the setting; the live test shows a limit-exceeding
  stream is not clean.
- **Disposition:** before merge (one setting and one test; this PR adds the scanner client).
- **Status:** open.

### [P3] Storage trusts path parts and keys from its caller
- **Evidence:** `write_quarantine` uses `str(agency_id)` as a path component without a check
  (`storage.py:168`); a non-UUID string with `/` would cross directories, since only each listed
  part is opened `O_NOFOLLOW`. mypy stops this today. In `_verified` a key that matches
  `CLEAN_KEY` but is not a UUID (for example 36 dashes) makes `uuid.UUID()` raise `ValueError`
  (`storage.py:326`), so the row is not marked `integrity_failed`; it still serves nothing.
- **Suggested correction:** normalise `agency_id` with `uuid.UUID(str(...))` at the boundary;
  treat a bad key as a failed verification.
- **Owner:** Builder. **Status:** open (non-blocking).

### [P3] `open_verified` marks the row and then raises (hand-over for M16)
- **Evidence:** `storage.py:240–242`. The harness commits the mark only because `download()`
  catches `FileIntegrityError` inside its transaction (`test_harness_live.py:131–140`). A natural
  M16 endpoint (`with transaction.atomic(): open_verified(...)`) rolls the mark back; only the log
  line remains. H5 requires the mark.
- **Suggested correction:** say this in the docstring and DECISIONS "Not built here", or return
  an outcome as `publish_clean` does.
- **Owner:** Builder. **Status:** open (non-blocking).

### Residual risks and test gaps
- Crashes are simulated with `BaseException`, not a real process kill; fsync durability is tested
  only by call order (stated in the PR).
- Image re-encoding, EXIF stripping, decode and page checks are M16 (recorded). Until then the
  output re-validation checks cannot fail, because the output is a copy of the verified source.
- The scanned bytes are not hashed: the source is hashed before the scan and again during the
  copy, not during the scan. Changing the file in between needs write access to the volume.
- `_open_file` opens before it checks `S_ISREG`: a FIFO planted at a clean path would block the
  open. Needs volume write access.
- clamav still runs as root at start (DECISIONS open item); the backup uid cannot read 0600 files
  (M6 decides).
- PROJECT.md §7 is out of date about where the harness runs (owner, setup).
