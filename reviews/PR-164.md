### Findings

### [P1] Cancelled code verification can restart Add after the dialog has closed

- Category: defect / lifecycle mismatch
- Rule: spec decision 6(a),(d), 8; PR 164's Cancel/Escape contract
- Evidence: `web/src/screens/StepUp.tsx:65-76` awaits the code POST and calls `settled()` without a cancelled/unmounted check. Cancel/unmount only aborts `flight.current` (`:37-40`, `:51-55`), which is assigned only for the passkey branch, not the code POST. Security's `onCancel` closes the dialog but does not invalidate the original Add controller (`web/src/screens/Security.tsx:164-166`); a later `onVerified` tests that still-live controller and calls `add(true)` (`:159-162`). Existing late-verification tests leave/unmount Security, a different condition from cancelling only its dialog.
- Reproduction: real headless Chromium against this exact checkout, fake API/authenticator. Initial Add begin returned `stepup-required`; entered a code and submitted; held the `/api/auth/stepup` response; clicked Cancel and confirmed the dialog detached; then released `{next: verified, until: ...}`. Actual subsequent requests were a second `/api/auth/factors/passkey`, `/api/auth/factors/passkey/confirm` and factors GET. `credentials.create()` was invoked once after Cancel, and the page displayed “Passkey added.” The held code response therefore resurrected the cancelled operation.
- Failure scenario: a person cancels because verification is slow, but the delayed answer starts registration anyway. If they reopen Add, the old dialog's response can also interfere with the newer attempt because the parent checks a shared current ref rather than the old dialog's own lifetime. Late signed-out/error callbacks from the code branch similarly lack cancellation ownership.
- Why it matters: Cancel and Escape must stop this user operation. This is an unintended continuation of a sensitive action; successful server step-up does not establish continuing user intent after cancellation.
- Required correction: give each StepUp lifetime/request an explicit cancellation identity. Invalidate it synchronously on Cancel/Escape and on unmount; ignore every late code-response callback/state/focus action from that lifetime. Abort the code request where appropriate, but do not rely on abort alone: an already-arrived or abort-ignoring response must still be ignored. Ensure Security's retry belongs to the dialog/attempt that verified, rather than any currently live Add controller. Preserve normal successful retry, passkey cancellation and token-consumption behavior.
- Owner: builder
- Verification: held code-verification tests cancel using both Cancel and Escape, then release verified, signed-out and error answers. Assert no new begin/confirm/authenticator call, no stale screen transition/status/focus update, and Add remains available. Close and reopen a new dialog before resolving the old answer; old callbacks must not close or advance the new one. Retain existing unmount/leaving and one-retry tests. Replay the Cancel + late verified case in a real browser.
- Status: open
