### [P3] #6 A cancelled dialog still acts on the server's answer
- Category: latent defect (the dialog is not mounted yet)
- Rule: AUTH-09 intent (step-up confirms one action the person chose); FE failure paths
- Evidence: `web/src/screens/StepUp.tsx`. The Cancel button is not disabled while the request runs (`busy` disables only Confirm), and `submit` calls `onVerified(until)` after the `await` without checking whether the dialog was cancelled. **Reproduced** with a scratch vitest probe (not added to the repo): a host closes the dialog on `onCancel`; the person types a code, presses Confirm, then presses Cancel while the request is open; the server then answers `verified`; **`onVerified` is called once** after the dialog has closed.
- Failure scenario: a later screen wires `onVerified` to "go ahead with the factor change". A person starts "remove authenticator", has second thoughts and presses Cancel or Escape while "Checking" shows. The action runs anyway.

- Required correction (with the first PR that mounts the dialog): after cancel, ignore the answer, for example with a cancelled ref checked after the `await`, or an `AbortController` passed to `post`. Or disable Cancel and Escape while busy. Add the probe's case to `stepup.test.tsx`.
- Owner: builder · Verification: the probe passes and a mutant that removes the guard fails it.
