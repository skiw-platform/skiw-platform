### [P2] The pool is reachable without `async_with_agency()`; only the class name is lint-enforced
- Category: spec/guardrail mismatch
- Rule: spec D26 ("lint-enforced as the only way to use that pool (TEN-09/10)"); TEN-10; plan UNI-04 for M4c-8
- Evidence: Semgrep `tenancy-async-pool` (`semgrep/tenancy-boundaries.yml:123-132`) matches only `\bAsyncConnectionPool\b`. `app/tenancy/async_binding.py:30,33,47` expose `_pool`, `_new_pool()` and `_get_pool()` as plain module attributes; no Semgrep rule or import-linter contract stops another module from `from tenancy.async_binding import _get_pool` (grep of `semgrep/` and `pyproject.toml`: no reference). The PR's own tests already use `_pool` and `_new_pool` from outside the module, which shows the path works.
- Failure scenario: M14 bridge code (or anything later) takes `await _get_pool()` and runs statements on an autocommit `skiw_app` connection outside any tenant transaction, bypassing the one-short-transaction shape D26 relies on (e.g. holding a pooled connection across the long-poll wait).
- Why it matters: D26 makes the helper the only entry by lint, not by convention. Downgraded from P1 because the impact is isolated today: an unbound connection gets `guard.current_agency()` NULL, so RLS fails closed on every tenant table; nothing calls the pool before M14; and the Django default connection already gives unbound access to global tables.
- Required correction: a Semgrep rule (with fixture cases) refusing any reference to `async_binding._pool`, `_new_pool` or `_get_pool` (and `from tenancy.async_binding import _…`) outside `app/tenancy/async_binding.py` and `app/tenancy/tests/`; `bridge.db` re-exports only `async_with_agency`.
- Owner: builder
- Verification: `make lint` passes with the rule; its fixture shows a hit for `_get_pool()` in a non-tenancy module.
- Disposition: deferred to M14 (the `bridge.db` re-export PR), before any caller of the pool lands
- Status: open

### [P3] Pooled sessions are not normalised like Django's, and are not reset on return
- Category: material risk (minor) / maintainability
- Rule: D26 ("the async twin of `with_agency()`"); TEN-09 intent
- Evidence: `_new_pool()` (`async_binding.py:33-44`) passes no `configure` or `reset` callback. Django's PostgreSQL backend sets the session `TimeZone` to UTC on its connections (`USE_TZ`); these connections keep the server default. Session-level state a block leaves behind (any `SET` other than the Semgrep-banned `app.*`, e.g. `statement_timeout`, `search_path`) carries over to the next agency's checkout. The xid-bound token itself cannot leak (the leak test and the replayed-B forgery prove it).
- Failure scenario: M14 code inserts a naive datetime or reads `timestamptz` text and gets server-local rather than UTC behaviour that differs from the sync path; or one poll's session `SET` changes the next tenant's block.
- Required correction (at M14): a `configure` callback that sets what Django sets (`TimeZone` UTC) and a `reset` callback (`RESET ALL` when idle), with a test that a session `SET` in one block is gone in the next.
- Owner: builder
- Status: open (optional; M14)
