### [P1] A cancelled Remove recovery read can overwrite the token installed by logout

- Category: defect / auth lifecycle mismatch
- Rule: spec decision 6(a),(b),(e); AUTH-13; UNI-03
- Evidence: `web/src/passkey.ts:327-329` awaits `reread()` before checking the operation's aborted signal. `reread()` (`:283-287`) calls an independent, uncancelled `readSession()` and then clears the token gate. Sign out can run its own session read/logout while that older read is pending. The API consumes every readable body's `csrf` immediately (`web/src/api.ts:11-22`), before the cancelled Remove sees its signal. The new test at `web/src/remove-passkey.test.tsx:206-217` actually resolves the older session answer after logout but asserts only that no Remove POST follows; it does not assert the token of the next POST.
- Reproduction: headless Chromium against this exact checkout, fake API. First Remove lost its answer and its session recovery failed, leaving the phase unresolved. Retried Remove and held its pre-send session read. Clicked Sign out; its separate session read succeeded, then logout completed and installed fake token `t9`. Released the older read with fake pre-logout token `t6`. No cancelled removal was sent, but a subsequent diagnostic POST through the real API client carried `X-CSRFToken: t6`, not `t9`. Observed sequence after the initial list: Remove → failed session read → factors GET → held session read → Sign out's session read → logout → late held answer → diagnostic POST with the obsolete token.
- Failure scenario: the user signs out successfully, but an older cancelled operation poisons the client token afterward. The sign-in screen's next CSRF-protected request can fail against the rotated cookie. Checking the operation signal after `readSession()` does not undo `keepToken()`'s shared-state write.
- Why it matters: the new Remove cancellation path guarantees no late mutation but does not protect the shared session state. This violates the token-coherence guarantee the runner and logout gate are explicitly designed to provide. The same shared recovery helper is used by Add, so its correction must cover both callers.
- Required correction: establish ordering/ownership for token-bearing session reads and logout. Either serialize/drain the earlier recovery read before allowing logout to rotate the session, or invalidate obsolete reads at the API token-commit boundary so they cannot overwrite a newer token or clear a newer operation's phase. Cancellation must also handle an answer that ignores abort or whose headers/body have already arrived. A guard only after the existing `readSession()` await is insufficient because the token has already changed. Preserve sent-mutation reconciliation after screen departure.
- Owner: builder
- Verification: extend the existing held-reread/sign-out test to complete logout with token B, release the older answer with token A, then assert the next protected POST uses B and the cancelled mutation never sends. Cover Add and Remove, aborted/abort-ignoring reads and the phase after logout. Replay this ordering with a real browser and fake held responses; keep existing after-send reconciliation and late-dialog cancellation tests green.
