### Findings

### [P2] The runbook's version report can't run on a host: `psql -U postgres` has no password
- Category: defect (runbook, reviewer §7)
- Rule: UNI-16; reviewer §7 ("no checks that can't actually be run"); PR 117 R1 P2, which this PR closes
- Evidence:
  - `docs/runbooks/host-rebuild.md:137-140` runs `docker compose … exec -T db sh -c 'psql -X -At -U
    postgres -d "$POSTGRES_DB"'` and gives no password.
  - `infra/host/db/pg_hba.conf` has `local all postgres scram-sha-256`. The `db` service has no
    `PGPASSWORD` and no password file (`POSTGRES_PASSWORD_FILE` is read only by the image's init, not by
    psql).
  - `bootstrap_db.psql_script` and `restore.md` steps 4–5 build a `PGPASSFILE` from
    `/run/secrets/postgres_password` for exactly this reason.
  - **Reproduced:** `postgres:17` with those hba lines, the runbook's exact `sh -c` and heredoc through
    `docker exec -i`:
    - result: `FATAL: password authentication failed for user "postgres"`, exit 2;
    - psql took the heredoc's SQL as the password;
    - the same SQL behind the restore.md `PGPASSFILE` wrapper printed the result, exit 0.
  - The unit test pins the SQL text only, not the shell around it. The live test runs the SQL as
    `skiw_app`, so neither reaches this path.
- Failure scenario: before a planned rotation, the operator runs the report and gets an authentication
  error. The one check PR 117 R1 P2 asked for can't be run. The operator either stops, or removes the
  version without the count, which voids codes silently.
- Required correction:
  - Wrap the SQL in the same password-file pattern as `restore.md` / `psql_script` (mode 0600 temp
    file, `trap` removal, password never in argv or env).
  - Keep the SQL byte-identical, so the pinning test still holds.
  - Optionally extend the pinning test to require `PGPASSFILE=` in the same block.
- Owner: builder
- Verification:
  - the reworded block, run against a container with the host hba lines, prints the report;
  - the unit test still pins the SQL.
- Disposition: **before merge**. This PR exists to make that runbook step executable, and the fix is a
  few lines.
- Status: open.

### What was checked (no finding)
- **Stored form:**
  - The version is 4 bytes big-endian (it fits 999999; a test covers `000f423f`), then the HMAC.
  - Newest signs; `consume` matches the full 36 bytes against each `version || MAC`.
  - A row with an edited version or a swapped key pairing matches nothing. That is covered by the
    builder's mutants and by my reading of `CONSUME = ANY(%s)`.
- **Version outside the MAC:** fine. It isn't secret, and the full-row equality still binds it.
- **CHECKs (`sqlmigrate`):**
  - `NOT (kind = 'totp') OR (LENGTH(secret_ct) = 48 AND secret_ct IS NOT NULL)`, and the same with 36
    for recovery.
  - The explicit `IS NOT NULL` is needed because a CHECK passes on NULL.
  - Passkey rows are left unchecked, for M3g.
  - 9 refusal cases plus each kind's acceptance are tested live.
- **UNI-15:**
  - Only `recovery.py`, `totp.py` and `blob.py` touch `user_factor` outside tests and migrations, and no
    route calls them.
  - The previous digest's `generate` would write 32 bytes, but nothing invokes it, and no host holds a
    factor row.
  - Additive and reversible: I migrated `accounts` to 0009 and forward again on the disposable DB.
  - `lintmigrations --warnings-as-errors` and `makemigrations --check` are clean (via `make migrate`).
- **Fixtures:** `isolation_cases.py` now inserts 48 bytes. `add_factor` defaults to `passkey` so the
  generic tests avoid the new CHECKs. The kind-scoping test now uses a passkey row holding a recovery
  MAC, next to a real 48-byte TOTP row. That keeps both mutant kills from PR 117.
- **Report SQL:** `get_byte` shifts give big-endian. The `::bigint` on the high byte avoids int overflow
  above 2^31. The test uses random versions, so committed users from other tests don't collide.
- **UNI-02:** lengths derive from `OVERHEAD`, `FACTOR_SECRET_SIZE` and `RECOVERY_VERSION_BYTES`.
