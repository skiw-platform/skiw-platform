### Findings

#### [P1] Hidden reverse accessors still leave ORM joins to scoped rows

- **Category:** Guardrail mismatch.
- **Rule:** UNI-04, platform D18 and slice Decisions 9–10, §7 intra-agency visibility.
- **Evidence:** `app/accounts/access/scope.py:72`–`:76` accepts every relation marked hidden. `app/accounts/tests/test_access_scope.py:112`–`:119` explicitly accepts a forward foreign key into a scoped model when its backward accessor is hidden.
- **Failure scenario:** In an isolated Django 5.2.17 model registry, `Record.check()` returned no messages for a scoped model with both of these relations. A plain model's forward foreign key into the scoped model used `related_name="+"`, and `select_related()` on the plain model selected the scoped record's fields. In the other direction, a scoped model's foreign key used `related_name="+"` together with an explicit `related_query_name`. A queryset for the plain parent followed that name to select scoped record IDs. Both queries compiled without an ownership or team predicate. The probe compiled SQL without connecting to a database.
- **Impact:** RLS limits a relation read to the agency. The within-agency record policy is therefore the check that would keep an own- or team-scoped user from seeing records outside their scope. A valid Django relation can currently reach those rows outside that check. This is a gap in the proposed boundary. The slice introduces only an abstract model.
- **Required correction:** Reject forward relationships into scoped models and explicit reverse query names on otherwise hidden relationships that expose scoped rows, or enforce the same visibility policy on those paths. Add system-check regressions for the forward relation and hidden accessor with an explicit reverse query name. Preserve valid owner relationships going from the scoped record to the user.
- **Owner:** Builder.
- **Verification:** The two synthetic relationship declarations fail the scope check or can only read through the protected path. Ordinary owner-field declarations and the coverage check still pass.
- **Status:** Open.

#### [P1] Django's lookup shortcuts select the unfiltered manager

- **Category:** Guardrail mismatch.
- **Rule:** UNI-04, platform D18 and slice Decision 10, §7 intra-agency visibility.
- **Evidence:** `app/accounts/access/scope.py:31`–`:38` makes `_unscoped` the sole declared manager. `semgrep/scoped-only.yml:13`–`:31` catches literal manager access and direct queryset construction. The independent Semgrep 1.179.0 probe flagged the direct `_default_manager` control and returned zero findings for Django's `get_object_or_404(ScopedRow, ...)` and `get_list_or_404(ScopedRow, ...)`. Installed Django 5.2.17's `django/shortcuts.py:56`–`:65` selects that manager internally, and the isolated model probe confirmed its queryset carried no scope predicate.
- **Failure scenario:** A future handler passes the scoped model class to a stock lookup shortcut. The call passes CI and performs the lookup against the agency's rows using only the caller's extra filters.
- **Impact:** A handler can omit `scoped()` on an otherwise ordinary model lookup. The decisions entry identifies this limitation and carries it forward, while the owner-approved 4a slice covers the access boundary.
- **Required correction:** Provide an enforceable check for Django shortcuts receiving a scoped model class, and keep the normal path working when the shortcut receives an already-scoped queryset. Add coverage for the direct class and appropriate allowed calls.
- **Owner:** Builder.
- **Verification:** The two original shortcut calls fail the boundary check. An unrelated model and an already-scoped queryset remain usable in the shortcuts.
- **Status:** Open.
