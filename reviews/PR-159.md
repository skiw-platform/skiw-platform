### Findings

#### P3 #1 — the marker time is the statement time, not the transaction start, as the docs say; the order in `_commit` is therefore load-bearing
- **Evidence:**
  - On the migrated review DB, `information_schema.columns` gives `session_revocation.revoked_at` the default **`statement_timestamp()`**. That comes from `db_default=Now()` in `revocation_model.py` / 0006, and Django renders `Now()` as `STATEMENT_TIMESTAMP()` on PostgreSQL.
  - Yet these all say it is `CURRENT_TIMESTAMP`, the transaction start:
    - `revoke.py` (module docstring);
    - `login.reissue`'s docstring;
    - DECISIONS (M3h-5 entry "`revoked_at` is `CURRENT_TIMESTAMP`, the **transaction start time** (not the statement time, PR 141 R1 P3 #2)"; the "Docstrings" bullet);
    - and, new in this PR, DECISIONS "M3g-2s-1" ("`login.AUTH_AT` is the app clock, after the marker's transaction start").
- **Why it matters here:**
  - If the marker were the transaction start, the order of `revoke.mark` and `then` in `_commit` wouldn't matter.
  - Because it's the statement time, moving `then` (that is, `login()`) before `revoke.mark` revokes the brand-new session. My mutant Q1 did exactly that: `added(cookie)` gave 401 and 4 tests failed.
  - The tests catch it, but a reader trusting the docs would think the order is free.
- **Safety:** the real behaviour is stricter than documented everywhere I looked, so it fails closed:
  - A later marker time revokes more sessions and refuses more pending logins (`changed_since`).
  - Every place that must survive its own marker reads the app clock after the marker's INSERT: `reissue`, the factor changes (`mark` then `reissue`) and now enrolment.
  - The M3h-5 "window is the whole change transaction" is in fact shorter: it runs from the marker's statement to commit.
- **Correction** (this PR or a docs follow-up):
  - say `statement_timestamp()` in `revoke.py`, `login.reissue`, the M3h-5 bullets and "M3g-2s-1";
  - add one comment in `_commit` that `then` must stay after `revoke.mark`.

  Alternatively, make the column `CURRENT_TIMESTAMP` with a migration. That's an owner call, and I wouldn't: the statement time is the safer of the two.
- **Severity: P3.** No behaviour is wrong, the load-bearing order is tested, and the error is inherited (M3d / PR 141). This PR only repeats it.
