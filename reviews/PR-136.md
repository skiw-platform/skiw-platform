### Findings

### [P3] Two follow-ups for M3h-2, now that a named factor can never be deleted
1. **Only a TOTP (later a passkey) may be named.** `recovery.py` deletes recovery rows with raw `DELETE … WHERE kind = 'recovery'` (one code at sign-in, all of them on regenerate). If a step-up ever named a recovery row, the NO ACTION FK would make that delete fail, and sign-in by recovery code or regenerating codes would break for that user. Recovery codes are excluded from step-up by design [A], so `record()` in M3h-2 should refuse any factor that isn't TOTP (or a passkey from M3g), with a test.
2. **`factor_id` is nullable with no remaining use.** Its only null case was the old `SET NULL`. A step-up is by definition the re-verification of a factor, and the new test docstring ("a step-up that no factor proved is still evidence") describes a case nothing should produce. Either make the column NOT NULL (a cheap migration while the table is empty, in M3h-2) or have `record()` require a factor and say why the column stays nullable.

### Findings

### [P2] `ON DELETE SET NULL (factor_id)` voids genuine step-up evidence that the spec's consumers verify later
- Category: spec mismatch (design) · material risk (forward)
- Rule: spec §4.1 `auth_stepup` ("consumers verify `evidence_mac`"); §4.3 executor; T10 tests; D25; AUTH-09
- Evidence:
  - DECISIONS "M3h-1" fixes the MAC over every column including `factor_id`. The FK then lets the database change `factor_id` to NULL when the factor is deleted, so the row stops verifying. The PR accepts that as harmless "because a factor change re-issues the session, so the session's earlier step-ups are dead anyway".
  - That premise holds only for consumers that use a step-up within its own session and its ≤ 5 min window. The spec's two named consumers store the step-up id and check the evidence **later, outside the session**:
    - §4.3 and T10: "an `auth_stepup` row inserted by raw SQL (invalid `evidence_mac`) is refused by approval **and executor**". The executor runs in a job, up to `approval_expires_at` after the approval.
    - D25: the step-up id "is stored on the row and checked by `documents.drive_writer` before any Drive call". A `drive_operation` can sit `waiting` on a dependency, and a person's "Retry" re-runs it later.
- Failure scenario (M9 / M16 onward): a user approves a CRM write (step-up with TOTP A), then replaces TOTP A (M3h-5/6) before the executor claims the action. `factor_id` is cleared, `evidence_mac` no longer verifies, and the executor refuses a genuinely approved action. Worse, it refuses it on the same check that exists to catch forged SQL rows, so a genuine row now looks forged. The same happens to a waiting Drive operation, and to every user whose factors the owner resets (M4-rest) or who removes a passkey (M3g). After the fact, the row also no longer says which factor proved it. That forensic loss matters, because the table exists to be evidence.
- It fails closed: no forged evidence is accepted. That is why this is P2, not P1. But it is built into an append-only table's schema and its recorded rationale, and M3h-2 and M3h-6 are about to build on it.
- Required correction (choose one; my recommendation first):
  1. **Keep the FK as NO ACTION (or RESTRICT), and retire factors instead of deleting them.** M3h-6 then marks the old TOTP retired (for example `retired_at`, with the secret ciphertext destroyed or cleared and every check refusing a retired factor). M3g does the same for passkeys. Recovery codes are never step-up factors, so their `DELETE … RETURNING` is unaffected. The `user_factor` change belongs to M3h-6, but this PR should fix the FK and record the plan. **This stays inside the spec** (§4.1 says FK→user_factor and never that a factor row is deleted), so it does not need an owner decision unless Ying wants to override it.
  2. Drop the FK, or leave `factor_id` out of the MAC. Each is a deviation from spec §4.1 ("FK→user_factor"; "over all other columns"), so it needs the owner's decision and a spec change. I don't recommend either.
- Either way, correct the DECISIONS rationale: remove "harmless … dead anyway", and name the later consumers (executor M9, `drive_writer` M16).
- Owner: builder (option 2 would need Ying)
- Verification: re-review. Catalog test pins `auth_stepup_factor_id_fk` without an `ON DELETE` action; a live test shows that deleting a `user_factor` referenced by a step-up is refused as `skiw_app`; DECISIONS states the retire plan for M3h-6.
