### [P2] Parallel attempts all pass `blocked`, so the 5-per-account limit does not hold under load
- Category: security control (rate limit)
- Rule: spec Flow 5.1 ("rate limit 5 fails / 15 min / account and 20 / 15 min / IP"); T5; AUTH-06
- Evidence: `app/accounts/auth/throttle.py`. `blocked()` reads the counts. `record_failure()` adds to them later, after M3e's Argon2 verify. Nothing holds the two together. I proved the gap in a scratch copy against the live tables (as `skiw_app`): 20 threads for one email, each from its own IP. Each thread called `blocked`, slept 100 ms (one Argon2 verify), then called `record_failure`. **All 20 passed `blocked`.** The limit is 5. DECISIONS M3c-2 "Known limits (a)" names this overshoot. The duty it gives M3e ("records the failure before answering") does not bound it, because the gap is between the check and the record, not the record and the answer.
- Failure scenario: after M3e mounts the login, an attacker sends 50 wrong passwords for the owner's email at once, from many addresses. The server runs as many as it can in parallel. Each burst gets about as many guesses as the server runs at once, not 5. The lock limits this, but only after 10 recorded failures. In-flight attempts still finish, so the attacker gets several times the spec's guess rate.
- Why it matters: the per-account limit is the main T5 control against password guessing. In PR 78 I treated a 4× weaker limit as a P2. This is the same class.
- Required correction (in M3e, before the login route merges): make the check and the count one step. Two ways:
  - **(a) Count first (my pick).** Before the Argon2 verify, upsert the account and IP counters and read back the new counts in one statement each. Refuse if a count goes over its limit. On a verified password, take back the account count (`count - 1`; `skiw_app` holds UPDATE) and reset the lock run. The counters still count failures, and the race is gone.
  - **(b) Serialise per account.** Take `pg_advisory_xact_lock` on the account key around check, verify and record. This holds one transaction open for the Argon2 time.
  
  Add a test: 20 parallel wrong passwords for one email → at most 5 password verifies (count the `passwords.verify` and `dummy_verify` calls) and at most 5 non-429 answers.
- Owner: builder
- Disposition: deferred to M3e (the first caller). It must land before the login route is mounted.
- Verification: the M3e review runs the parallel test and the scratch probe again.
- Status: open

### Notes (no severity)
- **The lock design [A] needs the owner's yes.** The builder follows spec Flow 5.1 ("10 consecutive fails → soft-lock 30 min") over the plan text ("≥ 10 within the lock window"). I agree: the spec wins, and "consecutive" with a reset on success is what the spec says. I advise the owner to accept it.
- **Anyone who knows a staff email can keep that account locked.** Ten wrong passwords lock it for 30 minutes, from any IP, and this can be repeated. This is the Flow 5.1 trade-off, not a defect here. M3e or M3g must decide whether the password lock also blocks passkey login. My advice: let a passkey login through, because a passkey cannot be guessed. Then the lock cannot shut a user out.
- **TOTP needs its own limit (M3f).** `reset_on_success` runs after a verified password, before the second factor. So these counters do not limit TOTP guesses. M3f must add a TOTP fail limit.
- **"After the commit" is true only with no outer transaction.** `record_failure` logs after its own `atomic()` block exits. If M3e calls it inside an outer `atomic()`, the counts and the log line can disagree on a rollback. M3e should log through `transaction.on_commit`, or call it outside any transaction. The builder already records the "no `ATOMIC_REQUESTS`" duty.
- **IPv6.** The per-IP key is the full address. A client with a /64 has many buckets. The builder keeps per-address because the spec says "per IP" and records the limit. The account limit and lock still hold. The owner can revisit this if the host takes IPv6 traffic.
- **Disclosed and accepted:** a `tenant_source_key` rotation resets all counters and locks; rows are never cleaned up (`skiw_app` has no DELETE); the `"malformed"` bucket is shared; `UvicornWorker` `forwarded_allow_ips` was read from the library, not tested.
