### [P2] The plan gives the migrator standing SELECT on `guard.tenant_mac_key`, but the spec says only the owner can read it, and §9 does not list the change
- Category: spec conformance (key secrecy)
- Rule: spec §4.1 `guard.tenant_mac_key` row; spec §4.2 "Tenant binding" item 1 ("`guard.tenant_mac_key`, which only the NOLOGIN owner `skiw_tenant_guard` can read"); TEN-02; builder §8 (a plan lists every spec change)
- Evidence: plan §3 M4c-2a step 6: "Each owner grants the migrator SELECT, INSERT, UPDATE and DELETE". Plan §9 item 2 lists only the membership. No item says that the migrator can read the key tables.
- Failure scenario: M4c-2a is built as planned. A later reviewer checks TEN-02 against the spec text, and finds a standing grant that the spec forbids and no recorded change allows. Worse: the grant lets a plain migrator connection run `pg_dump -t guard.tenant_mac_key` with no `SET ROLE`. Under Q1 (a) that read needs an explicit `SET ROLE`, which a reviewer can look for in migrations.
- Why it matters: the tenant MAC key is the root of the tenant binding. Anyone who holds it and has a `skiw_app` SQL session can mint a token for any agency.
- Required correction (plan text):
  1. Do the key writes in M4c-3 through `as_owner('skiw_tenant_guard', …)` and `as_owner('skiw_auth_lookup', …)`, or a `SET LOCAL ROLE` in the same step. Then drop step 6's standing grants. The compare ("same bytes left alone, different bytes stop `migrate`") then runs as the owner, which the spec allows.
  2. Add to §9 item 2: under Q1 (a), the migrator can read both key tables by `SET ROLE`. So the spec's "only the owner can read" becomes "only the owner, and the migrator acting as the owner through `SET ROLE`".
  3. Add a test to M4c-2a: `has_table_privilege('skiw_migrator', 'guard.tenant_mac_key', 'SELECT')` is false.
- Owner: builder
- Status: open

### [P2] Changing `SKIW_DEPLOYMENT_AGENCY_ID` would silently add a second agency
- Category: design gap (owner gate)
- Rule: `agents/PROJECT.md` §9 ("Second agency onboarding: not allowed"); plan §3 M4c-5 ("Exactly one uuid is allowed while the second-agency gate is locked")
- Evidence: plan §3 M4c-5. The seed is `INSERT … ON CONFLICT (id) DO NOTHING`, and it never updates or deletes. The plan checks that the config holds exactly one uuid. It does not check the table.
- Failure scenario: an operator edits `infra/host/env/production.env` and changes the agency id, for example by a copy-paste from staging. The next deploy's `migrate` inserts a second `agency` row. `/readyz` runs `with_agency(<new id>)`, sees the new row, and returns 200. From then on, new users (the M3e invite command) go into the new agency. The existing users and data stay in the old one. Nothing fails, and the "one agency" gate is broken without a decision.
- Why it matters: the second-agency gate is an owner gate with its own conditions (PROJECT §9). A config typo must not open it.
- Required correction (plan text): in the migrate step (not in `insert_agency`, which the A/B test fixtures use), after the lock and the `NO FORCE`, refuse and roll back when any `agency` row has a different id. Add a test in M4c-5: seed id X, then run the step with id Y → `migrate` exits ≠ 0, the table still holds only X, and FORCE is on.
- Owner: builder
- Status: open

### Notes (no severity)
- **The seed takes ACCESS EXCLUSIVE on `agency` on every deploy.** Every tenant-table write takes a key-share lock on the agency row through its FK. So writes queue behind the seed for up to `lock_timeout` (5 s), and a long transaction makes the deploy fail cleanly. At about 5 users this is acceptable. A later PR can skip the lock when the row is already there.
- **The schema check runs after the migrations are applied.** If it fails on a host, the bad table stays in the database (migrations are never reversed), and the old digest keeps serving. CI runs the same check first, so this needs a missed CI result. Say this in the M4c-6b runbook text.
- **`flush` also emits `post_migrate`.** Today no test or tool runs `flush` (the live tests override `django_db_setup`), so the role check is enough. If a test ever uses `TransactionTestCase`, the key-write receiver will refuse it as `skiw_app`.
- **`skiw_backup` can read the key tables.** It holds `pg_read_all_data` and BYPASSRLS (`roles.sql`). H6 keeps the key data out of dumps, and the backup coordinator's statement allow-list limits what it runs. This is spec-level and older than this plan.
