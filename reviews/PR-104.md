### [P1] CI's full-history secret scan fails on a test constant
- **Category:** CI gate (security job)
- **Evidence:**
  - `KEY_HASH = "<16 hex chars>" * 4` at `app/accounts/tests/test_user_tables_live.py:24`. The value is
    [REDACTED] here per the kit rule, though it is a fixed test pattern, not a secret.
  - The name contains `KEY` and the literal is high-entropy hex, so gitleaks' default `generic-api-key`
    rule matches it.
  - The line was added in `392c138`. `make secrets` scans the **full history**, so fixing it in a later
    commit on top won't clear the job.
- **Failure scenario:** the `security` job is red on every run of this branch, so the PR can't merge
  with all checks green. Merged as is, the hit stays in `main`'s history, and every later PR's scan
  fails too.
- **Required correction:**
  - Rewrite the branch so that no commit contains the literal, then force-push. Either:
    - derive it, for example `KEY_HASH = hashlib.sha256(b"session-revocation-test").hexdigest()`; or
    - rename it to something that doesn't look like a key, and build it so it isn't one literal.
  - Rerun gitleaks locally before pushing (`make secrets`, or the pinned image as above).
  - A `.gitleaksignore` fingerprint would also clear the scan. But it is an allowlist, which the owner
    turned down for a related case (PR 74 Q1). Use it only with the owner's yes.
- **Owner:** builder · **Disposition:** fix here · **Status:** open
