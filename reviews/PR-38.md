### [P2] Escrow filename is not made durable before installing keys
- Category: resilience / crash-consistency defect
- Rule: H4 escrow creation; init's escrow-before-key guarantee
- Evidence: escrow.py:56–65 fsyncs the encrypted file but never its parent directory. bootstrap_secrets.py:92 proceeds to key installation immediately; its only directory fsync at 98–100 covers host.secrets, not host.escrow. Instrumented successful init: eleven file fsync calls and one secrets-directory fsync; no escrow-directory fsync.
- Failure scenario: power loss/reboot after the secret-store directory is synced but before the escrow directory entry reaches disk can retain installed key files without retaining the bundle filename. Writing and syncing bundle bytes alone does not durably establish its directory entry.
- Why it matters: process-order escrow-first is not durable-order escrow-first, weakening bootstrap recovery protection. Isolated P2: no crash loss reproduced and the normal successful run has its bundle; this is the documented filesystem durability gap, not a claim that current keys were lost.
- Required correction: durably persist the encrypted bundle's directory entry before installing any key; account for newly created directory ancestors as needed. Keep the sync within failure cleanup, close descriptors on all paths, and retain atomic/no-overwrite key installation. Add an order/failure test for the escrow directory sync.
- Owner: Builder
- Verification: spy on file/directory fsync order and key installation; escrow-directory sync must precede the first key install. Inject failure at that sync and assert no key installed and no orphan bundle from the run. Use a root/disposable test only where actual ownership needs proof.
- Disposition: before merge
- Status: open

The primary [Linux fsync manual](https://man7.org/linux/man-pages/man2/fsync.2.html) explicitly distinguishes syncing file contents/metadata from syncing its containing directory entry.
