### Findings

### [P1] Cancel during confirm can leave a hidden signed-in session behind the sign-in screen
- Category: security weakness / defect
- Rule: AUTH-13; FE-21; reviewer evidence rule §3
- Evidence: `SecondFactor.back()` aborts the one controller and immediately renders `signed_out` (`web/src/screens/SecondFactor.tsx:72-75`). `round()` gives that same signal to the confirm POST and returns null after abort (`web/src/passkey.ts:81-89`). `api.run()` catches an aborted fetch as `NETWORK`; if body parsing is aborted, `keepToken()` never receives the new CSRF value (`web/src/api.ts:17-26`). On a successful passkey confirm, the server calls `login()`, which cycles the session and rotates CSRF, then returns the new token (`app/accounts/views.py:192-205`; `app/accounts/auth/login.py:44-69`). The durable decision acknowledges that a confirm already completed on the server stays completed while “the page just does not act” (`docs/DECISIONS.md:1527`). No state read or logout follows `back()`; App simply renders SignIn (`web/src/App.tsx:122-143`).
- Browser probe: with Chromium 153, abort before response headers kept the old cookie, but abort after `Set-Cookie` headers and before a delayed JSON body returned `AbortError` **and kept the new cookie**: `beforeHeaders={AbortError, probe=old}`, `afterHeaders={AbortError, probe=new}`. This matches the Fetch processing order: response cookies are stored from headers before later body consumption (WHATWG Fetch, “parse and store response Set-Cookie headers”). The unit server intentionally ignores the abort signal (`web/src/testkit.ts:7-19`), so its delayed-confirm tests cannot reproduce this browser state.
- Failure scenario: the user completes the platform passkey prompt, then clicks “Use a different account” while confirm is in flight. The server completes login and response cookies reach the browser, but abort interrupts JSON parsing. The UI now shows SignIn, while a reload opens the prior user’s authenticated account; the module-level API token can also remain the pre-login CSRF value. On a shared device, the user can walk away believing the prior account was left.
- Why it matters: client navigation and server authentication disagree at the exact boundary intended to switch accounts. Aborting fetch does not roll back server authentication, and hiding the success response is not a sign-out.
