### Findings

### [P1] Leaving the screen does not invalidate an in-flight passkey ceremony
- Category: defect
- Rule: FE-21; passkey interaction contract
- Evidence: `SecondFactor.passkey()` awaits the whole begin → browser → confirm sequence and unconditionally calls `moved()` afterward (`web/src/screens/SecondFactor.tsx:38-51`), while “Use another account” remains enabled and immediately calls `onNext("signed_out")` (`:72-74`). `StepUp.passkey()` likewise awaits the sequence and can later call `onVerified` through `settled()` (`web/src/screens/StepUp.tsx:34-39`, `:55-68`), while Escape and Cancel call `onCancel` without aborting or invalidating it (`:71-73`, `:97-99`). `round()` accepts no cancellation signal (`web/src/passkey.ts:76-81`). The tests cover ordinary cancel/refusal by the authenticator, but not UI exit while begin or confirm is pending (`web/src/passkey.test.tsx:132-176`, `:198-223`).
- Failure scenario: on a slow begin response, the user chooses another account or cancels the step-up. The response then arrives, opens the platform passkey prompt on the replacement screen, confirms, and invokes `onNext("signed_in")` or `onVerified` after the user already exited. The callback contract can therefore report both cancel and success for one dialog.
- Why it matters: cancellation is not final, and an authentication or sensitive-action flow can continue after the user explicitly left it.
- Required correction: make UI exit invalidate or abort the active begin/browser/confirm operation. A late result must not open a prompt, send confirm, change screens, call `onVerified`, or call `onSignedOut`. Keep cancellation available rather than merely trapping the user behind a disabled exit.
- Owner: builder
- Verification: add deferred-begin and deferred-confirm tests for SecondFactor and StepUp; exit/cancel first, resolve the deferred work, and prove there is no prompt/confirm request or late transition/callback as applicable. Re-run Vitest and the browser flow.
- Status: open

### [P1] Passkey and availability messages falsely mark the code field invalid
- Category: guardrail mismatch
- Rule: A11Y-03
- Evidence: both screens keep code errors, passkey refusal/cancellation, unsupported-browser status, no-passkey status, rate-limit errors, and network errors in the same `error` state. Any non-null value is passed to `Field.errorId` (`web/src/screens/SecondFactor.tsx:44-51`, `:58-59`; `web/src/screens/StepUp.tsx:61-68`, `:86-87`). `Field` turns that into `aria-invalid=true` and links the message to the input (`web/src/forms.tsx:35-36`). The new no-passkey test explicitly requires the code field’s `aria-describedby` to contain `code-error` even though no code was rejected (`web/src/passkey.test.tsx:155-164`).
- Failure scenario: a user cancels a passkey, has no passkey, uses an unsupported browser, or encounters a passkey/network failure without entering a code. A screen reader is told that the untouched code input is invalid and that the passkey/system status is its validation error.
- Why it matters: the programmatic error relationship is false and can send assistive-technology users to correct a value that was never submitted.
- Required correction: separate code-field validation state from general/passkey status. Only an actual rejected/invalid code should set the code input’s `aria-invalid` and error `aria-describedby`; passkey, availability, limit, and network messages should remain independently announced in a polite live region. Focusing the code as the fallback is fine, but it must not be marked invalid unless its value failed validation.
- Owner: builder
- Verification: for passkey cancel/refusal/no-passkey/unsupported/limit/network cases, assert the message is announced while the code field has neither `aria-invalid=true` nor an error description; retain the existing code-refusal assertions that do mark and describe the field. Run axe in the browser on both states.
- Status: open
