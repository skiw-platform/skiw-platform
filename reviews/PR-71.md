### Findings

### [P1] The favicon bypasses the approved hashed-static-asset contract
- Category: spec/guardrail mismatch
- Rule: spec D2 (`docs/specs/2026-10-05-skiw-platform-stack-design.md:86`)
- Evidence: `web/public/assets/icon.svg:1` is emitted at the stable URL referenced by `app/shell/templates/shell/shell.html:7` and `web/index.html:7`; `app/shell/views.py:16,45-48` gives every `/assets/` response a one-year immutable cache; `docs/DECISIONS.md:395` explicitly records that this asset is unhashed and relies on a future manual rename.
- Failure scenario: a later branding or icon correction replaces `icon.svg` at the same URL, while existing browsers retain the old immutable response for up to one year. The code and build do not enforce the decision-log instruction to choose a new name.
- Why it matters: D2 requires hashed static assets, and this PR introduces a deliberate exception without an owner-approved spec change. It also makes a likely visual asset update depend on an unenforced manual cache-busting step.
- Required correction: give the icon a content-versioned/hashed URL through the build and make both the Django shell and Vite development shell resolve that URL. Add a regression proving that an immutable icon URL changes with its content (or otherwise prove that no unhashed asset receives immutable caching).
- Owner: builder
- Verification: inspect the production build/manifest and shell response, then change the icon in a scratch copy and prove the emitted URL changes; rerun the shell unit tests, production build, and browser CSP test.
- Status: open
