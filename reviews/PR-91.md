### Findings

### [P2] The SQL side is never checked against the committed vector
- **Category:** test gap (spec requirement)
- **Evidence:** spec v1.21 §4.2 item 2: "The exact bytes are pinned by a committed test vector that both
  implementations must reproduce." Plan M4c-4a tests: "Python and SQL agree on a fixed vector." The live
  test `test_the_verifier_reproduces_the_vector_and_refuses_retired_and_absent_versions` (despite its
  name) mints with the vector **key** but the live xid and database name, and only checks that the
  verifier accepts. The SQL encoding is therefore checked only against the Python minter on small xids
  and an ASCII database name. It is never checked against the committed bytes, a large xid
  (`xid8send` above 2^32) or a multi-byte name (`octet_length` vs character length).
- **Failure scenario:** a later edit to `MAC_INPUT` and to `token.py` together (or a refactor that swaps
  `octet_length` for `length`) keeps every current test green. The verifier and minter agree with each
  other but no longer with the spec's encoding. A second implementation (the bridge, M14) written to the
  spec then fails every token. The vector exists to catch exactly this.
- **Required correction:** add a live test that evaluates the migration's `MAC_INPUT` expression (import
  it from the migration module, as my probe did) with the vector's literal database name, agency and xid.
  It must give `VECTOR_INPUT`, and `guard.hmac(…, VECTOR_KEY, 'sha256')` over it must give the MAC in
  `VECTOR`. Add one more row with a multi-byte name and xid 2^64−1, compared with `mac_input`. Rename or
  re-word the existing test so it doesn't claim to reproduce the vector.
- **Owner:** builder · **Disposition:** before merge · **Status:** open

### [P3] Semgrep `tenancy-token-setting` choice (the builder asked the reviewer)
- **Decision:** keep this PR as it is. In M4c-4b, take the other option: add `/app/tenancy/tests/` to the
  rule's excludes and to the plan table (as `tenancy-guard-key-sql` does), and write the tests with the
  literal setting name.
- **Why:** passing the name as a bound parameter (`set_config(%s, %s, true)`) works because the rule only
  sees literal SQL. That same form would let any module set the token unseen. The spec makes the MAC,
  not the lint, the boundary, so this is hygiene, not a hole. But the tests shouldn't model the bypass.
  M4c-4b, which adds the Semgrep TEN-09 rules, should also:
  - flag `set_config` with a non-literal first argument outside `tenancy.binding`;
  - limit imports of `tenancy.token.mint` to `tenancy.binding` / `async_binding` and tests (import-linter
    or Semgrep). The key is in settings, so any module that imports `mint` can make a token for any agency
    outside `with_agency()`.
- **Owner:** builder · **Disposition:** deferred to M4c-4b (named in the plan row "Semgrep TEN-09 rules")
  · **Status:** open (deferred)
