### Findings

### [P2] With the count fixed, a known-password attacker can still guess codes all day without tripping the soft-lock or the owner alert
- Category: material risk (forward, for the helper's next consumer)
- Rule: AUTH-06; spec Flow 5.1 "Failures: 10 consecutive fails → account soft-lock 30 min + owner alert", (1) "5 fails / 15 min / account"
- Evidence:
  - `factor_reserve` caps a user at `SKIW_AUTH_FAILS_PER_ACCOUNT` (5) wrong codes per fixed `SKIW_AUTH_WINDOW_MIN` (15) window.
  - Nothing in the factor path feeds the consecutive-failure lock (`throttle.record_failure` → `LOCK`, `account.locked` event, log warning), and it writes no event of its own (PR 128 R1 P3 #1 is still open).
  - This PR only builds the count; 3c-1b wires sign-in to it (DECISIONS M3f-3c-1a "TOTP and recovery codes will share the one per-user budget").
- Failure scenario: someone with a stolen password (phished, reused) runs 5 wrong TOTP guesses every 15 minutes, which is 480 a day. At ±1 skew that is 3 valid codes in 10⁶ per guess, so about 0.14 % a day and about 4 % a month. Every attempt passes the password step, so `reset_on_success` keeps the password soft-lock at zero. Nobody is told.
- Why it matters: the spec's "soft-lock + owner alert" exists to make sustained guessing visible. As built so far, the second factor is the only barrier left, and its failures are invisible.
- Required correction (in 3c-1b): decide and record how second-factor failures meet Flow 5.1 "Failures". For example, wrong codes count toward the consecutive soft-lock (and its owner alert), or a factor-specific lock and alert fires after N consecutive wrong codes. Test it: N consecutive wrong codes lock the user for `SKIW_AUTH_LOCK_MIN` and produce the alert or event; a success resets it. If you think the spec means the password step only, put that to Ying as a question rather than leaving it implicit.
- Owner: builder (3c-1b); Ying if the spec reading is disputed
- Verification: 3c-1b review: the lock and alert test, and the DECISIONS entry.
- Disposition: deferred to M3f-3c-1b (`accounts.auth.second_factor.attempt`).
- Status: open

### [P3] Release-on-fault must stay limited to faults before the code is compared
- Category: material risk (guidance for 3c-1b)
- Evidence: `confirm_totp` releases the reservation on *any* `BaseException` from `_confirm` (`factors.py`, `except BaseException: throttle.factor_release(reservation)`). For enrolment this is safe: after `totp.accept` returns None, the only work left is leaving `with_agency()`, which commits a read-and-lock transaction an attacker cannot make fail.
- Failure scenario (3c-1b, if copied): if the sign-in path does more database work after a *wrong* comparison, and that work can be made to fail (a lock wait under `lock_timeout`, a serialization error), each failure gives the guess back. The attacker then sees 500 instead of 401 and the guess goes uncounted.
- Required correction (3c-1b): release only for faults that happen before the comparison, or decide the outcome first and keep a wrong code counted even if later work raises. Add a test that a fault after a wrong comparison leaves the count at +1.
- Owner: builder · Status: open (3c-1b)

### [P3] Runbook and DECISIONS wording
- Runbook "Too many wrong codes … at enrolment and at sign-in alike": sign-in isn't built yet (3c-1b). The line is right once 3c-1b merges; until then it describes behaviour that doesn't exist. Add "(sign-in from M3f-3c)" or check it in 3c-1b.
- DECISIONS design call (1), the success give-back, claims a cost: "one extra guess in flight". There isn't one. The count is wrong codes plus attempts in flight and is capped at LIMIT, and only non-wrong outcomes give back. So wrong codes per user per window never exceed LIMIT, with or without the user's own sign-ins. The decision stands; the cost line overstates it. Correct it in 3c-1b's entry if you touch it.
