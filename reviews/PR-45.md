### [P1] SSH Match overrides are invisible to the hardening check
- Category: defect / spec mismatch.
- Rule: spec §8.4 H2 key-only SSH and PermitRootLogin no; M1 plan §3 M1f effective sshd settings; UNI-03.
- Evidence: `infra/host/skiw_host/hardening.py:84–94` only invokes `sshd -T` without connection parameters. `stale_files` at lines 194–201 examines only drop-ins sorting before 00-skiw.conf. Later Match blocks can override protected global settings even though ordinary later global settings cannot. [OpenSSH sshd manual](https://man.openbsd.org/sshd.8) documents applying Match rules with -C; [sshd_config manual](https://man.openbsd.org/sshd_config) documents conditional overrides.
- Failure scenario: a later `90-local.conf` contains `Match User root`, `PasswordAuthentication yes` and `PermitRootLogin yes`. The global output remains passwordauthentication no / permitrootlogin no, so both sshd and stale-files PASS, while matching root connections are allowed those insecure settings.
- Verification performed: created a disposable configuration and generated test host key inside the review snapshot, with the real shipped 00-skiw.conf values and the later Match block. Native `/usr/sbin/sshd` (OpenSSH 10.3p1 on macOS) exited 0 in both modes: plain -T printed no/no; -T -C user=root,host=localhost,addr=127.0.0.1 printed yes/yes. Feeding that real global output to the actual hardening.main with the other host fixtures returned 0 and all seven PASS lines. No SSH server was started, no host configuration changed, and generated key/config files were removed by the temporary-directory context.
- Why it matters: a security-sensitive override passes the post-change/monthly security gate. This is a false attestation of the SSH policy, not just unsupported formatting.
- Required correction: verify protected settings for the relevant connection policies, including conditional Match rules and included files. A closed, validated policy for permitted Match overrides is acceptable; do not rely on a single arbitrary -C sample that misses other users or addresses. Add regression coverage for later user/group/address conditions that weaken password, keyboard-interactive or root-login restrictions, while preserving legitimate forced-command policy where required.
- Owner: Builder.
- Verification: the demonstrated later root Match block must FAIL; safe conditional policy must PASS; missing or unparseable context evidence must fail closed. Keep duplicate-port regressions.
- Status: open.

### [P1] Docker’s on-disk settings can PASS while the active daemon violates H2
- Category: defect / material risk.
- Rule: spec §8.4 H2 no TCP daemon socket and default no-new-privileges; M1 plan §3 M1f effective hardening check; UNI-03.
- Evidence: `hardening.py:148–158` checks live-restore/logging from docker info, but checks no-new-privileges and hosts only in daemon.json. `hardening.py:170–172` excludes every loopback listener from the socket check. Docker supports a systemd ExecStart override with `-H fd:// -H tcp://127.0.0.1:2375`, independently of daemon.json: [Docker remote-access documentation](https://docs.docker.com/engine/daemon/remote-access/). In the exact pinned Engine source, docker info SecurityOptions includes name=no-new-privileges only when the live daemon has it enabled: [Moby docker-v29.9.1 info.go, lines 178–212](https://github.com/moby/moby/blob/docker-v29.9.1/daemon/info.go#L178-L212).
- Failure scenarios: (1) daemon.json has no-new-privileges true but a running daemon still uses its earlier false setting, or was started with another config file; the live SecurityOptions lacks the flag and is ignored. (2) a systemd override adds a loopback TCP Docker API endpoint while daemon.json retains the expected file; the daemon check sees no configured TCP host, and the socket check intentionally skips the live loopback listener. Such an API endpoint is outside the root-only Unix-socket boundary, even without a public listener.
- Verification performed: added a valid-shaped info fixture with live-restore true, journald and SecurityOptions lacking no-new-privileges, plus an ss fixture showing `127.0.0.1:2375` owned by dockerd. Left daemon.json unchanged. Actual hardening.main returned 0 and all seven PASS lines. This was an output-fixture reproduction backed by the pinned source and official startup documentation, not a claim to have reconfigured or run an insecure Docker daemon.
- Why it matters: the check can certify a stale file while the runtime lacks the required privilege default or exposes a root-equivalent API. The public-port filter is not sufficient to enforce the separate no-TCP-Docker rule.
- Required correction: verify no-new-privileges from the live daemon evidence and verify the actual daemon endpoints/startup configuration, including systemd/CLI/socket-activation paths and loopback TCP. Retain the file check as configuration evidence. Missing fields, unknown endpoint evidence or unparseable output must fail closed. Do not reject all ordinary loopback services to compensate for this Docker-specific rule.
- Owner: Builder.
- Verification: independently test live NNP off with a compliant file; live loopback Docker TCP with a compliant file; CLI/alternate config drift; missing runtime fields; and a compliant active Unix-only daemon. Each insecure/unknown case must fail.
- Status: open.

### [P1] Named APT origin entries bypass the security-only comparison
- Category: defect / spec mismatch.
- Rule: M1 host security-only automatic-update contract (`infra/host/apt/52skiw-unattended`); spec §8.4 H2; UNI-03.
- Evidence: `hardening.py:130–145` parses dump keys but compares only the literal unnamed list keys `Unattended-Upgrade::Allowed-Origins::` and `Unattended-Upgrade::Origins-Pattern::`. Named children such as `Allowed-Origins::extra` and `Origins-Pattern::extra` are ignored. The unattended-upgrades implementation reads all child values with apt_pkg.config.value_list for both lists: [upstream implementation, get_allowed_origins_legacy/get_allowed_origins](https://github.com/mvo5/unattended-upgrades/blob/master/unattended-upgrade#L946-L985).
- Failure scenario: a later APT config adds `Unattended-Upgrade::Allowed-Origins::extra "Ubuntu:noble-updates";` while retaining the expected anonymous security entry. unattended-upgrades accepts the extra non-security origin; the checker still sees its expected anonymous value and returns PASS. A named Origins-Pattern entry has the same gap.
- Verification performed: actual hardening.main with that extra valid dump line returned 0 and seven PASS lines. In a separate disposable offline container using cached Debian image d74eeac9a635, actual apt-config dump produced the anonymous security child and named extra child exactly in this shape. No package install, host mount, existing container or host configuration was changed; the --rm container was removed automatically. Upstream value_list consumption establishes the effect on the accepted origins; no upgrade was executed.
- Why it matters: the check promises to validate the effective security-only origin policy but omits valid APT list syntax. This allows an expanded automatic-update policy to pass the host gate.
- Required correction: validate the complete relevant config subtrees, collecting named as well as unnamed children, or reject unsupported named entries explicitly. Prove that every effective Allowed-Origins/Origins-Pattern entry is permitted; do not silently skip entries based on the key spelling.
- Owner: Builder.
- Verification: named non-security entries in either list must FAIL; valid security-only configuration must PASS; add real-shaped dump regressions for both named and anonymous entries and malformed/unsupported list structure.
- Status: open.
